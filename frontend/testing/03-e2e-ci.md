## 1. E2E는 무엇을, 어느 범위로

E2E(End-to-End)는 **실제 브라우저에서 사용자 시나리오 전체**를 검증한다(로그인→상품 담기→결제). 가장 신뢰도 높지만 느리고 깨지기 쉬워, **핵심 happy path 위주로 소수만** 둔다.

```js
// Playwright
import { test, expect } from '@playwright/test';

test('로그인 후 대시보드 진입', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('이메일').fill('a@b.com');
  await page.getByLabel('비밀번호').fill('pw');
  await page.getByRole('button', { name: '로그인' }).click();
  await expect(page.getByRole('heading', { name: '대시보드' })).toBeVisible();
});
```

> 범위 가이드: 단위/통합으로 잡을 수 있는 건 거기서 잡고, E2E는 "여러 시스템이 실제로 함께 동작하는가"(라우팅·인증·결제 연동)만 검증한다.

---

## 2. 안정적인 E2E 작성 원칙

- **사용자 관점 선택자**: `getByRole`/`getByLabel` 우선, CSS 클래스·XPath 지양(구조 바뀌면 깨짐). 필요시 `data-testid`.
- **자동 대기(auto-wait)**: 임의 `sleep` 금지. Playwright는 요소가 액션 가능해질 때까지 자동 대기(web-first assertion). `expect(...).toBeVisible()`가 재시도한다.
- **테스트 격리**: 각 테스트가 독립 상태에서 시작(시드 데이터·로그인 상태 주입). 테스트 간 의존 금지.
- **상태 셋업은 UI 우회**: 로그인 등 전제 조건은 매번 UI로 클릭하지 말고 API/스토리지 주입으로 빠르게(`storageState`).

## 3. 플레이키(flaky) 테스트 다루기

같은 코드에 통과/실패가 갈리는 테스트는 신뢰를 무너뜨린다. 주원인과 대책:

| 원인 | 대책 |
|------|------|
| 고정 `sleep`·타이밍 의존 | 조건 기반 대기(web-first assertion) |
| 네트워크 변동 | 핵심 외 의존은 모킹/스텁, 재시도 |
| 테스트 간 상태 공유 | 격리·시드 초기화 |
| 애니메이션·포커스 경쟁 | 애니메이션 비활성, 명시적 대기 |
| 시간/타임존/로케일 | 고정 주입 |

> 플레이키 테스트는 **격리해 추적하되 방치하지 말 것**. 재시도(retry)는 임시방편이지 근본 해결이 아니다. 무시되기 시작하면 진짜 실패도 묻힌다.

## 4. 시각 회귀 테스트

CSS·레이아웃 깨짐은 기능 테스트로 못 잡는다. **스크린샷을 기준(baseline)과 비교**해 시각적 변화를 감지한다.

```js
// Playwright 시각 비교
await expect(page).toHaveScreenshot('dashboard.png', { maxDiffPixels: 100 });
```

- 컴포넌트 단위는 **Storybook + Chromatic**, 페이지 단위는 Playwright/Percy.
- 함정: 폰트 렌더·안티앨리어싱·동적 데이터·애니메이션이 거짓 차이를 만든다 → 데이터 고정, 애니메이션 끄기, 허용 임계치 설정.
- 의도된 변경이면 baseline을 갱신(리뷰 후 승인).

## 5. 접근성·계약 테스트

- **접근성 자동 검사**: `axe-core`(jest-axe/Playwright axe)로 위반(대비, 라벨 누락 등)을 테스트에 포함. 자동 검사는 a11y 이슈의 일부(약 30~50%)만 잡으니 수동 검증과 병행.

```js
import { injectAxe, checkA11y } from 'axe-playwright';
await injectAxe(page);
await checkA11y(page);
```

- **계약 테스트(contract test)**: 프론트와 백엔드가 합의한 API 스키마(OpenAPI/Pact)를 양쪽이 검증해, 통합 환경 없이도 "인터페이스가 맞는지"를 보장. 마이크로서비스·BFF에서 유용.

## 6. CI 파이프라인 통합

테스트는 **자동으로, 빠르게, 신뢰성 있게** 돌아야 의미가 있다.

```yaml
# 개념 예시 (GitHub Actions)
jobs:
  test:
    steps:
      - run: npm ci
      - run: npm run lint && npm run typecheck   # 정적 (가장 빠름, 먼저)
      - run: npm run test:unit -- --coverage      # 단위/통합
      - run: npx playwright test                  # E2E (느림, 뒤에/병렬)
```

전략:
- **빠른 것부터**: 타입·린트 → 단위/통합 → E2E. 빨리 실패시켜 피드백 단축(fail fast).
- **병렬화·샤딩**: E2E를 여러 워커로 분할.
- **PR 게이팅**: 머지 전 필수 통과. 커버리지 임계·시각 회귀 승인을 게이트로.
- **캐싱**: 의존성·브라우저 바이너리 캐시로 시간 단축.
- 변경 영향 범위만 테스트(affected) → 모노레포에서 특히 효과.

## 7. 면접 포인트

**Q. E2E는 어느 범위로 두나요?**
> 핵심 사용자 시나리오(로그인·결제 같은 happy path) 위주로 소수만 둔다. 신뢰도는 가장 높지만 느리고 깨지기 쉬워, 단위/통합으로 잡을 수 있는 건 거기서 잡고 E2E는 여러 시스템이 실제로 함께 동작하는지만 검증한다.

**Q. E2E를 안정적으로 만드는 핵심은?**
> 임의 `sleep` 대신 조건 기반 자동 대기(web-first assertion), 사용자 관점 선택자(getByRole), 테스트 격리와 시드 초기화, 전제 상태는 UI 대신 API/스토리지로 주입. 이렇게 타이밍·구조·상태 의존을 제거한다.

**Q. 플레이키 테스트의 원인과 대처는?**
> 고정 sleep·네트워크 변동·상태 공유·애니메이션·시간 의존이 주원인. 조건 대기·모킹·격리·애니메이션 비활성·시간 고정으로 해결한다. 재시도는 임시방편일 뿐이고, 방치하면 진짜 실패가 묻히므로 추적해 고쳐야 한다.

**Q. 시각 회귀 테스트는 무엇을 잡고 무엇이 함정인가요?**
> 기능 테스트가 못 잡는 CSS·레이아웃 깨짐을 스크린샷 비교로 잡는다. 함정은 폰트 렌더·동적 데이터·애니메이션이 만드는 거짓 차이라, 데이터를 고정하고 애니메이션을 끄고 허용 임계치를 둔다.

**Q. CI에서 테스트를 어떻게 배치하나요?**
> 빠른 정적 검사(타입·린트)를 먼저, 그다음 단위/통합, 느린 E2E는 뒤에 병렬·샤딩으로. fail fast로 피드백을 줄이고, PR 머지 게이트로 필수 통과를 강제하며, 의존성·브라우저 캐시로 시간을 단축한다.
