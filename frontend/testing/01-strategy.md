## 1. 테스트의 목적: 확신, 커버리지가 아니라

테스트는 **코드를 바꿔도 동작이 깨지지 않는다는 확신**을 주기 위한 것이다. 그래서 "변경에 강하고(리팩터링 허용), 실패하면 진짜 버그"인 테스트가 좋은 테스트다.

- 구현 세부에 결합된 테스트 → 리팩터링마다 깨짐(거짓 양성) → 결국 삭제됨.
- 느린 테스트 → 안 돌림 → 무의미.
- 불안정한(flaky) 테스트 → 신뢰 상실 → 무시됨.

> "테스트가 사용자가 코드를 쓰는 방식과 닮을수록 더 큰 확신을 준다." — Testing Library 철학.

---

## 2. 테스트 종류와 트레이드오프

| 종류 | 범위 | 속도 | 신뢰도 | 비용 |
|------|------|------|--------|------|
| **단위(Unit)** | 함수/모듈 1개 | 매우 빠름 | 낮음(통합 경로 못 봄) | 낮음 |
| **통합(Integration)** | 여러 모듈 협업 | 빠름 | 높음 | 중간 |
| **E2E** | 실제 브라우저 전체 흐름 | 느림 | 매우 높음 | 높음 |
| **정적(Static)** | 타입·린트 | 즉시 | (버그 일부 예방) | 매우 낮음 |

위로 갈수록 **실제 사용자에 가까워 신뢰는 높지만 느리고 비싸다**. 핵심은 균형이다.

## 3. 테스트 피라미드 vs 테스트 트로피

**테스트 피라미드(전통)**: 단위 多 → 통합 中 → E2E 少. 빠른 단위 테스트를 토대로 쌓는다.

```
      /\      E2E (적게)
     /  \     통합
    /____\    단위 (많이)
```

**테스트 트로피(Kent C. Dodds, 프론트엔드 권장)**: **통합 테스트에 무게**를 둔다. 정적(타입/린트)을 바닥에 깔고, 단위보다 통합이 ROI가 높다고 본다.

```
      ___
     [E2E]
    [통합 ████]   ← 가장 두껍게
    [단위]
   [정적 타입]
```

> 프론트엔드는 컴포넌트가 여러 단위(상태·렌더·이벤트)의 협업이라, 단위를 잘게 쪼개 모킹하면 정작 통합 버그를 못 잡는다. "컴포넌트를 사용자처럼 렌더해 상호작용을 검증"하는 통합 테스트가 가성비가 가장 높다.

## 4. 무엇을 테스트할까 — 동작 vs 구현

**동작(behavior)을 테스트하고 구현(implementation)을 테스트하지 마라.**

```jsx
// ❌ 구현 결합: 내부 상태/메서드를 직접 검사 → 리팩터링하면 깨짐
expect(wrapper.state('count')).toBe(1);

// ✅ 동작 검증: 사용자가 보는 결과 → 내부를 바꿔도 통과
fireEvent.click(screen.getByRole('button', { name: '증가' }));
expect(screen.getByText('카운트: 1')).toBeInTheDocument();
```

테스트 우선순위:
1. **핵심 비즈니스 경로**(결제, 로그인, 폼 제출) — 반드시.
2. **버그가 났던 곳** — 회귀 방지 테스트.
3. **복잡한 로직·엣지 케이스**(날짜 계산, 권한 분기).
4. 게터/세터, 단순 표시 등 깨질 일 없는 것 — 굳이 안 함.

쿼리 우선순위(Testing Library): 접근성 우선 — `getByRole` > `getByLabelText` > `getByText` > (최후) `getByTestId`. 이러면 테스트가 접근성도 함께 강제한다.

## 5. 좋은 테스트의 속성 (FIRST)

- **F**ast — 빠르게(자주 돌리려면).
- **I**solated — 독립적(순서·공유 상태에 의존 X).
- **R**epeatable — 결정적(시간·랜덤·네트워크에 흔들리지 않게 → 모킹/고정).
- **S**elf-validating — 통과/실패가 자동 판정(수동 확인 X).
- **T**imely — 적시에(가능하면 코드와 함께/먼저, TDD).

```js
// 비결정성 제거 예: 시간 고정
vi.useFakeTimers();
vi.setSystemTime(new Date('2024-01-01'));
```

> Arrange-Act-Assert(준비-실행-검증) 구조로 한 테스트는 **하나의 동작**만 검증하면 실패 원인이 명확하다.

---

## 6. 커버리지를 읽는 법

커버리지(라인/분기/함수)는 "**테스트가 안 된 곳**"을 찾는 지표이지 품질 보증이 아니다.

- 100% 커버리지도 잘못된 단언이면 버그를 못 잡는다(실행만 되고 검증 안 됨).
- 목표는 숫자가 아니라 "핵심 경로가 커버됐는가". 분기 커버리지를 라인보다 중시.
- **변이 테스트(mutation testing)**: 코드를 일부러 변형해 테스트가 잡아내는지 본다 → 커버리지보다 진짜 효과를 측정.

## 7. 면접 포인트

**Q. 테스트의 목적은 무엇인가요?**
> 커버리지 숫자가 아니라 "코드를 바꿔도 동작이 안 깨진다는 확신"이다. 그래서 리팩터링을 허용하고(구현에 결합되지 않고) 실패 시 진짜 버그인 테스트가 좋다.

**Q. 테스트 피라미드와 테스트 트로피의 차이는?**
> 피라미드는 빠른 단위 테스트를 가장 많이 두는 전통 모델, 트로피는 정적 분석을 바닥에 깔고 **통합 테스트에 무게**를 두는 프론트엔드 권장 모델이다. 컴포넌트는 여러 단위의 협업이라 통합 테스트의 ROI가 높기 때문이다.

**Q. 구현이 아니라 동작을 테스트하라는 말의 의미는?**
> 내부 상태·메서드 호출을 검사하면 리팩터링마다 깨진다(거짓 양성). 사용자가 보는 출력·상호작용 결과를 검증하면 내부를 바꿔도 통과하므로 리팩터링에 강하고 진짜 회귀만 잡는다. Testing Library가 `getByRole` 같은 접근성 쿼리를 권장하는 이유다.

**Q. 무엇을 우선 테스트하나요?**
> 핵심 비즈니스 경로(결제·로그인), 버그가 났던 곳(회귀 방지), 복잡한 로직/엣지 케이스다. 단순 게터나 깨질 일 없는 표시는 굳이 안 한다.

**Q. 커버리지 100%면 충분한가요?**
> 아니다. 실행은 됐지만 단언이 부실하면 버그를 못 잡는다. 분기 커버리지를 중시하고, 진짜 효과는 변이 테스트(코드를 변형해 테스트가 잡는지)로 측정한다. 커버리지는 "안 된 곳 찾기" 지표일 뿐이다.
