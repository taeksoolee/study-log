## 1. 수직 확장 vs 수평 확장은?

**답변:**
수직(scale-up)은 한 서버의 사양을 키우는 것 — 단순하지만 한계·SPOF·비용 급증. 수평(scale-out)은 서버 수를 늘리는 것 — 사실상 무한 확장·내결함성이 있으나 분산(로드밸런싱·상태 공유·일관성) 복잡성이 생긴다. 대규모는 수평이 정석.

## 2. 로드 밸런서의 역할과 알고리즘은?

**답변:**
트래픽을 여러 서버로 분산하고 헬스체크로 죽은 노드를 제외한다. 알고리즘: 라운드로빈, 최소 연결(least connections), 가중치, IP/일관 해시(같은 사용자→같은 서버, 세션 고정). L4(전송)·L7(애플리케이션, 경로 기반 라우팅) 계층이 있다.

## 3. 무상태(stateless) 서비스가 왜 중요한가요?

**답변:**
서버가 요청 간 상태를 안 들고 있어야 아무 서버나 요청을 처리할 수 있고(수평 확장·장애 대체 용이), 세션은 외부 저장소(Redis)나 토큰(JWT)으로 분리한다. 상태가 서버에 박히면(sticky) 확장과 장애 복구가 어려워진다.

## 4. 처리량(throughput)과 지연(latency)은?

**답변:**
지연은 한 요청의 응답 시간, 처리량은 단위 시간당 처리 요청 수다. 둘은 독립적일 수 있다(배칭은 처리량↑·지연↑). 성능 목표는 평균이 아니라 p95/p99 지연으로 잡아야 꼬리 사용자를 본다.

## 5. 캐싱은 어디에 두나요?

**답변:**
계층별로: 브라우저 → CDN(엣지) → 리버스 프록시 → 애플리케이션(인메모리/Redis) → DB 쿼리 캐시. 가장 사용자에 가깝고 비용 낮은 곳부터 캐시하면 효과가 크다. 읽기 많고 쓰기 적은 데이터가 캐싱 대상.

## 6. 캐시 무효화 전략은?

**답변:**
- **Cache-aside**(lazy): 앱이 미스 시 DB 조회 후 캐시 채움(가장 흔함).
- **Write-through**: 쓰기 시 캐시+DB 동시 갱신(일관성↑, 쓰기 지연).
- **Write-back**: 캐시에 먼저 쓰고 나중에 DB 반영(빠르나 유실 위험).
- TTL 만료 + 명시적 무효화. "캐시 무효화는 컴퓨터 과학의 2대 난제 중 하나."

## 7. 캐시 스탬피드(stampede)란?

**답변:**
인기 키가 동시에 만료되면 수많은 요청이 한꺼번에 DB로 몰려(thundering herd) 과부하가 나는 현상. 대처: 갱신 잠금(한 요청만 재계산), TTL에 지터 추가, 만료 전 비동기 갱신(stale-while-revalidate), 영구 캐시+백그라운드 리프레시.

## 8. 복제(replication)와 읽기/쓰기 분리는?

**답변:**
데이터를 여러 노드에 복제해 가용성·읽기 확장을 얻는다. 보통 단일 리더(쓰기)+다수 팔로워(읽기) 구조로 읽기를 분산한다. 복제 지연(replication lag)으로 방금 쓴 걸 못 읽는 문제가 생겨, 필요한 읽기는 리더로 보내거나 read-your-writes 보장을 둔다.

## 9. 샤딩(sharding)이란?

**답변:**
데이터를 키 기준으로 여러 DB에 수평 분할해 단일 DB 한계를 넘는다. 샤딩 키 선택이 핵심(고른 분포, 핫스팟 회피). 범위·해시·디렉터리 샤딩이 있고, 일관 해싱으로 리샤딩 비용을 줄인다. 단점: 조인·트랜잭션·재분배가 복잡.

## 10. SQL vs NoSQL 선택 기준은?

**답변:**
SQL은 강한 일관성·복잡한 조인·트랜잭션(ACID)·정형 스키마에. NoSQL은 유연 스키마·수평 확장·고쓰기 처리량(문서/키값/컬럼/그래프)에. 관계·트랜잭션 중심이면 SQL, 대규모·단순 접근 패턴·스키마 변화가 잦으면 NoSQL. 혼합(polyglot)도 흔하다.

## 11. 인덱스는 어떻게 성능을 높이나요?

**답변:**
B-tree 인덱스로 풀스캔 O(n) 대신 O(log n) 조회를 가능케 한다. 단 인덱스는 쓰기 시 갱신 비용·저장 공간을 더하므로 과다 생성은 해롭다. 복합 인덱스는 컬럼 순서가 중요(좌측 접두사 규칙), 카디널리티 높은 컬럼이 효과적.

## 12. CAP 정리란?

**답변:**
분산 시스템은 일관성(C)·가용성(A)·분할 내성(P) 중 **셋을 동시에 보장 못 한다**. 네트워크 분할(P)은 현실에서 불가피하므로, 분할 시 **C와 A 중 선택**하게 된다. CP(일관성 우선, 예: 일부 거부)·AP(가용성 우선, 예: 최종 일관성)로 갈린다.

## 13. 최종 일관성(eventual consistency)이란?

**답변:**
쓰기 후 모든 노드가 즉시는 아니지만 **언젠가 같은 값으로 수렴**하는 모델(AP 시스템). 가용성·확장성을 얻는 대신 일시적 불일치를 허용한다. SNS 좋아요 수처럼 약간 늦어도 되는 데이터에 적합. 강한 일관성이 필요한 결제엔 부적합.

## 14. 멱등성(idempotency)이 왜 중요한가요?

**답변:**
같은 요청을 여러 번 보내도 결과가 한 번과 같아야 재시도·중복 전송(네트워크 불안정)에서 안전하다. 결제·주문은 멱등 키(idempotency key)를 받아 중복 처리를 막는다. GET/PUT/DELETE는 본래 멱등, POST는 아니라 키로 보장한다.

## 15. 메시지 큐는 왜 쓰나요?

**답변:**
생산자와 소비자를 비동기로 분리(decoupling)해 트래픽 급증을 버퍼링(부하 평준화)하고, 소비자 장애 시에도 메시지를 보존하며, 작업을 백그라운드로 오프로드한다. 전달 보장(at-least-once 등)·순서·중복 처리(멱등)를 설계해야 한다.

## 16. 동기 vs 비동기 통신 선택은?

**답변:**
동기(요청-응답)는 즉시 결과가 필요하고 흐름이 단순할 때. 비동기(큐/이벤트)는 즉시 응답이 불필요하거나(이메일 발송), 느린 작업·피크 흡수·서비스 결합도를 낮출 때. 비동기는 복잡성(추적·일관성)을 늘리므로 필요할 때만.

## 17. 속도 제한(rate limiting) 구현은?

**답변:**
토큰 버킷(버스트 허용), 누출 버킷(일정 속도), 고정/슬라이딩 윈도우 카운터. 분산 환경은 Redis로 카운터를 공유한다. 남용·DDoS 완화, 공정한 자원 분배가 목적이며 `429 Too Many Requests`로 응답한다.

## 18. 단일 장애점(SPOF)을 어떻게 없애나요?

**답변:**
모든 계층을 다중화(이중화)한다: 다중 서버+로드밸런서, DB 복제+자동 페일오버, 다중 가용 영역(AZ)/리전, 로드밸런서 자체도 이중화. 헬스체크·자동 복구를 두고, 장애 주입 테스트(카오스 엔지니어링)로 검증한다.

## 19. 서킷 브레이커와 재시도 전략은?

**답변:**
서킷 브레이커는 의존 서비스 실패가 임계치를 넘으면 회로를 열어 빠르게 실패시키고(연쇄 장애·자원 고갈 방지), 일정 후 반열림으로 회복을 탐색한다. 재시도는 지수 백오프+지터로(동시 재시도 폭주 방지), 멱등 요청에만 안전하게 적용한다.

## 20. 고유 ID를 분산 환경에서 어떻게 생성하나요?

**답변:**
중앙 자동증가는 SPOF·병목. 대안: UUID(충돌 거의 없으나 정렬 불가·큼), **Snowflake**(타임스탬프+머신ID+시퀀스로 시간순 정렬 가능한 64비트), DB 티켓 서버(범위 할당). 정렬 가능성·크기·조정 비용으로 선택한다.

## 21. URL 단축기를 설계해보세요

**답변:**
- 핵심: 짧은 키 ↔ 원본 URL 매핑. 키 생성은 자동증가 ID를 base62 인코딩하거나 해시 후 충돌 처리.
- 저장: 읽기가 압도적으로 많음 → KV 스토어 + 캐시(인기 링크). 읽기 캐시 적중률이 성능 좌우.
- 확장: 무상태 API + 샤딩, 리다이렉트는 301(영구)/302(추적용). 분석(클릭 수)은 비동기 큐로.
- 고려: 키 충돌, 커스텀 별칭, 만료, 악성 URL 필터.

## 22. 뉴스 피드를 설계해보세요

**답변:**
- **Fan-out on write(push)**: 글 작성 시 팔로워 피드에 미리 뿌림 → 읽기 빠름, 유명인(팔로워 수백만)에 쓰기 폭증.
- **Fan-out on read(pull)**: 읽을 때 팔로잉들의 글을 모음 → 쓰기 가벼움, 읽기 느림.
- **하이브리드**: 일반 사용자는 push, 유명인은 pull로 혼합. 피드 캐싱+페이지네이션(커서), 랭킹은 비동기 점수화.
