## 1. 시맨틱 HTML이 접근성의 핵심인 이유는?

**답변:**
`<button>`, `<nav>`, `<main>` 같은 시맨틱 요소는 역할(role)·키보드 포커스·기본 동작(Enter/Space)·비활성화 지원을 **공짜로** 제공한다. `div`로 같은 걸 만들면 `tabindex`·`role`·키 핸들러를 일일이 붙여야 하고 빠뜨리기 쉽다. 접근성의 90%는 올바른 요소 선택에서 온다.

## 2. WCAG의 4대 원칙(POUR)과 목표 수준은?

**답변:**
Perceivable(인지)·Operable(운용)·Understandable(이해)·Robust(견고). 적합성은 A/AA/AAA 중 **AA가 실무·법적 기준선**이다(한국 장차법, 미국 ADA/508 모두 사실상 AA).

## 3. 접근 가능한 이름은 어떻게 정해지나요?

**답변:**
우선순위: `aria-labelledby` > `aria-label` > 내부 텍스트/`<label>`/`alt`/`title`. 아이콘만 있는 버튼처럼 보이는 텍스트가 없으면 `aria-label`이 필수다.

## 4. ARIA를 쓰면 키보드 동작도 생기나요?

**답변:**
아니다. ARIA는 접근성 트리의 역할·상태·이름 *표현*만 바꾼다. `role="button"`을 붙여도 포커스·Enter/Space 처리는 직접 구현해야 한다. 그래서 네이티브 요소가 거의 항상 낫다("No ARIA is better than bad ARIA").

## 5. `aria-live`의 polite/assertive 차이는?

**답변:**
polite는 사용자의 현재 읽기가 끝난 뒤 알림을 읽고, assertive(`role="alert"`)는 즉시 끊고 읽는다. 일반 상태 변화는 polite, 긴급 에러만 assertive. live region 컨테이너는 미리 존재해야 하고 내용만 갱신해야 감지된다.

## 6. 접근성 있는 모달의 조건은?

**답변:**
① 열 때 포커스를 모달 안으로, ② Tab을 모달에 가두는 포커스 트랩, ③ Esc로 닫기, ④ 닫을 때 연 요소로 포커스 복원. 네이티브 `<dialog>`의 `showModal()`이 ①②③+배경 inert를 기본 제공한다.

## 7. `:focus`를 지우면 안 되는 이유는?

**답변:**
키보드 사용자가 현재 위치를 알 수 없어 WCAG 2.4.7 위반이다. 디자인을 바꾸려면 `:focus-visible`로 키보드 탐색 시에만 커스텀 아웃라인을 보여준다.

## 8. 색 대비 AA 기준과 "색만으로 전달 금지"는?

**답변:**
본문 4.5:1, 큰 텍스트·UI 요소 3:1. 색은 보조 수단이라 오류·상태를 색만으로 표시하면 색맹 사용자가 인지 못 하므로 아이콘·텍스트를 병행한다.

## 9. 미디어 쿼리 vs 컨테이너 쿼리?

**답변:**
미디어 쿼리는 뷰포트(화면 전체)에, 컨테이너 쿼리는 요소가 놓인 부모 컨테이너 크기에 반응한다. 같은 컴포넌트가 사이드바·본문 등 다른 폭에 재사용될 때 진짜 재사용 가능한 반응형은 컨테이너 쿼리로만 가능하다.

## 10. `:has()`로 무엇이 가능해졌나요?

**답변:**
CSS에 없던 부모/관계 선택자. 특정 자식·형제를 가진 요소를 선택해 `label:has(input:checked)`, `form:has(:invalid) button` 같은 상태 기반 UI를 JS 없이 표현한다.

## 11. `@layer`(Cascade Layers)가 푸는 문제는?

**답변:**
명시도 전쟁. 레이어 간에는 선언 순서가 명시도보다 우선하므로, 서드파티 CSS를 앞 레이어에 두면 내 스타일이 명시도와 무관하게 항상 이긴다. 단 레이어 밖 규칙은 모든 레이어보다 강하고 `!important`는 레이어 순서가 역전된다.

## 12. subgrid가 필요한 상황은?

**답변:**
중첩 그리드의 자식들이 부모의 같은 행/열 트랙에 정렬돼야 할 때. 카드 그리드에서 카드별 제목·본문 높이를 맞추려면 `grid-template-rows: subgrid`로 부모 트랙을 상속한다.

## 13. CSS 명시도(specificity) 계산은?

**답변:**
(인라인, ID, 클래스/속성/의사클래스, 요소/의사요소) 순 가중치로 비교한다. 같은 명시도면 나중 선언이 이긴다. `!important`는 이를 무시(남용 금지), `@layer`·`:where()`(명시도 0)로 관리한다.

## 14. 논리 속성을 쓰는 이유는?

**답변:**
`margin-inline`·`padding-block`처럼 물리 방향 대신 흐름 방향으로 지정하면 RTL·세로쓰기에서 자동으로 방향이 뒤집혀 국제화에 강하다.

## 15. `try/catch`로 못 잡는 에러 수집법은?

**답변:**
전역 핸들러로 보완한다. 동기/리소스 에러는 `window.addEventListener('error')`, 처리 안 된 Promise 거부는 `'unhandledrejection'`, React 렌더 에러는 Error Boundary로 잡아 한곳으로 전송한다. 이탈 중 유실 방지엔 `navigator.sendBeacon`.

## 16. 소스맵이 필요한 이유와 운영 주의점은?

**답변:**
minify된 프로덕션 스택을 원본 파일·줄·함수로 복원하기 위해서다. 원본 노출을 막으려 공개 배포하지 말고 `hidden` 모드로 생성해 에러 추적 서비스에만 릴리스와 짝지어 업로드한다.

## 17. Core Web Vitals 3가지는?

**답변:**
LCP(최대 콘텐츠 페인트, 로딩 체감, ≤2.5s), INP(상호작용→다음 페인트, 반응성, ≤200ms, 2024년 FID 대체), CLS(누적 레이아웃 이동, 시각 안정성, ≤0.1). p75 분포로 평가한다.

## 18. 합성 모니터링과 RUM의 차이는?

**답변:**
합성(Lighthouse)은 통제된 환경에서 일관 측정해 CI 회귀 게이트에 좋고, RUM은 실제 사용자의 다양한 기기·네트워크에서 측정해 진짜 경험을 반영한다. 평균이 아니라 p75 분포로 봐야 느린 사용자를 놓치지 않는다.

## 19. 에러 그룹핑(fingerprinting)이 왜 중요한가요?

**답변:**
동일 원인 에러 수천 건을 하나의 이슈로 묶지 않으면 알림이 폭발해 신호가 묻힌다. 스택·메시지 기반으로 묶어 새로운/급증한 이슈에 집중하고, 릴리스 추적과 결합해 회귀를 일으킨 배포를 특정한다.

## 20. 클라이언트 수집 시 프라이버시·성능은?

**답변:**
PII(이메일·토큰)를 전송 전 스크러빙하고(GDPR/개인정보보호법), 트래픽이 크면 성능 트레이스를 샘플링하며, SDK는 비동기 로드·`sendBeacon` 배치 전송으로 메인 스레드를 막지 않게 한다.
