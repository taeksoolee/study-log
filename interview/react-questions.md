## 1. React의 렌더링은 언제 일어나나요?

**답변:**
① 자신의 상태(state) 변경, ② 부모 리렌더(props 동일해도 기본적으로 자식도 렌더), ③ Context 값 변경, ④ 강제 업데이트. "렌더"는 컴포넌트 함수를 호출해 VDOM을 만드는 단계이고, 실제 DOM 반영(커밋)은 변경분이 있을 때만 일어난다. 즉 **렌더 ≠ DOM 갱신**이다.

---

## 2. Virtual DOM과 Reconciliation, Fiber는?

**답변:**
VDOM은 UI의 가벼운 JS 객체 표현. 상태가 바뀌면 새 VDOM을 만들어 이전 것과 **diff(Reconciliation)** 해 바뀐 부분만 실제 DOM에 반영한다. **Fiber**는 이 작업을 작은 단위로 쪼개 **중단·재개·우선순위 부여**가 가능하게 한 재조정 엔진으로, 동시성 기능의 토대다.

---

## 3. `key`는 왜 중요하고 index를 쓰면 안 되나요?

**답변:**
key는 리스트 diff에서 항목의 **동일성**을 식별한다. 배열 인덱스를 key로 쓰면 중간 삽입·삭제·정렬 시 항목과 상태가 어긋나 잘못된 재사용/입력값 꼬임이 생긴다. 안정적인 고유 ID를 써야 한다.

---

## 4. 상태 업데이트는 왜 비동기처럼 보이나요? (배칭)

**답변:**
React는 한 이벤트 처리 동안의 여러 `setState`를 **배칭**해 한 번만 리렌더한다. 그래서 `setState` 직후 state를 읽으면 옛 값이다. React 18부터는 Promise/setTimeout 안에서도 자동 배칭된다(automatic batching).

---

## 5. 함수형 업데이트 `setState(prev => ...)`는 언제?

**답변:**
이전 상태에 기반해 갱신할 때. 배칭으로 여러 번 호출하거나 클로저가 옛 값을 캡처할 위험이 있을 때 `setCount(c => c + 1)`로 최신 값을 보장한다.

---

## 6. `useEffect`의 실행 시점과 클린업은?

**답변:**
브라우저가 **화면을 그린 후(비동기)** 실행된다. 의존성이 바뀌면 다음 이펙트 실행 전에 이전 클린업이 호출된다. DOM 측정처럼 페인트 전 동기 실행이 필요하면 `useLayoutEffect`를 쓴다(단 성능 주의).

---

## 7. `useEffect` 의존성 배열의 함정은?

**답변:**
의존성을 빠뜨리면 **stale closure**(옛 값 참조) 버그, 객체/함수를 그대로 넣으면 매 렌더 새 참조라 **무한 루프**. 함수는 `useCallback`, 값은 `useMemo`로 안정화하거나, 이펙트 안으로 옮기거나, 함수형 업데이트로 의존성을 줄인다.

---

## 8. `useMemo`와 `useCallback`은 언제 쓰나요?

**답변:**
`useMemo`는 비싼 계산 결과 캐시, `useCallback`은 함수 참조 안정화(메모된 자식/이펙트 의존성용). 둘 다 **공짜가 아니다**(비교·메모리 비용). 측정 없이 남발하면 오히려 손해 — 실제 병목이나 참조 안정성이 필요한 곳에만.

---

## 9. `useRef`의 두 가지 용도는?

**답변:**
① DOM 노드 참조, ② **리렌더를 유발하지 않는 가변 값** 저장(타이머 ID, 이전 값, 인스턴스 변수). `ref.current` 변경은 렌더를 트리거하지 않는다.

---

## 10. `useState` vs `useReducer` 선택 기준은?

**답변:**
독립적인 단순 상태는 `useState`. 여러 하위 값이 함께 바뀌거나 다음 상태가 이전 상태/액션에 복잡하게 의존하면 `useReducer`로 전이 로직을 한곳에 모은다(테스트·예측성↑).

---

## 11. Hooks 규칙이 존재하는 이유는?

**답변:**
React는 훅을 **호출 순서**로 식별한다(이름이 아니라 인덱스). 조건문/반복문 안에서 호출하면 순서가 흔들려 상태가 어긋난다. 그래서 "최상위에서만, React 함수 안에서만" 호출해야 한다.

---

## 12. 커스텀 훅은 상태를 공유하나요?

**답변:**
아니다. 커스텀 훅은 **로직**을 재사용할 뿐, 호출할 때마다 **독립된 상태**를 가진다. 상태 자체를 공유하려면 Context나 외부 스토어가 필요하다.

---

## 13. `React.memo`는 어떻게 동작하나요?

**답변:**
props를 **얕은 비교(shallow)**해 같으면 리렌더를 건너뛴다. 단 콜백/객체 props가 매번 새로 생성되면 무의미하므로 `useCallback`/`useMemo`와 짝지어야 효과가 난다. 자식이 가볍거나 자주 안 바뀌면 오히려 비교 비용만 든다.

---

## 14. Context가 리렌더를 유발하는 문제는?

**답변:**
Context 값이 바뀌면 **그 값을 구독하는 모든 소비자**가 리렌더된다. value에 객체 리터럴을 그대로 넣으면 매 렌더 새 참조라 전부 리렌더. 해결: value를 `useMemo`로 안정화, 자주 바뀌는 값/안 바뀌는 값으로 Context 분리, 또는 선택적 구독(zustand 등).

---

## 15. 리렌더 최적화 전략 정리

**답변:**
1. 상태를 **필요한 곳까지 내리기**(state colocation) → 영향 범위 축소.
2. `children`으로 컴포넌트를 **올려두기**(부모 렌더에 영향 안 받게).
3. `React.memo` + `useCallback`/`useMemo`로 메모화(측정 후).
4. 리스트 가상화, Context 분리, 파생 상태는 렌더 중 계산(불필요한 state 제거).

---

## 16. Concurrent 기능(useTransition, useDeferredValue)은?

**답변:**
긴급한 업데이트(입력)와 덜 긴급한 업데이트(무거운 목록 필터링)를 구분해, 후자를 **중단 가능한 전환(transition)**으로 처리한다. `useTransition`은 상태 갱신을 저우선으로 표시(`isPending` 제공), `useDeferredValue`는 값의 지연된 사본을 준다. 입력 반응성을 유지하면서 무거운 렌더를 미룬다.

---

## 17. `useSyncExternalStore`는 왜 생겼나요?

**답변:**
외부 스토어(Redux/Zustand 등)를 동시성 렌더링과 안전하게 구독하기 위해. 동시성 모드에서 발생할 수 있는 **tearing**(같은 렌더에서 서로 다른 스토어 값을 보는 현상)을 방지한다.

---

## 18. Strict Mode가 이펙트를 두 번 실행하는 이유는?

**답변:**
개발 모드에서 마운트→언마운트→재마운트를 모의 실행해 **클린업 누락 등 부수효과 버그를 조기에 드러내기** 위해서다. 프로덕션에선 한 번만 실행된다. 이펙트를 멱등하고 클린업을 제대로 짜라는 신호다.

---

## 19. 서버 컴포넌트(RSC)란 무엇인가요?

**답변:**
서버에서만 렌더되고 **JS 번들에 포함되지 않는** 컴포넌트. DB·파일에 직접 접근하고 결과를 직렬화해 보낸다. 클라이언트로 보내는 JS를 줄이고 데이터 접근을 단순화한다. 단 상태/이벤트/브라우저 API는 못 쓴다(그건 클라이언트 컴포넌트의 몫).

---

## 20. `'use client'`와 `'use server'`의 경계는?

**답변:**
`'use client'`는 그 파일부터 클라이언트 컴포넌트 경계(상호작용·훅 사용 가능). `'use server'`는 서버 액션(클라이언트에서 호출하는 서버 함수)을 표시. 기본은 서버 컴포넌트이고, 상호작용이 필요한 잎(leaf) 컴포넌트만 클라이언트로 내리는 게 권장 패턴이다.

---

## 21. Suspense와 데이터 페칭의 관계는?

**답변:**
Suspense는 자식이 "준비 안 됨"을 던지면 **폴백 UI**를 보여주는 선언적 로딩 경계다. 코드 스플리팅(`lazy`)과 RSC/프레임워크 데이터 로딩에 통합돼, 로딩 상태를 컴포넌트 트리 단위로 선언한다.

---

## 22. Error Boundary로 못 잡는 에러는?

**답변:**
이벤트 핸들러, 비동기 콜백(setTimeout/Promise), SSR, Error Boundary 자신의 에러는 못 잡는다. 렌더/라이프사이클 에러만 잡는다. 나머지는 try/catch와 전역 핸들러(`window.onerror`, `unhandledrejection`)로 보완한다.

---

## 23. 상태를 어디에 둘지(끌어올리기/공동화) 결정 기준은?

**답변:**
여러 컴포넌트가 공유하면 **가장 가까운 공통 조상으로 끌어올린다**(lifting state up). 반대로 한 곳에서만 쓰면 그 컴포넌트에 **공동 배치(colocation)**해 리렌더 범위를 좁힌다. 전역이 정말 필요할 때만 Context/스토어.

---

## 24. 제어/비제어 컴포넌트 차이는?

**답변:**
제어 컴포넌트는 값을 React state가 소유(`value`+`onChange`)해 실시간 검증·동기화가 쉽지만 리렌더가 잦다. 비제어는 DOM이 값을 소유(`ref`로 읽음)해 리렌더가 적고 큰 폼에 유리하다. react-hook-form은 비제어 기반으로 성능을 얻는다.

---

## 25. React 19의 주요 변화는?

**답변:**
액션(폼 `action`, `useActionState`, `useFormStatus`), `use()` 훅(Promise/Context 읽기), `ref`를 prop으로(별도 forwardRef 불필요화), 문서 메타/리소스 호이스팅, 향상된 서버 컴포넌트·서버 액션 통합. 전반적으로 비동기 처리와 폼을 1급으로 끌어올렸다.
