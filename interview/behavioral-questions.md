## STAR 기법이란

STAR 기법은 행동 면접(Behavioral Interview)에서 경험 기반 질문에 답변하기 위한 구조화된 프레임워크입니다.

| 요소 | 의미 | 설명 |
|------|------|------|
| **S** - Situation | 상황 | 어떤 맥락, 배경에서 일어난 일인가? |
| **T** - Task | 과제 | 내가 맡은 역할과 해결해야 할 문제는? |
| **A** - Action | 행동 | 문제 해결을 위해 구체적으로 무엇을 했나? |
| **R** - Result | 결과 | 행동의 결과는 무엇이었고 무엇을 배웠나? |

**비율 가이드:**
- Situation + Task: 20~30%
- Action: 50~60% (가장 중요, 구체적으로)
- Result: 20~30% (정량적 수치 포함 시 강력)

---

## 답변 구성 팁

1. **구체적 수치를 사용하세요**: "성능을 개선했다"보다 "API 응답 시간을 3초에서 0.8초로 73% 단축했다"가 훨씬 설득력 있습니다.

2. **"우리(We)"보다 "나(I)"에 집중하세요**: 팀 성과를 말하되, 내가 구체적으로 무엇을 했는지 명확히 밝혀야 합니다.

3. **부정적 결과도 솔직하게 말하되, 배운 점을 강조하세요**: 실패 경험 질문에서 실패를 인정하고 성장한 모습을 보여주는 것이 중요합니다.

4. **답변 길이는 1~3분을 목표로 하세요**: 너무 짧으면 피상적으로 보이고, 너무 길면 집중력을 잃습니다.

5. **미리 5~7개의 핵심 스토리를 준비하세요**: 한 스토리를 여러 질문에 각도를 달리하여 활용할 수 있습니다.

6. **Action의 "왜"를 설명하세요**: 무엇을 했는지뿐 아니라 왜 그 방법을 선택했는지를 설명하면 사고력을 보여줄 수 있습니다.

## 행동 면접 질문 20개

---

### Q1. 가장 어려웠던 기술적 문제와 해결 방법은?

**의도:** 문제 해결 능력, 기술적 깊이, 인내력 평가

**STAR 구조 예시:**

- **S**: 사용자가 급증하던 시점에 특정 API 엔드포인트에서 간헐적으로 타임아웃이 발생했습니다. 재현이 어렵고 에러 로그도 명확하지 않았습니다.
- **T**: 서비스 가용성을 유지하면서 원인을 파악하고 해결해야 했습니다.
- **A**: 먼저 APM 도구(Datadog)로 느린 쿼리를 추적했습니다. N+1 쿼리 문제를 발견했고, 추가로 해당 테이블의 인덱스가 없다는 사실도 확인했습니다. `EXPLAIN ANALYZE`로 실행 계획을 분석하고, 복합 인덱스를 추가하고 ORM의 `select_related`를 적용했습니다. 스테이징 환경에서 부하 테스트로 검증 후 배포했습니다.
- **R**: 응답 시간이 평균 4.2초에서 0.3초로 단축되었고, 타임아웃이 완전히 해소되었습니다. 이후 팀에 쿼리 분석 가이드를 공유했습니다.

**핵심 포인트:** 단계적 원인 추적 과정과 검증 절차를 구체적으로 서술하세요.

---

### Q2. 팀원과 갈등이 있었을 때 어떻게 해결했나요?

**의도:** 대인 관계 능력, 갈등 해결 방식, 협업 태도 평가

**STAR 구조 예시:**

- **S**: 코드 리뷰에서 동료가 제안한 설계 방식에 동의할 수 없었습니다. 성능 면에서 제 방식이 더 낫다고 판단했지만, 동료는 가독성을 강조했습니다.
- **T**: 기술적 결론을 내리면서도 관계를 건강하게 유지해야 했습니다.
- **A**: 즉각적인 반박보다는 "의도를 이해하고 싶다"는 자세로 동료의 관점을 먼저 들었습니다. 이후 두 방식의 트레이드오프를 벤치마크 데이터와 함께 정리하여 팀 전체에 공유했고, 팀 회의에서 논의하자고 제안했습니다. 결국 성능이 중요한 경로에는 제 방식을, 나머지에는 동료의 방식을 사용하기로 합의했습니다.
- **R**: 기술적으로 균형 잡힌 결정을 내릴 수 있었고, 동료와 신뢰 관계도 오히려 강화되었습니다.

**핵심 포인트:** 자신이 옳았음을 강조하기보다 합의 과정과 상호 존중을 강조하세요.

---

### Q3. 촉박한 마감 기한에서 어떻게 작업했나요?

**의도:** 우선순위 결정 능력, 압박 상황에서의 판단력, 시간 관리 평가

**STAR 구조 예시:**

- **S**: 런칭 일정이 2주 앞당겨졌고, 기존에 계획된 기능 중 일부를 제거하거나 범위를 줄여야 하는 상황이었습니다.
- **T**: 핵심 기능을 정시에 안정적으로 출시해야 했습니다.
- **A**: 기능 목록을 Must-Have, Nice-to-Have, Later로 분류했습니다. 팀 내부 합의와 PM과의 협의를 통해 스코프를 조정했고, 남은 기능에 집중했습니다. 일일 스탠드업을 짧게 늘려 블로커를 빠르게 공유했습니다. 야근보다 집중 근무(Deep Work 블록)를 지정해 효율성을 높였습니다.
- **R**: 핵심 기능 100%를 예정일에 출시했고, 후순위 기능은 다음 스프린트에서 완성했습니다. 이 경험 이후 팀의 스코프 관리 프로세스를 정비했습니다.

**핵심 포인트:** 무조건 열심히 했다는 서술보다 어떻게 판단하고 우선순위를 정했는지를 강조하세요.

---

### Q4. 새로운 기술을 빠르게 배운 경험은?

**의도:** 학습 능력, 자기주도성, 적응력 평가

**STAR 구조 예시:**

- **S**: 프로젝트에서 Kubernetes 기반 배포 환경으로 전환이 결정되었고, 팀 내에 Kubernetes 경험자가 없었습니다.
- **T**: 2주 안에 기본 배포 파이프라인을 구축해야 했습니다.
- **A**: 공식 문서와 CNCF 자료를 우선 학습했고, 사이드 환경에서 직접 클러스터를 구성하며 실습했습니다. 막히는 부분은 팀원들과 공유하며 함께 해결했고, 학습 내용을 위키에 정리하여 팀 전체의 온보딩을 도왔습니다.
- **R**: 예정보다 3일 일찍 스테이징 환경 배포에 성공했습니다. 작성한 위키 문서는 이후 신규 팀원 온보딩에도 활용되었습니다.

**핵심 포인트:** 단순한 "열심히 공부했다"보다 어떤 방법론으로 학습했는지를 구체적으로 설명하세요.

---

### Q5. 실패한 프로젝트 경험과 배운 점은?

**의도:** 자기 인식, 성장 마인드셋, 책임감 평가

**STAR 구조 예시:**

- **S**: 사이드 프로젝트로 독서 기록 앱을 출시했지만 3개월 후 DAU가 10명 이하로 유지되지 못하고 서비스를 종료했습니다.
- **T**: 출시 후 사용자 유지율을 높이는 것이 목표였습니다.
- **A**: 기능 개발에는 집중했지만 사용자 인터뷰나 실제 페인포인트 검증 없이 내가 원하는 기능을 만들었습니다. 온보딩 경험도 복잡해서 신규 사용자의 이탈이 높았습니다.
- **R**: 서비스는 실패했지만, 사용자 검증 없는 개발의 한계를 체험했습니다. 이후 프로젝트에서는 반드시 초기에 사용자 인터뷰를 진행하고, MVP부터 시작하는 방식으로 접근을 바꿨습니다.

**핵심 포인트:** 실패를 회피하거나 외부 탓으로 돌리지 마세요. 자신의 역할과 인사이트에 집중하세요.

---

### Q6. 다른 팀원의 코드 품질 문제를 어떻게 처리했나요?

**의도:** 동료에 대한 피드백 방식, 팀 문화 기여도, 소통 능력 평가

**STAR 구조 예시:**

- **S**: 코드 리뷰 중 동료가 반복적으로 에러 핸들링 없이 코드를 제출하는 패턴을 발견했습니다.
- **T**: 팀 전체의 코드 품질을 유지하면서 동료의 감정을 고려한 방식으로 피드백을 전달해야 했습니다.
- **A**: 리뷰 코멘트로 지적하기보다 먼저 1:1로 얘기를 나눴습니다. 상황을 이해하니 해당 동료가 에러 핸들링 패턴에 대한 경험이 부족했던 것이었습니다. 팀 전체를 대상으로 에러 핸들링 패턴에 관한 짧은 세션을 진행했고, ESLint 규칙에도 추가했습니다.
- **R**: 이후 에러 핸들링 관련 리뷰 코멘트가 80% 줄었고, 팀 전반의 코드 품질이 향상되었습니다.

**핵심 포인트:** 비난이 아닌 교육과 시스템 개선으로 접근했다는 점을 보여주세요.

---

### Q7. 요구사항이 모호할 때 어떻게 했나요?

**의도:** 커뮤니케이션 능력, 주도성, 불확실성 처리 방식 평가

**STAR 구조 예시:**

- **S**: PM으로부터 "사용자 경험을 개선해주세요"라는 요청을 받았지만 구체적인 기준이나 범위가 없었습니다.
- **T**: 명확한 구현 목표를 정의하고 작업을 시작해야 했습니다.
- **A**: 먼저 PM에게 질문 목록을 정리하여 공유했습니다. "어떤 사용자 행동을 개선 대상으로 보시나요?", "성공 지표는 무엇인가요?", "우선순위가 가장 높은 화면은 어디인가요?" 등을 물었습니다. 답변을 토대로 요구사항 문서를 직접 작성하여 PM에게 리뷰를 요청했고, 확인 후 작업을 시작했습니다.
- **R**: 작업 완료 후 의도와 다른 결과물이 나오는 일이 없었고, 이 방식을 팀 내 표준으로 채택하게 되었습니다.

**핵심 포인트:** 모호함을 받아들이고 추측으로 진행하지 않고, 능동적으로 명확화한 행동이 핵심입니다.

---

### Q8. 성능 문제를 발견하고 해결한 경험은?

**의도:** 문제 감지 능력, 기술적 실행력, 사용자 영향 인식 평가

**STAR 구조 예시:**

- **S**: 모니터링 대시보드에서 특정 시간대에 서버 CPU 사용률이 90%를 넘는 현상을 발견했습니다.
- **T**: 서비스 장애로 이어지기 전에 원인을 파악하고 해결해야 했습니다.
- **A**: 프로파일링 도구로 병목을 분석했더니, 정렬 로직이 매 요청마다 전체 데이터셋을 메모리에 올리는 방식이었습니다. 데이터가 늘어남에 따라 O(n log n)이 점점 비싸지고 있었습니다. 사전 계산된 집계 데이터를 Redis에 캐싱하는 방식으로 전환했고, 데이터 갱신 시에만 캐시를 무효화하도록 처리했습니다.
- **R**: CPU 피크 사용률이 90% → 15%로 감소했고, 응답 시간도 2.1초 → 0.2초로 개선되었습니다.

**핵심 포인트:** 직관이 아닌 데이터와 도구로 원인을 파악했다는 점을 보여주세요.

---

### Q9. 레거시 코드를 개선한 경험은?

**의도:** 코드 품질 감각, 리팩토링 접근 방식, 안전한 변경 능력 평가

**STAR 구조 예시:**

- **S**: 5년 된 결제 모듈에 기능을 추가해야 했는데, 테스트 코드가 전혀 없고 비즈니스 로직이 뷰 레이어에 혼재되어 있었습니다.
- **T**: 기존 동작을 유지하면서 기능을 안전하게 추가해야 했습니다.
- **A**: 먼저 기존 동작을 문서화하고, 코드 변경 전에 통합 테스트를 먼저 작성했습니다("테스트로 잠금" 전략). 이후 기능별로 작은 단위로 분리하고 단위 테스트를 추가하면서 점진적으로 리팩토링했습니다. 한 번에 전면 교체하는 빅뱅 방식은 피했습니다.
- **R**: 신규 기능을 안전하게 추가했고, 결제 모듈의 테스트 커버리지가 0% → 72%로 올랐습니다. 이후 해당 모듈의 버그 발생이 눈에 띄게 감소했습니다.

**핵심 포인트:** 점진적 접근과 테스트 확보를 먼저 한 판단 과정을 부각하세요.

---

### Q10. 코드 리뷰에서 비판을 받았을 때 어떻게 했나요?

**의도:** 피드백 수용 능력, 겸손함, 성장 지향성 평가

**STAR 구조 예시:**

- **S**: 자신 있게 제출한 PR에서 시니어 개발자로부터 "이 설계는 확장성이 부족하다"는 피드백을 받았습니다. 처음에는 방어적인 감정이 들었습니다.
- **T**: 피드백을 올바르게 받아들이고 코드를 개선해야 했습니다.
- **A**: 즉각 반박하지 않고, 시니어 개발자에게 구체적으로 어떤 시나리오를 우려하는지 먼저 물었습니다. 설명을 듣고 나니 제가 고려하지 못한 케이스가 있다는 것을 인정했습니다. 해당 피드백을 반영하여 설계를 수정했고, 변경 사항과 이유를 PR 설명에 추가했습니다.
- **R**: 코드 품질이 실질적으로 개선되었고, 이후 같은 실수를 반복하지 않았습니다. 리뷰어와의 신뢰도 높아졌습니다.

**핵심 포인트:** 감정적 반응이 아닌 성장으로 이어진 과정을 보여주세요.

---

### Q11. 혼자 결정해야 하는 상황에서 어떻게 했나요?

**의도:** 자율성, 의사결정 능력, 책임감 평가

**STAR 구조 예시:**

- **S**: 야간 배포 중 예상치 못한 에러가 발생했고, 팀장은 연락이 닿지 않는 상황이었습니다.
- **T**: 롤백 여부를 혼자 결정해야 했습니다.

**핵심 포인트:** 임의로 결정한 게 아니라, 기준에 따라 판단했음을 보여주세요.
