## 1. JOIN 종류와 차이는?

**답변:**
INNER(양쪽 일치만), LEFT(왼쪽 전부+오른쪽 일치, 없으면 NULL), RIGHT(반대), FULL OUTER(양쪽 전부), CROSS(곱집합). 가장 흔한 건 INNER·LEFT. "한쪽 기준 다 보여주되 매칭 없으면 NULL"이 LEFT JOIN.

## 2. `WHERE`와 `HAVING`의 차이는?

**답변:**
WHERE는 **집계 전** 개별 행을 필터링, HAVING은 **집계 후** 그룹을 필터링한다. `GROUP BY` 결과(예: `COUNT(*) > 5`)에 조건을 걸 땐 HAVING. WHERE에서 집계 함수는 못 쓴다.

## 3. `GROUP BY`와 집계 함수는?

**답변:**
GROUP BY는 지정 컬럼이 같은 행을 묶고, 각 그룹에 COUNT/SUM/AVG/MAX/MIN을 적용한다. SELECT의 비집계 컬럼은 GROUP BY에 있어야 한다(표준). "카테고리별 매출 합" 같은 요약에 쓴다.

## 4. 서브쿼리와 JOIN 중 무엇을 쓰나요?

**답변:**
대개 JOIN이 옵티마이저 최적화·가독성에서 유리하다. 상관 서브쿼리(각 행마다 실행)는 느릴 수 있다. 단 `EXISTS`/`IN` 서브쿼리가 더 명확하거나 빠른 경우도 있어, 실행 계획으로 확인한다.

## 5. 윈도우 함수란?

**답변:**
행을 그룹으로 묶지 않고(행을 유지한 채) 집계·순위를 계산한다. `ROW_NUMBER()`, `RANK()`, `LAG/LEAD`, 이동 평균(`SUM() OVER(...)`). 예: 카테고리별 순위.

```sql
SELECT name, category,
       RANK() OVER (PARTITION BY category ORDER BY sales DESC) AS rnk
FROM products;
```

## 6. `UNION`과 `UNION ALL` 차이는?

**답변:**
UNION은 두 결과를 합치며 **중복 제거**(정렬·해싱 비용), UNION ALL은 중복 제거 없이 그냥 합친다(빠름). 중복이 없거나 상관없으면 UNION ALL이 성능상 낫다.

## 7. `NULL`을 다룰 때 주의점은?

**답변:**
NULL은 "값 없음"이라 `= NULL`이 아니라 `IS NULL`로 비교한다. `NULL`과의 산술/비교는 NULL(=거짓 취급)이 되고, 집계 함수는 NULL을 무시한다(COUNT(col)은 NULL 제외). `COALESCE`로 기본값 대체.

## 8. 인덱스는 어떻게 동작하나요?

**답변:**
보통 B+tree로 컬럼 값을 정렬 저장해 풀스캔 O(n) 대신 O(log n) 조회와 범위 검색을 가능케 한다. 대신 **쓰기 시 인덱스 갱신 비용·저장 공간**이 들어 과다 생성은 INSERT/UPDATE를 느리게 한다.

## 9. 복합 인덱스의 컬럼 순서가 왜 중요한가요?

**답변:**
복합 인덱스 `(a, b, c)`는 **좌측 접두사**(a, a+b, a+b+c) 순으로만 효율적이다. `b`만으로 조회하면 인덱스를 제대로 못 탄다. 자주 쓰는 조건·카디널리티 높은 컬럼을 앞에 둔다.

## 10. 인덱스를 타지 못하는 경우는?

**답변:**
컬럼에 함수/연산 적용(`WHERE YEAR(date)=2024`), 앞에 와일드카드(`LIKE '%x'`), 타입 불일치 암묵 변환, 부정 조건(`!=`, `NOT IN`), 낮은 카디널리티(대부분 같은 값), OR로 묶인 비인덱스 컬럼. 함수는 컬럼이 아닌 값에 적용하도록 쿼리를 재작성한다.

## 11. 실행 계획(EXPLAIN)은 무엇을 보나요?

**답변:**
옵티마이저가 쿼리를 어떻게 실행할지 — 인덱스 사용 여부, 스캔 타입(풀스캔/인덱스 스캔/seek), 조인 순서·방식, 예상 행 수·비용. 풀 테이블 스캔·예상 행 폭증·인덱스 미사용이 튜닝 신호다.

## 12. 커버링 인덱스란?

**답변:**
쿼리가 필요로 하는 컬럼을 인덱스가 모두 포함해, **테이블 본체를 안 읽고 인덱스만으로** 답하는 것. 추가 디스크 접근(랜덤 I/O)을 없애 매우 빠르다. SELECT 컬럼까지 인덱스에 포함시키면 된다.

## 13. N+1 쿼리 문제란?

**답변:**
목록 1번 조회 후 각 항목의 연관 데이터를 N번 추가 조회하는 것(ORM에서 흔함). 총 N+1번 쿼리로 성능이 급락. 해결: JOIN이나 `IN`으로 한 번에 가져오기(eager loading), ORM의 배치/include.

## 14. ACID란?

**답변:**
Atomicity(원자성: 전부 or 전무), Consistency(일관성: 제약 유지), Isolation(격리성: 동시 트랜잭션 간섭 차단), Durability(지속성: 커밋되면 영구). 트랜잭션이 신뢰성 있게 동작하기 위한 4속성.

## 15. 트랜잭션 격리 수준 4가지는?

**답변:**
READ UNCOMMITTED(더티 리드 허용) < READ COMMITTED(커밋된 것만, 반복 불가능 읽기 가능) < REPEATABLE READ(반복 읽기 보장, 팬텀 가능) < SERIALIZABLE(완전 직렬화, 가장 엄격·느림). 높을수록 일관성↑·동시성↓. 격리 수준이 막는 이상 현상(더티/논리피터블/팬텀)을 함께 안다.

## 16. 낙관적 락 vs 비관적 락은?

**답변:**
비관적 락은 읽을 때부터 잠가 충돌을 막음(`SELECT ... FOR UPDATE`) — 충돌 잦을 때. 낙관적 락은 잠그지 않고 **버전 컬럼**으로 커밋 시 충돌을 감지해 재시도 — 충돌 드물 때(동시성↑). 웹은 보통 낙관적 락.

## 17. 데드락은 왜 생기고 어떻게 푸나요?

**답변:**
두 트랜잭션이 서로가 가진 락을 기다리며 순환 대기할 때 발생. DB가 감지해 한쪽을 롤백한다. 예방: 락 획득 순서를 일관되게, 트랜잭션을 짧게, 격리 수준 낮추기, 인덱스로 락 범위 축소.

## 18. 정규화와 반정규화는?

**답변:**
정규화는 중복을 제거해 이상 현상을 막고 무결성을 높임(1NF~3NF). 반정규화는 의도적으로 중복을 허용해 조인을 줄이고 **읽기 성능**을 높임. 쓰기 무결성 vs 읽기 속도의 트레이드오프로, 읽기 많은 시스템은 반정규화·캐시를 곁들인다.

## 19. 기본 키와 외래 키는?

**답변:**
기본 키(PK)는 행을 유일 식별(NULL 불가, 보통 클러스터드 인덱스). 외래 키(FK)는 다른 테이블 PK를 참조해 **참조 무결성**을 보장(존재하지 않는 부모 참조 금지, 연쇄 삭제 등). 관계를 표현한다.

## 20. 페이지네이션을 효율적으로 하려면?

**답변:**
`OFFSET N`은 N개를 건너뛰며 읽어 깊은 페이지에서 느리다. **키셋(cursor) 페이지네이션**(`WHERE id > 마지막id ORDER BY id LIMIT n`)이 인덱스를 타 일정하게 빠르고, 데이터 변동에도 안정적이다.

## 21. SQL 인젝션은 어떻게 막나요?

**답변:**
사용자 입력을 쿼리 문자열에 직접 붙이지 말고 **파라미터화 쿼리(prepared statement)**를 쓴다. ORM의 바인딩, 입력 검증·최소 권한 계정, 에러 메시지 노출 최소화를 병행한다. 문자열 이스케이프만으론 불충분.

## 22. 느린 쿼리를 어떻게 튜닝하나요?

**답변:**
① EXPLAIN으로 병목(풀스캔·미사용 인덱스) 확인 → ② 적절한 인덱스 추가(WHERE/JOIN/ORDER BY 컬럼) → ③ 필요한 컬럼만 SELECT(커버링 인덱스) → ④ N+1 제거·조인 최적화 → ⑤ 쿼리 재작성(함수 제거, 키셋 페이지네이션) → ⑥ 그래도 느리면 캐싱·반정규화·읽기 복제본.
