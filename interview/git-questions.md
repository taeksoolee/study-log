## 1. Git의 3가지 영역(작업/스테이징/저장소)은?

**답변:**
Working Directory(작업 중 파일) → Staging Area(인덱스, 커밋할 변경 선별) → Repository(`.git`, 커밋 영구 저장). `git add`로 작업→스테이징, `git commit`으로 스테이징→저장소. 스테이징이 있어 변경을 선택적으로 커밋할 수 있다.

## 2. `git merge`와 `git rebase`의 차이는?

**답변:**
merge는 두 브랜치를 병합 커밋으로 합쳐 **이력을 그대로 보존**(분기가 보임). rebase는 내 커밋을 대상 브랜치 끝으로 **재적용해 선형 이력**을 만든다(병합 커밋 없음, 깔끔). rebase는 커밋 해시가 바뀐다.

## 3. rebase의 황금 규칙은?

**답변:**
**공유된(푸시된) 브랜치는 rebase하지 마라.** rebase는 이력을 새로 쓰므로(해시 변경), 남이 그 커밋을 기반으로 작업 중이면 이력이 갈라져 충돌·혼란이 생긴다. 로컬 전용 브랜치 정리에만 쓴다.

## 4. `reset`의 soft/mixed/hard 차이는?

**답변:**
모두 HEAD를 이동시키되 영향 범위가 다르다: `--soft`는 HEAD만(스테이징·작업 보존), `--mixed`(기본)는 HEAD+스테이징 초기화(작업 보존), `--hard`는 HEAD+스테이징+작업까지 모두 되돌림(변경 소실, 위험).

## 5. `reset`과 `revert`의 차이는?

**답변:**
`reset`은 이력을 과거로 되돌려 커밋을 **지운다**(공유 이력엔 위험). `revert`는 해당 변경을 취소하는 **새 커밋을 추가**해 이력을 보존한다. 이미 푸시된 커밋을 되돌릴 땐 안전한 `revert`를 쓴다.

## 6. `fetch`와 `pull`의 차이는?

**답변:**
`fetch`는 원격 변경을 가져오기만 하고 로컬 브랜치엔 병합 안 함(검토 가능). `pull`은 `fetch` + `merge`(또는 `--rebase`)를 한 번에. pull은 즉시 합쳐 편하지만 예기치 않은 병합/충돌이 생길 수 있어, 신중하면 fetch 후 확인한다.

## 7. `cherry-pick`은 언제 쓰나요?

**답변:**
다른 브랜치의 **특정 커밋 하나(또는 몇 개)만** 골라 현재 브랜치에 적용한다. 핫픽스를 여러 브랜치에 반영하거나, 잘못된 브랜치에 한 커밋을 옮길 때. 새 해시로 복제되며 남용하면 중복 커밋이 생긴다.

## 8. Fast-forward 머지와 `--no-ff`는?

**답변:**
대상 브랜치에 새 커밋이 없으면 Git은 포인터만 앞으로 옮긴다(fast-forward, 병합 커밋 없음). `--no-ff`는 항상 병합 커밋을 만들어 **기능 브랜치의 존재를 이력에 남긴다**(언제 어떤 기능이 합쳐졌는지 추적).

## 9. `stash`는 무엇인가요?

**답변:**
작업 중인 변경을 커밋하지 않고 임시 보관해 작업 트리를 깨끗하게 만든다. 급한 브랜치 전환 시 유용. `git stash` → `git stash pop`(되살리기). 여러 개 스택처럼 쌓을 수 있다.

## 10. `HEAD`, 브랜치, detached HEAD는?

**답변:**
HEAD는 "현재 위치" 포인터로 보통 브랜치를 가리킨다. 브랜치는 커밋을 가리키는 이동하는 포인터. 특정 커밋을 직접 체크아웃하면 브랜치가 아닌 커밋을 가리키는 **detached HEAD** 상태가 되어, 여기서 한 커밋은 브랜치를 안 만들면 유실될 수 있다.

## 11. 충돌(conflict)은 왜 나고 어떻게 푸나요?

**답변:**
같은 파일의 같은 영역을 양쪽이 다르게 바꾸면 Git이 자동 병합을 못 해 충돌 마커(`<<<<<<<`)를 남긴다. 해당 부분을 수동으로 정리하고 `git add` 후 커밋(merge) 또는 `git rebase --continue`로 마무리한다.

## 12. squash는 언제 하나요?

**답변:**
여러 자잘한 커밋(WIP, 오타 수정)을 하나의 의미 있는 커밋으로 합쳐 이력을 깔끔하게 한다. PR 머지 시 squash merge로 기능 단위 한 커밋만 남기는 전략이 흔하다(대신 세부 이력은 사라짐).

## 13. `.gitignore`에 이미 추적 중인 파일은?

**답변:**
`.gitignore`는 **추적되지 않은** 파일에만 적용된다. 이미 추적 중이면 무시되지 않으므로 `git rm --cached <file>`로 추적에서 제거한 뒤 커밋해야 한다(로컬 파일은 유지).

## 14. 실수로 한 커밋/푸시를 어떻게 되돌리나요?

**답변:**
- 로컬 미푸시: `git reset --soft HEAD~1`(커밋만 취소, 변경 보존) 또는 `--amend`.
- 이미 푸시됨(공유): `git revert <commit>`로 취소 커밋을 푸시(이력 보존, 안전). force push로 이력 갈아엎기는 협업 중엔 피한다.

## 15. `reflog`는 무엇인가요?

**답변:**
HEAD가 이동한 **모든 이력**(리셋·체크아웃·리베이스 포함)을 기록한다. 실수로 reset/rebase로 잃은 커밋도 `git reflog`로 해시를 찾아 복구할 수 있다. "Git의 안전망."

## 16. 대표적인 브랜치 전략은?

**답변:**
- **Git Flow**: main/develop/feature/release/hotfix — 릴리스 주기가 명확한 제품에. 복잡.
- **GitHub Flow**: main + 짧은 기능 브랜치 + PR + 지속 배포 — 단순, 웹 서비스에 인기.
- **Trunk-based**: 짧게 사는 브랜치를 자주 main에 통합 — CI/CD·기능 플래그와 결합.

## 17. `git commit --amend`는?

**답변:**
직전 커밋을 수정한다(메시지 변경 또는 빠뜨린 파일 추가). 새 커밋으로 **대체**되어 해시가 바뀌므로, 이미 푸시한 커밋엔 쓰지 않는다(공유 이력 변경).

## 18. 좋은 커밋 메시지란?

**답변:**
제목은 명령형·50자 내로 "무엇을 왜"(예: `fix: 로그인 시 토큰 만료 처리`), 본문에 이유·맥락. 한 커밋은 하나의 논리적 변경(원자적)이어야 리뷰·되돌리기·이력 추적이 쉽다. Conventional Commits 규약이 흔하다.
