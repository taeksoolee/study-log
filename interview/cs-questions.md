## 네트워크

### Q1. OSI 7계층을 설명해주세요

**A.**
OSI(Open Systems Interconnection) 7계층은 네트워크 통신을 7단계로 추상화한 참조 모델입니다.

| 계층 | 이름 | 역할 | 프로토콜/장비 |
|------|------|------|----------------|
| 7 | 응용 계층 | 사용자와 직접 상호작용 | HTTP, FTP, SMTP |
| 6 | 표현 계층 | 데이터 형식 변환, 암호화 | SSL, TLS |
| 5 | 세션 계층 | 세션 수립·유지·종료 | NetBIOS |
| 4 | 전송 계층 | 종단 간 신뢰성 있는 전송 | TCP, UDP |
| 3 | 네트워크 계층 | 라우팅, 논리 주소 지정 | IP, 라우터 |
| 2 | 데이터링크 계층 | 프레임 전송, 오류 감지 | MAC, 스위치 |
| 1 | 물리 계층 | 비트 신호 전송 | 케이블, 허브 |

실제 구현에서는 TCP/IP 4계층 모델(응용, 전송, 인터넷, 네트워크 인터페이스)을 주로 사용합니다.

### Q2. TCP와 UDP의 차이는?

**A.**

| 특성 | TCP | UDP |
|------|-----|-----|
| 연결 방식 | 연결 지향 (3-way handshake) | 비연결 지향 |
| 신뢰성 | 데이터 순서 보장, 손실 재전송 | 보장 없음 |
| 속도 | 상대적으로 느림 | 빠름 |
| 흐름 제어 | 있음 | 없음 |
| 사용 예 | HTTP, FTP, 이메일 | 스트리밍, DNS, 게임 |

TCP는 데이터 무결성이 중요한 경우(파일 전송, 웹 요청)에 사용하고, UDP는 실시간성이 더 중요한 경우(영상 통화, 게임)에 사용합니다.

### Q3. TCP 3-way handshake를 설명해주세요

**A.**
TCP 연결 수립 과정입니다.

```
클라이언트                  서버
    |   --- SYN (seq=x) --->  |   1단계: 클라이언트가 연결 요청
    |   <-- SYN+ACK --------  |   2단계: 서버가 수락 및 자신의 SYN 전송
    |       (seq=y, ack=x+1)  |
    |   --- ACK (ack=y+1) --> |   3단계: 클라이언트가 확인
    |                         |
    |     연결 수립 완료       |
```

- **1단계 SYN**: 클라이언트가 서버에 연결 의사 전달 (SYN 플래그, 초기 시퀀스 번호 전송)
- **2단계 SYN-ACK**: 서버가 SYN 수신 확인(ACK)과 동시에 자신의 SYN 전송
- **3단계 ACK**: 클라이언트가 서버의 SYN에 대한 확인 응답

연결 해제는 4-way handshake(FIN, ACK, FIN, ACK)로 진행됩니다.

### Q4. HTTP와 HTTPS의 차이는?

**A.**
HTTP(HyperText Transfer Protocol)는 웹 통신의 기본 프로토콜이며, HTTPS는 HTTP에 SSL/TLS 암호화를 추가한 버전입니다.

**주요 차이점:**
- **암호화**: HTTP는 평문 전송, HTTPS는 TLS로 암호화
- **포트**: HTTP는 80번, HTTPS는 443번
- **인증서**: HTTPS는 CA(인증 기관)에서 발급한 SSL/TLS 인증서 필요
- **SEO**: 구글은 HTTPS 사이트를 검색 순위에 우대

**HTTPS 동작 과정:**
1. 클라이언트가 서버에 연결 요청 (ClientHello)
2. 서버가 인증서 전송 (ServerHello + Certificate)
3. 클라이언트가 인증서 검증 후 대칭키 교환
4. 이후 대칭키로 암호화 통신

### Q5. DNS 조회 과정을 설명해주세요

**A.**
DNS(Domain Name System)는 도메인 이름을 IP 주소로 변환하는 시스템입니다.

**조회 순서:**
1. 브라우저 캐시 확인
2. OS 캐시 및 hosts 파일 확인
3. **로컬 DNS 리졸버(ISP)** 에 질의
4. 캐시 없으면 **루트 네임서버**에 질의 → `.com` TLD 서버 주소 반환
5. **TLD 네임서버**에 질의 → `example.com` 권한 서버 주소 반환
6. **권한 있는 네임서버**에 질의 → 최종 IP 주소 반환
7. IP 주소를 캐시에 저장 후 브라우저에 전달

**재귀적 조회 vs 반복적 조회:**
- 재귀적: 리졸버가 최종 답을 대신 찾아줌 (클라이언트 입장)
- 반복적: 각 서버가 다음 서버 주소만 알려줌 (리졸버-서버 간)

### Q6. CDN이란 무엇인가요?

**A.**
CDN(Content Delivery Network)은 전 세계 여러 지점에 서버(엣지 서버)를 분산 배치하여 사용자에게 가까운 서버에서 콘텐츠를 제공하는 기술입니다.

**주요 이점:**
- **지연 시간 감소**: 지리적으로 가까운 서버에서 응답
- **원본 서버 부하 감소**: 정적 콘텐츠를 캐싱하여 원본 트래픽 절감
- **가용성 향상**: 특정 서버 장애 시 다른 서버로 대체
- **DDoS 방어**: 트래픽을 여러 서버로 분산

**동작 원리:**
사용자 요청 → DNS가 가장 가까운 엣지 서버 IP 반환 → 엣지 서버 캐시에 있으면 즉시 응답, 없으면 원본 서버에서 가져와 캐싱 후 응답

대표 서비스: Cloudflare, AWS CloudFront, Akamai

### Q7. 로드 밸런서란 무엇인가요?

**A.**
로드 밸런서(Load Balancer)는 여러 서버에 네트워크 트래픽을 균등하게 분산시키는 장치 또는 소프트웨어입니다.

**주요 알고리즘:**
- **라운드 로빈**: 순서대로 서버에 분배
- **최소 연결**: 현재 연결이 가장 적은 서버에 분배
- **IP 해시**: 클라이언트 IP 기반으로 항상 같은 서버에 분배 (세션 유지)
- **가중 라운드 로빈**: 서버 성능에 따라 가중치 부여

**L4 vs L7 로드 밸런서:**
- L4: 전송 계층(TCP/UDP) 기반, IP와 포트로만 분배
- L7: 응용 계층(HTTP) 기반, URL, 헤더, 쿠키 등으로 분배 가능

**장점:** 가용성 향상, 수평 확장 가능, 서버 장애 감지 및 제거

### Q8. WebSocket과 HTTP의 차이는?

**A.**

| 특성 | HTTP | WebSocket |
|------|------|-----------|
| 연결 방식 | 요청-응답 후 연결 종료 | 연결 유지 (Full-Duplex) |
| 통신 방향 | 단방향 (클라이언트 → 서버) | 양방향 |
| 오버헤드 | 매 요청마다 헤더 전송 | 최초 핸드셰이크 이후 최소 헤더 |
| 사용 예 | 웹 페이지 요청 | 실시간 채팅, 알림 |

**WebSocket 연결 과정:**
1. HTTP로 Upgrade 요청 (Connection: Upgrade, Upgrade: websocket)
2. 서버가 101 Switching Protocols 응답
3. 이후 WebSocket 프레임으로 양방향 통신

HTTP/2의 Server-Sent Events(SSE)는 서버에서 클라이언트로의 단방향 실시간 통신을 HTTP로 구현하는 대안입니다.

### Q9. REST의 특징(제약조건)은?

**A.**
REST(Representational State Transfer)는 Roy Fielding이 정의한 분산 하이퍼미디어 시스템을 위한 아키텍처 스타일입니다.

**6가지 제약조건:**

1. **클라이언트-서버 분리**: UI와 데이터 저장소를 분리하여 독립적 발전 가능
2. **무상태(Stateless)**: 서버는 클라이언트 상태를 저장하지 않음, 모든 요청은 독립적
3. **캐시 가능(Cacheable)**: 응답에 캐시 가능 여부를 명시
4. **계층화 시스템(Layered System)**: 클라이언트는 중간 계층(프록시, 게이트웨이) 존재를 모름
5. **균일한 인터페이스(Uniform Interface)**: 리소스 식별, 표현을 통한 조작, 자기 서술적 메시지, HATEOAS
6. **코드 온 디맨드(선택적)**: 서버가 실행 가능한 코드(JavaScript 등)를 클라이언트에 전송 가능

RESTful API는 이 원칙을 따르는 API이며, HTTP 메서드(GET, POST, PUT, DELETE)와 URI로 리소스를 표현합니다.

### Q10. 브라우저에 URL을 입력하면 어떤 일이 일어나나요?

**A.**
전체 흐름을 단계별로 설명합니다.

1. **URL 파싱**: 브라우저가 프로토콜, 도메인, 경로를 파싱
2. **캐시 확인**: 브라우저 캐시에서 이전 응답 확인
3. **DNS 조회**: 도메인을 IP 주소로 변환 (브라우저 캐시 → OS 캐시 → DNS 서버 순)
4. **TCP 연결 수립**: 3-way handshake로 서버와 연결
5. **TLS 핸드셰이크**: HTTPS인 경우 암호화 채널 수립
6. **HTTP 요청 전송**: GET /path HTTP/1.1 형식으로 요청
7. **서버 처리**: 웹 서버가 요청 처리 후 응답 생성
8. **HTTP 응답 수신**: 상태 코드, 헤더, 바디 수신
9. **렌더링**:
   - HTML 파싱 → DOM 트리 생성
   - CSS 파싱 → CSSOM 트리 생성
   - DOM + CSSOM → 렌더 트리 생성
   - 레이아웃(Reflow) → 페인팅(Repaint)
   - JavaScript 실행
10. **페이지 표시 완료**

### Q11. 프로세스와 스레드의 차이는?

**A.**

| 특성 | 프로세스 | 스레드 |
|------|----------|--------|
| 정의 | 실행 중인 프로그램의 인스턴스 | 프로세스 내 실행 단위 |
| 메모리 | 독립적인 메모리 공간 | 스택만 독립, 나머지 공유 |
| 통신 | IPC 필요 (파이프, 소켓 등) | 공유 메모리로 직접 통신 |
| 생성 비용 | 높음 | 낮음 |
| 안정성 | 하나 죽어도 다른 프로세스 영향 없음 | 하나의 스레드 오류가 전체에 영향 |
| 컨텍스트 스위칭 비용 | 높음 | 낮음 |

**멀티프로세스 vs 멀티스레드:**
- 멀티프로세스: 안정성 높음, 메모리 소비 많음 (Chrome의 탭별 프로세스)
- 멀티스레드: 효율적, 동기화 문제 고려 필요

### Q12. 컨텍스트 스위칭이란?

**A.**
컨텍스트 스위칭(Context Switching)은 CPU가 현재 실행 중인 프로세스/스레드를 중단하고 다른 프로세스/스레드를 실행하기 위해 상태를 저장하고 복원하는 과정입니다.

**과정:**
1. 현재 프로세스의 레지스터, 프로그램 카운터, 스택 포인터 등을 PCB(Process Control Block)에 저장
2. 다음 실행할 프로세스의 PCB에서 상태 복원
3. CPU가 새 프로세스 실행 재개

**발생 시점:**
- 타임 슬라이스 만료 (선점형 스케줄링)
- I/O 대기 (블로킹 시스템 콜)
- 인터럽트 발생
- 우선순위 높은 프로세스 도착

**오버헤드:** 컨텍스트 스위칭 자체는 유용한 작업을 하지 않으므로 비용이 발생합니다. 스레드 간 스위칭이 프로세스 간 스위칭보다 빠릅니다.

### Q13. 가상 메모리란 무엇인가요?

**A.**
가상 메모리(Virtual Memory)는 실제 물리 메모리보다 큰 주소 공간을 프로세스에 제공하는 메모리 관리 기법입니다.

**핵심 개념:**
- 각 프로세스는 독립적인 가상 주소 공간을 가짐
- 실제 사용하는 페이지만 물리 메모리에 올림
- 나머지는 디스크(스왑 공간)에 저장

**장점:**
- 물리 메모리보다 큰 프로그램 실행 가능
- 프로세스 간 메모리 격리 (보안 및 안정성)
- 메모리 공유 가능 (공유 라이브러리 등)

**구현 방식:**
- **페이징**: 고정 크기 페이지 단위로 관리 (외부 단편화 없음)
- **세그멘테이션**: 가변 크기 세그먼트로 관리 (내부 단편화 없음)
- 현대 OS는 페이징 방식을 주로 사용

### Q14. 페이지 폴트란 무엇인가요?

**A.**
페이지 폴트(Page Fault)는 프로세스가 접근하려는 가상 주소의 페이지가 현재 물리 메모리에 없을 때 발생하는 예외(인터럽트)입니다.

**처리 과정:**
1. CPU가 가상 주소 접근 시 페이지 테이블 확인
2. 해당 페이지가 메모리에 없으면 페이지 폴트 인터럽트 발생
3. OS의 페이지 폴트 핸들러 실행
4. 디스크에서 해당 페이지를 물리 메모리로 로드
5. 페이지 테이블 업데이트
6. 프로세스 실행 재개

**페이지 교체 알고리즘:**
- **FIFO**: 가장 먼저 들어온 페이지 교체
- **LRU(Least Recently Used)**: 가장 오래 사용하지 않은 페이지 교체
- **LFU(Least Frequently Used)**: 사용 빈도가 가장 낮은 페이지 교체
- **Optimal**: 앞으로 가장 오래 사용되지 않을 페이지 교체 (이론적 최적)

### Q15. 교착상태(Deadlock)의 조건과 해결법은?

**A.**
교착상태는 두 개 이상의 프로세스가 서로 상대방의 자원을 기다리며 무한히 대기하는 상태입니다.

**4가지 필요 조건 (코프만 조건):**
1. **상호 배제**: 자원을 한 번에 하나의 프로세스만 사용
2. **점유와 대기**: 자원을 가진 채 다른 자원을 기다림
3. **비선점**: 다른 프로세스의 자원을 강제로 빼앗을 수 없음
4. **순환 대기**: 프로세스들이 원형으로 자원을 기다림

**해결 방법:**
- **예방(Prevention)**: 4가지 조건 중 하나를 제거 (자원 낭비 발생 가능)
- **회피(Avoidance)**: 은행가 알고리즘으로 안전 상태만 유지
- **탐지(Detection)**: 교착상태 발생 후 탐지하고 복구
- **무시**: 교착상태 드물게 발생 시 시스템 재시작 (Unix/Windows 방식)

### Q16. 세마포어와 뮤텍스의 차이는?

**A.**

| 특성 | 뮤텍스(Mutex) | 세마포어(Semaphore) |
|------|---------------|---------------------|
| 목적 | 상호 배제 (임계 구역 보호) | 동기화 + 자원 접근 제어 |
| 값 범위 | 0 또는 1 (이진) | 0 이상의 정수 |
| 소유권 | 잠근 스레드만 해제 가능 | 다른 스레드도 해제 가능 |
| 종류 | - | 이진 세마포어, 계수 세마포어 |

**뮤텍스 예시:**
```
mutex.lock()
// 임계 구역
mutex.unlock()  // 반드시 같은 스레드가 해제
```

**세마포어 예시 (계수형):**
```
semaphore = 3  // 동시 접근 허용 수
sem.wait()     // P 연산: 값 감소, 0이면 대기
// 공유 자원 접근
sem.signal()   // V 연산: 값 증가, 대기 중인 프로세스 깨움
```

이진 세마포어는 뮤텍스처럼 동작하지만, 소유권 개념이 없다는 차이가 있습니다.

### Q17. CPU 스케줄링 알고리즘 종류는?

**A.**

**비선점형 알고리즘:**
- **FCFS(First Come First Served)**: 도착 순서대로 처리, 구현 단순, 호위 효과 발생
- **SJF(Shortest Job First)**: 실행 시간이 짧은 작업 우선, 최적 평균 대기 시간, 기아 문제

**선점형 알고리즘:**
- **SRTF(Shortest Remaining Time First)**: SJF의 선점형 버전
- **Round Robin**: 타임 퀀텀 단위로 순환 처리, 응답 시간 균등, 타임 퀀텀 크기가 성능 좌우
- **Priority Scheduling**: 우선순위 기반, 기아(Starvation) 문제 → Aging으로 해결
- **Multilevel Queue**: 프로세스를 여러 큐로 분류하여 각 큐에 다른 알고리즘 적용

**주요 지표:**
- CPU 이용률, 처리량(Throughput)
- 대기 시간, 반환 시간, 응답 시간

### Q18. 캐시 메모리란 무엇인가요?

**A.**
캐시 메모리는 CPU와 주기억장치(RAM) 사이의 속도 차이를 줄이기 위한 고속의 소용량 메모리입니다.

**계층 구조:**
```
CPU 레지스터 (가장 빠름, 가장 작음)
     ↕
L1 캐시 (수 KB, 수 사이클)
     ↕
L2 캐시 (수백 KB, 수십 사이클)
     ↕
L3 캐시 (수 MB, 수백 사이클)
     ↕
RAM (수 GB, 수백~수천 사이클)
     ↕
디스크 (수 TB, 수백만 사이클)
```

**캐시 동작 원리:**
- **지역성 원리(Locality)**
  - 시간적 지역성: 최근 접근한 데이터는 다시 접근 가능성 높음
  - 공간적 지역성: 접근한 데이터 근처 데이터도 접근 가능성 높음
- **캐시 히트**: 원하는 데이터가 캐시에 있음 (빠름)
- **캐시 미스**: 캐시에 없어 하위 메모리 접근 필요 (느림)

### Q19. 동기화 문제(Race Condition)란?

**A.**
Race Condition(경쟁 조건)은 두 개 이상의 프로세스/스레드가 공유 자원에 동시에 접근하여, 실행 순서에 따라 결과가 달라지는 문제입니다.

**예시:**
```python
# 전역 변수 count = 0
# 스레드 A와 B가 동시에 count += 1 실행

# 문제 발생 시나리오:
# A: count 읽음 (0)
# B: count 읽음 (0)
# A: 0 + 1 = 1 저장
# B: 0 + 1 = 1 저장  ← 기대값 2가 아닌 1이 됨
```

**임계 구역(Critical Section):** 공유 자원에 접근하는 코드 구간

**해결 조건:**
1. **상호 배제**: 한 번에 하나의 프로세스만 임계 구역 진입
2. **진행**: 임계 구역 외부의 프로세스가 진입을 방해하지 않음
3. **한정 대기**: 무한 대기 없이 유한 시간 내 진입 보장

**해결책:** 뮤텍스, 세마포어, 모니터, synchronized 키워드(Java) 사용

### Q20. 사용자 공간과 커널 공간의 차이는?

**A.**
운영체제는 메모리를 사용자 공간(User Space)과 커널 공간(Kernel Space)으로 분리합니다.

**커널 공간:**
- OS 커널이 실행되는 영역
- 모든 하드웨어 자원에 직접 접근 가능
- 높은 권한 (Ring 0)

**사용자 공간:**
- 일반 응용 프로그램이 실행되는 영역
- 하드웨어에 직접 접근 불가
- 낮은 권한 (Ring 3)

**시스템 콜(System Call):**
사용자 공간에서 커널 기능이 필요할 때 사용하는 인터페이스

```
응용 프로그램 → 시스템 콜 → 커널 모드 전환 → 커널 처리 → 사용자 모드 복귀
```

**목적:** 보안과 안정성 보장. 프로그램이 실수로 또는 의도적으로 OS나 다른 프로그램의 메모리를 침범하지 못하도록 방어

## 데이터베이스

### Q21. ACID란 무엇인가요?

**A.**
ACID는 데이터베이스 트랜잭션이 안전하게 수행되기 위한 4가지 특성입니다.

- **A - 원자성(Atomicity)**: 트랜잭션의 모든 작업은 전부 완료되거나 전부 실패해야 함 (All or Nothing)
- **C - 일관성(Consistency)**: 트랜잭션 전후에 데이터베이스 제약 조건이 항상 유지되어야 함
- **I - 격리성(Isolation)**: 동시에 실행되는 트랜잭션은 서로 영향을 주지 않아야 함
- **D - 지속성(Durability)**: 커밋된 트랜잭션의 결과는 시스템 오류가 발생해도 영구적으로 보존

**예시 (계좌 이체):**
```
BEGIN TRANSACTION;
UPDATE accounts SET balance = balance - 1000 WHERE id = 'A';  -- A 계좌 차감
UPDATE accounts SET balance = balance + 1000 WHERE id = 'B';  -- B 계좌 추가
COMMIT;
-- 둘 중 하나 실패 시 ROLLBACK
```

### Q22. 트랜잭션 격리 수준을 설명해주세요

**A.**
격리 수준(Isolation Level)은 동시 트랜잭션 간 격리 정도를 정의합니다. 격리 수준이 높을수록 데이터 정합성은 높아지지만 성능은 낮아집니다.

| 격리 수준 | Dirty Read | Non-Repeatable Read | Phantom Read |
|-----------|------------|---------------------|--------------|
| READ UNCOMMITTED | 발생 | 발생 | 발생 |
| READ COMMITTED | 방지 | 발생 | 발생 |
| REPEATABLE READ | 방지 | 방지 | 발생 |
| SERIALIZABLE | 방지 | 방지 | 방지 |

- **Dirty Read**: 커밋되지 않은 데이터 읽기
- **Non-Repeatable Read**: 같은 쿼리 두 번 실행 시 결과가 다름 (중간에 UPDATE)
- **Phantom Read**: 같은 조건 쿼리 두 번 실행 시 행 수가 다름 (중간에 INSERT/DELETE)

MySQL InnoDB의 기본값은 REPEATABLE READ이며, MVCC로 Phantom Read도 대부분 방지합니다.

### Q23. 인덱스의 동작 원리는?

**A.**
인덱스(Index)는 데이터베이스 테이블의 검색 속도를 향상시키기 위한 자료구조입니다.

**동작 원리:**
- 인덱스 없이 검색: Full Table Scan → O(n)
- 인덱스로 검색: B+Tree 탐색 → O(log n)

**인덱스 종류:**
- **클러스터형(Clustered)**: 데이터 행이 인덱스 순서대로 물리적으로 정렬 (테이블당 1개, 주로 PK)
- **비클러스터형(Non-Clustered)**: 별도 자료구조에 인덱스 저장, 데이터 행의 포인터 보유 (여러 개 가능)

**인덱스를 사용하지 않는 경우:**
- `LIKE '%검색어'` (앞에 와일드카드)
- 인덱스 컬럼에 함수 적용: `WHERE UPPER(name) = 'KIM'`
- 부정 조건: `!=`, `NOT IN`
- 카디널리티가 낮은 컬럼 (성별 등)

**단점:** 쓰기 성능 저하 (INSERT/UPDATE/DELETE 시 인덱스도 갱신), 추가 저장 공간 필요

---

### Q24. B-Tree와 B+Tree의 차이는?

**A.**

| 특성 | B-Tree | B+Tree |
|------|--------|--------|
| 데이터 저장 위치 | 모든 노드(내부 + 리프) | 리프 노드에만 |
| 리프 노드 연결 | 없음 | 연결 리스트로 연결 |
| 범위 검색 | 비효율적 (트리 순회 필요) | 효율적 (리프 노드 순회) |
| 내부 노드 크기 | 데이터 포함으로 큼 | 키만 저장으로 작음 → 더 많은 자식 |
| 검색 속도 | 운이 좋으면 빠름 | 항상 리프까지 이동 |

**B+Tree가 DB 인덱스에 적합한 이유:**
1. 리프 노드가 연결 리스트로 이어져 범위 쿼리(`BETWEEN`, `>`, `<`) 고속 처리
2. 내부 노드에 데이터가 없어 더 많은 키를 저장 가능 → 트리 높이 낮아짐 → I/O 횟수 감소

MySQL InnoDB, PostgreSQL 등 대부분의 RDBMS가 B+Tree를 인덱스 구조로 사용합니다.

### Q25. 정규화란 무엇인가요?

**A.**
정규화(Normalization)는 데이터 중복을 최소화하고 데이터 무결성을 보장하기 위해 테이블을 구조적으로 분리하는 과정입니다.

**정규형 단계:**

| 정규형 | 조건 |
|--------|------|
| 1NF | 원자값만 허용 (반복 그룹 제거) |
| 2NF | 1NF + 부분 함수 종속 제거 (복합 키의 일부에만 종속된 속성 분리) |
| 3NF | 2NF + 이행 함수 종속 제거 (A→B→C 관계 분리) |
| BCNF | 3NF + 모든 결정자가 후보 키 |

**정규화의 장점:** 데이터 중복 감소, 이상(Anomaly) 현상 방지
**정규화의 단점:** JOIN 연산 증가 → 성능 저하 가능

**역정규화(Denormalization):** 읽기 성능 향상을 위해 의도적으로 중복을 허용하는 기법. 조회가 매우 빈번하고 수정이 적은 경우 사용.

### Q26. JOIN의 종류와 차이는?

**A.**

```
테이블 A    테이블 B
1           1
2           2
3           4
```

| JOIN 종류 | 결과 | 설명 |
|-----------|------|------|
| INNER JOIN | 1, 2 | 양쪽 모두에 존재하는 행만 |
| LEFT JOIN | 1, 2, 3 | 왼쪽 테이블 전체 + 오른쪽 매칭 (없으면 NULL) |
| RIGHT JOIN | 1, 2, 4 | 오른쪽 테이블 전체 + 왼쪽 매칭 (없으면 NULL) |
| FULL OUTER JOIN | 1, 2, 3, 4 | 양쪽 모두 포함 (없으면 NULL) |
| CROSS JOIN | 3 * 3 = 9행 | 카테시안 곱 |
| SELF JOIN | - | 같은 테이블과 JOIN (조직도, 계층 구조) |

**JOIN 내부 알고리즘:**
- **Nested Loop Join**: 작은 테이블 기준 반복 (소규모)
- **Hash Join**: 해시 테이블 생성 후 매칭 (대용량 등가 조인)
- **Sort-Merge Join**: 양쪽 정렬 후 병합 (이미 정렬된 경우 효율적)

### Q27. NoSQL vs RDBMS 선택 기준은?

**A.**

**RDBMS 선택 시:**
- 데이터 간 관계가 복잡하고 JOIN이 많은 경우
- ACID 트랜잭션이 반드시 필요한 경우 (금융, 결제)
- 데이터 구조가 명확하고 변경이 적은 경우
- 복잡한 쿼리와 집계가 필요한 경우

**NoSQL 선택 시:**
- 대용량 데이터, 높은 쓰기 처리량이 필요한 경우
- 스키마가 유연하게 변경되어야 하는 경우
- 수평 확장(Scale-out)이 필요한 경우
- 특수 데이터 구조에 최적화된 접근이 필요한 경우

**NoSQL 종류:**
| 타입 | 예시 | 용도 |
|------|------|------|
| Document | MongoDB | 유연한 JSON 문서 저장 |
| Key-Value | Redis | 캐시, 세션 저장 |
| Column-Family | Cassandra | 시계열, 대규모 쓰기 |
| Graph | Neo4j | 소셜 네트워크, 추천 시스템 |

### Q28. CAP 이론이란?

**A.**
CAP 이론은 분산 시스템에서 다음 세 가지 특성을 동시에 모두 보장할 수 없다는 이론입니다 (Eric Brewer).

- **C - 일관성(Consistency)**: 모든 노드가 항상 동일한 데이터를 반환
- **A - 가용성(Availability)**: 모든 요청에 응답 반환 (오류 없음)
- **P - 분할 내성(Partition Tolerance)**: 네트워크 분할(장애)이 발생해도 시스템이 계속 동작

**분산 시스템에서 P는 사실상 필수**이므로 실제 선택은 CP vs AP입니다.

| 분류 | 예시 | 특징 |
|------|------|------|
| CP | HBase, Zookeeper | 네트워크 분할 시 가용성 포기, 일관성 유지 |
| AP | Cassandra, DynamoDB | 네트워크 분할 시 일관성 포기, 최종 일관성 |
| CA | 단일 노드 RDBMS | 분산 환경에서는 P를 포기할 수 없어 사실상 불가 |

**PACELC 이론**: CAP의 확장 버전으로, 정상 운영 중에도 지연(Latency)과 일관성 간의 트레이드오프를 다룸.

### Q29. 샤딩(Sharding)이란?

**A.**
샤딩은 대용량 데이터를 여러 데이터베이스 서버에 분산하여 저장하는 수평 파티셔닝 기법입니다.

**샤딩 전략:**

1. **Range 샤딩**: 범위 기준으로 분할 (id 1~1000 → 샤드1, 1001~2000 → 샤드2)
   - 장점: 범위 쿼리 효율적
   - 단점: 데이터 쏠림 가능 (핫스팟)

2. **Hash 샤딩**: 키의 해시값으로 분할 (id % 샤드수)
   - 장점: 균등 분배
   - 단점: 범위 쿼리 비효율, 샤드 추가 시 재배치 필요

3. **Directory 샤딩**: 별도의 조회 테이블로 샤드 결정
   - 장점: 유연성 높음
   - 단점: 조회 테이블 자체가 병목

**샤딩의 어려움:**
- 교차 샤드 JOIN 불가
- 트랜잭션 처리 복잡
- 샤드 추가/재배치 복잡성

### Q30. N+1 쿼리 문제란?

**A.**
N+1 문제는 ORM 사용 시 1개의 쿼리로 N개의 결과를 가져온 뒤, 각 결과에 대해 추가로 N번의 쿼리를 실행하는 비효율적인 패턴입니다.

**예시 (게시글과 작성자):**
```python
# 문제 상황
posts = Post.objects.all()  # 쿼리 1번: 게시글 100개 조회
for post in posts:
    print(post.author.name)  # 쿼리 100번: 각 게시글의 작성자 조회
# 총 101번 쿼리 실행
```

**해결 방법:**

1. **Eager Loading (즉시 로딩)**:
   ```python
   # Django
   posts = Post.objects.select_related('author').all()  # JOIN으로 1번 쿼리
   # 또는
   posts = Post.objects.prefetch_related('comments').all()  # 2번 쿼리로 처리
   ```

2. **직접 JOIN 쿼리 작성**:
   ```sql
   SELECT posts.*, users.name
   FROM posts
   JOIN users ON posts.author_id = users.id;
   ```

3. **DataLoader 패턴** (GraphQL에서 주로 사용): 요청을 일괄 처리하여 배치 쿼리 실행

N+1 문제는 쿼리 로그를 통해 발견하고, ORM의 쿼리 분석 도구를 활용하면 탐지가 쉬워집니다.
