## 1. Core Web Vitals 3가지와 기준은?

**답변:**
LCP(최대 콘텐츠 페인트, ≤2.5s, 로딩), INP(상호작용→다음 페인트, ≤200ms, 반응성, 2024년 FID 대체), CLS(누적 레이아웃 이동, ≤0.1, 시각 안정성). 실사용자 p75 분포로 평가한다.

## 2. LCP를 개선하는 방법은?

**답변:**
대표 이미지를 `preload`+`fetchpriority="high"`로 우선 로드(lazy 제외), 서버 응답 시간(TTFB) 단축, 렌더 블로킹 CSS/JS 제거, 이미지 포맷·크기 최적화, 폰트 빠른 표시. LCP 요소가 무엇인지부터 측정해 그것을 빨리 그리는 데 집중한다.

## 3. CLS의 원인과 해결은?

**답변:**
크기 미지정 이미지/광고/임베드, 동적 삽입 콘텐츠, 폰트 교체(FOUT)로 레이아웃이 밀리는 것. 해결: `width/height` 또는 `aspect-ratio` 지정, 동적 영역 공간 예약, `font-display`로 교체 충격 완화, 삽입은 기존 콘텐츠 위가 아닌 아래로.

## 4. INP(반응성)를 개선하려면?

**답변:**
긴 작업(long task)을 쪼개고, 핸들러의 무거운 작업을 `requestIdleCallback`/`setTimeout`/`scheduler.yield`로 분할, 불필요한 리렌더 제거, 무거운 계산은 Web Worker로. 입력 후 다음 페인트까지의 지연이 핵심이라 메인 스레드를 빨리 비우는 게 관건이다.

## 5. 성능을 어떻게 측정하나요?

**답변:**
랩(합성): Lighthouse, WebPageTest, DevTools Performance 패널 — CI 회귀 게이트용. 필드(RUM): `web-vitals` 라이브러리로 실사용자 수집. `PerformanceObserver`/Navigation·Resource Timing API로 세부 단계 측정. 평균이 아닌 p75를 본다.

## 6. Critical Rendering Path 최적화는?

**답변:**
HTML→DOM, CSS→CSSOM→렌더트리→레이아웃→페인트 경로를 단축한다. CSS는 head에서 빠르게(critical CSS 인라인), JS는 `defer`/`async`로 파싱 차단 방지, 첫 화면에 필요 없는 리소스는 미루기. 첫 픽셀까지 필요한 리소스 수·크기를 최소화한다.

## 7. 렌더 블로킹 리소스를 어떻게 줄이나요?

**답변:**
CSS는 기본 렌더 블로킹 → critical CSS 인라인 + 나머지 비동기 로드, 미디어 쿼리로 분리. JS는 `<script defer>`(문서 파싱 후 순서대로) 또는 `async`(독립 실행)로 파서 차단을 막는다. 사용 안 하는 CSS 제거.

## 8. `preload`/`prefetch`/`preconnect` 차이는?

**답변:**
`preload`는 현재 페이지에 곧 필요한 리소스를 높은 우선순위로 미리 받음(폰트, LCP 이미지). `prefetch`는 다음 내비게이션에 쓸 리소스를 낮은 우선순위로 미리 받음. `preconnect`는 외부 출처에 미리 연결(DNS+TCP+TLS) 비용을 선지불.

## 9. 코드 스플리팅과 지연 로딩은?

**답변:**
번들을 라우트/컴포넌트 단위로 쪼개(`import()` 동적 임포트, `React.lazy`) 초기 번들을 줄이고 필요할 때 로드한다. 라우트 기반 분할이 가장 효과적이고, 무거운 위젯(차트·에디터)은 상호작용 시 로드한다.

## 10. 번들 크기를 어떻게 줄이나요?

**답변:**
트리셰이킹(ESM, sideEffects 설정), 무거운 라이브러리 경량 대체(moment→dayjs), 동적 임포트, 중복 의존성 제거, 번들 분석기(webpack-bundle-analyzer)로 큰 모듈 식별, polyfill을 타깃 브라우저에 맞게 축소.

## 11. 이미지 최적화 전략은?

**답변:**
차세대 포맷(WebP/AVIF), `srcset`+`sizes`로 반응형 해상도, `loading="lazy"`, CDN 리사이즈, `width/height` 지정(CLS 방지), LCP 이미지는 우선 로드. SVG는 아이콘/로고에, 큰 사진은 손실 압축.

## 12. 폰트 최적화는?

**답변:**
`font-display: swap`(텍스트 즉시 표시), 서브셋(필요 글리프만), WOFF2, 핵심 폰트 `preload`, 시스템 폰트 폴백 지정으로 CLS 최소화, 가변 폰트로 파일 수 절감.

## 13. HTTP 캐싱 전략은?

**답변:**
정적 자산은 콘텐츠 해시 파일명 + `Cache-Control: immutable, max-age=1년`. HTML은 `no-cache`로 항상 검증. 변하는 API는 `ETag`/`Last-Modified`로 조건부 요청(304). 캐시 무효화는 파일명 변경(cache busting)으로.

## 14. CDN은 어떻게 성능을 높이나요?

**답변:**
사용자와 지리적으로 가까운 엣지에서 정적 자산을 제공해 RTT를 줄인다. 엣지 캐싱, 압축, HTTP/2·3, TLS 종단, 트래픽 분산. 동적 콘텐츠도 엣지 컴퓨팅으로 가속 가능.

## 15. HTTP/2·HTTP/3가 성능에 주는 영향은?

**답변:**
HTTP/2는 멀티플렉싱(한 연결로 병렬 요청, HOL 블로킹 완화), 헤더 압축, 서버 푸시. HTTP/3는 QUIC(UDP) 기반이라 TCP HOL 블로킹을 없애고 연결 수립이 빠르며 네트워크 전환에 강하다. 도메인 샤딩 같은 1.1 시절 기법은 불필요해진다.

## 16. Reflow와 Repaint를 줄이는 방법은?

**답변:**
레이아웃 속성(width, top, margin) 변경은 reflow, 색·배경은 repaint. DOM 변경을 배치(DocumentFragment), 레이아웃 읽기/쓰기 분리(강제 동기 레이아웃 방지), `class` 토글로 일괄 변경, 애니메이션은 `transform`/`opacity`만 사용.

## 17. 어떤 CSS 속성이 컴포지터에서만 처리되나요?

**답변:**
`transform`과 `opacity`는 레이아웃·페인트를 건너뛰고 GPU 컴포지터에서만 처리돼 60fps 애니메이션에 적합하다. `will-change`로 레이어 승격을 힌트할 수 있으나 남용하면 메모리를 낭비한다. `top/left`로 애니메이션하면 매 프레임 reflow가 난다.

## 18. 긴 리스트 렌더링 최적화는?

**답변:**
가상화(windowing): 화면에 보이는 항목만 렌더(react-window/virtual). 수천 개 DOM을 수십 개로 줄여 메모리·페인트 비용을 낮춘다. 무한 스크롤과 결합하고, 항목에 안정적 key를 준다.

## 19. 디바운스와 스로틀의 차이는?

**답변:**
디바운스는 "마지막 호출 후 N ms 동안 잠잠하면 1회 실행"(검색 입력). 스로틀은 "N ms마다 최대 1회 실행"(스크롤·리사이즈). 둘 다 고빈도 이벤트의 핸들러 실행 횟수를 줄여 성능을 지킨다.

## 20. 메인 스레드 블로킹을 어떻게 푸나요?

**답변:**
무거운 계산을 Web Worker로 오프로드, 작업을 청크로 쪼개 양보(`scheduler.yield`/`setTimeout`), 가상화로 렌더 비용 축소, 불필요한 리렌더·강제 동기 레이아웃 제거. 50ms 넘는 long task를 없애는 게 목표.

## 21. 메모리 누수를 어떻게 찾나요?

**답변:**
DevTools Memory 패널의 힙 스냅샷을 시점별로 비교(detached DOM, 증가하는 객체 확인), Performance의 메모리 그래프 추세 관찰. 흔한 원인은 제거 안 한 이벤트 리스너·타이머, 전역 캐시 무한 증가, 클로저가 잡은 큰 객체다.

## 22. SSR/SSG/스트리밍이 성능에 주는 이점은?

**답변:**
SSG는 빌드 시 HTML 생성으로 TTFB·LCP가 가장 빠르고 SEO에 좋다. SSR은 동적 데이터를 서버에서 그려 초기 콘텐츠를 빠르게 보낸다. 스트리밍 SSR(React Suspense)은 준비된 부분부터 점진 전송해 TTFB를 낮춘다. 대신 서버 부하·hydration 비용을 고려한다.
