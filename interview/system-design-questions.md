## 1. 프론트엔드 시스템 디자인 접근 프레임워크 (RADIO)

**답변:**
무엇을 묻든 다음 순서로 풀어가면 빠짐이 없다.

| 단계 | 내용 |
|------|------|
| **R**equirements | 기능/비기능 요구사항 명확화. 사용자 규모, 기기, 핵심 시나리오 질문 |
| **A**rchitecture | 컴포넌트 구조, 데이터 흐름, 모듈 경계 |
| **D**ata model | 클라이언트 상태 vs 서버 상태, 정규화, 캐시 |
| **I**nterface(API) | 컴포넌트 props / 서버 API 계약(페이지네이션, 에러 형태) |
| **O**ptimization | 성능(렌더·네트워크·번들), 접근성, 반응형, 에러 처리 |

> 첫 5분은 **항상 요구사항 질문**에 쓴다. "사용자 수는? 모바일 비중은? 실시간성이 필요한가?"를 묻지 않고 코드부터 그리면 감점이다.

## 2. 무한 스크롤 피드를 설계해보세요

**답변:**
- **데이터 로딩**: 오프셋 페이지네이션은 데이터가 바뀌면 항목 중복/누락 → **커서 기반(cursor) 페이지네이션** 권장.
- **트리거**: 스크롤 이벤트(throttle) 대신 **IntersectionObserver**로 sentinel 요소가 보이면 다음 페이지 로드 (성능·정확성↑).
- **DOM 폭증 방지**: 항목이 수천 개면 **윈도잉/가상화(virtualization)**로 화면에 보이는 것만 렌더(react-window 등).
- **UX**: 스켈레톤 로더, 낙관적 스크롤 위치 유지, 실패 시 재시도, 빈/끝 상태.
- **접근성**: 무한 스크롤은 푸터 도달 불가·스크린리더 혼란 → "더 보기" 버튼 병행 또는 `aria-live`로 로드 알림.

```js
const io = new IntersectionObserver(([e]) => {
  if (e.isIntersecting) loadNextPage(); // sentinel 진입 시
});
io.observe(sentinelEl);
```

## 3. 자동완성(타입어헤드) 검색을 설계해보세요

**답변:**
- **요청 최소화**: 입력마다 호출하면 과부하 → **디바운스**(예: 250ms). 최소 글자 수 제한.
- **경쟁 상태(race condition)**: 느린 이전 요청이 빠른 최신 요청보다 늦게 도착해 옛 결과를 덮어쓰는 문제 → 요청에 순번을 달거나 **AbortController로 이전 요청 취소**.
- **캐싱**: 같은 쿼리 결과를 메모리/LRU 캐시로 재사용.
- **응답성**: 결과는 `aria-live`/`role="listbox"`로 노출, 방향키 탐색(roving tabindex), Enter 선택.
- **백엔드 협의**: prefix 검색 인덱스(트라이/검색엔진), 결과 개수 제한, 인기순 랭킹.

```js
let controller;
async function search(q) {
  controller?.abort();              // 이전 요청 취소
  controller = new AbortController();
  const res = await fetch(`/search?q=${q}`, { signal: controller.signal });
  render(await res.json());
}
```

> 디바운스 + 요청 취소 + 캐싱, 이 3종 세트가 핵심 답변. 면접관이 가장 듣고 싶어 하는 건 "race condition을 어떻게 막느냐"다.

## 4. 대규모 폼/디자인 시스템을 설계해보세요

**답변:**
- **상태 관리**: 비제어(uncontrolled) + ref로 리렌더 최소화 vs 제어(controlled)로 실시간 검증. 큰 폼은 필드 단위 구독(react-hook-form식)으로 리렌더 격리.
- **검증**: 스키마 기반(zod/yup)으로 클라이언트·서버 공유. 동기/비동기(중복 확인) 검증 분리. 에러는 `aria-describedby`로 입력과 연결.
- **디자인 시스템**: 토큰(색·간격·타이포) → 프리미티브 컴포넌트 → 합성 컴포넌트 계층. 접근성을 컴포넌트에 내장(Headless UI/Radix식 동작 + 스타일 분리).
- **API**: 컴포넌트는 일관된 props 계약(`value`, `onChange`, `error`, `disabled`), 합성(composition)으로 확장.
- **버전/배포**: 모노레포 + 변경 로그 + 시각 회귀 테스트(Storybook + Chromatic).

## 5. 실시간 협업/채팅 UI를 설계해보세요

**답변:**
- **전송 채널**: 단방향 서버→클라 알림은 **SSE**, 양방향 고빈도(채팅·커서)는 **WebSocket**. 폴링은 최후수단.
- **낙관적 업데이트**: 메시지를 즉시 화면에 그리고(임시 ID) 서버 확인 후 확정/실패 롤백.
- **순서·중복**: 메시지 시퀀스 번호, 멱등 처리, 재연결 시 마지막 수신 이후만 동기화.
- **연결 관리**: 끊김 감지 → 지수 백오프 재연결, 오프라인 큐.
- **협업 동시 편집**: 충돌 해결 전략 **CRDT** 또는 **OT**(운영 변환) 언급.
- **성능**: 메시지 목록 가상화, 이미지 지연 로드, 입력 중(typing) 이벤트 throttle.

## 6. 이미지 갤러리의 성능을 어떻게 최적화하나요

**답변:**
- **포맷/크기**: WebP/AVIF, `srcset`+`sizes`로 기기별 적정 해상도, CDN 리사이즈.
- **지연 로드**: `loading="lazy"` 또는 IntersectionObserver.
- **레이아웃 안정성**: `width/height` 또는 `aspect-ratio` 지정으로 **CLS 방지**(이미지 로드 시 점프 막기).
- **LCP 최적화**: 첫 화면 대표 이미지는 `fetchpriority="high"`+preload, lazy 제외.
- **대량 목록**: 가상화 + 썸네일 → 원본 점진 로드(blur-up placeholder).

---

## 7. 클라이언트 상태/서버 상태를 어떻게 나누나요

**답변:**
- **서버 상태**(원격 데이터: 목록, 프로필): React Query/SWR 같은 **데이터 페칭 캐시 라이브러리**로. 캐싱·재검증·중복요청 제거·낙관적 업데이트를 위임.
- **클라이언트 상태**(UI: 모달 열림, 폼 입력, 테마): 지역 `useState`/`useReducer`, 전역이 필요하면 Zustand/Jotai.
- 안티패턴: 서버 데이터를 Redux에 수동 복제 → 동기화 지옥. 서버 상태는 전용 라이브러리에 맡기는 게 현대적 정석.

## 8. 공통 트레이드오프 정리

| 결정 | 한쪽 | 다른 쪽 |
|------|------|---------|
| 페이지네이션 | 오프셋(단순) | 커서(정확·일관) |
| 렌더링 | CSR(상호작용) | SSR/SSG(초기 로딩·SEO) |
| 상태 | 제어 컴포넌트(검증 쉬움) | 비제어(리렌더 적음) |
| 실시간 | WebSocket(양방향) | SSE/폴링(단순·단방향) |
| 목록 | 전체 렌더(간단) | 가상화(대량 성능) |

> 면접에서 점수를 따는 문장: **"상황에 따라 다릅니다. X가 중요하면 A, Y가 중요하면 B를 택합니다. 여기선 요구사항이 ~이니 A가 적절합니다."** — 트레이드오프를 요구사항에 연결해 결론을 내리는 것이 핵심.
