# 11. Path Alias 일괄 마이그레이션 & 대규모 기계적 변경 검증

> 실전 배경: `../../../shared/...` 같은 상대경로 import를 `@/shared/...` alias로
> **250여 파일 일괄 전환**했다. "단순 치환"처럼 보이지만, 이중 설정(빌드 도구 + 타입)과
> "무엇을 제외할지", 그리고 "대규모 기계 변경을 어떻게 안전하다고 증명할지"가 관건이었다.

## 1. 왜 alias인가

```ts
// Before — 깊이에 따라 ../가 늘고, 파일을 옮기면 전부 깨진다
import { formatDate } from '../../../../shared/libs/dayjs';

// After — 위치와 무관하게 항상 동일
import { formatDate } from '@/shared/libs/dayjs';
```

- **가독성**: `../`의 개수를 세지 않아도 어디서 오는지 한눈에 보인다.
- **이동 내성**: 파일을 다른 디렉터리로 옮겨도 import 경로가 안 바뀐다(상대경로는 전부 깨짐).
- **일관성**: "이 모듈은 항상 `@/shared/...`"라는 단일 표기.

---

## 2. alias는 두 곳에 설정해야 한다

alias는 **번들러**와 **타입체커**가 각각 알아야 한다. 한쪽만 하면 "빌드는 되는데 타입 에러" 또는 "타입은 통과인데 런타임에 모듈 못 찾음"이 난다.

```ts
// vite.config.ts — 번들러/개발서버가 실제로 모듈을 해석
import { fileURLToPath, URL } from 'node:url';
export default defineConfig({
  resolve: {
    alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) },
  },
});
```

```jsonc
// tsconfig.json — vue-tsc/tsc가 타입 해석에 사용
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": { "@/*": ["src/*"] }
  }
}
```

> 두 설정의 `@`가 가리키는 경로가 **정확히 일치**해야 한다. Jest/Vitest를 쓴다면 그쪽 `resolve.alias`(또는 `moduleNameMapper`)에도 동일하게 필요하다. **alias는 "동일한 매핑을 여러 도구에 중복 선언"하는 것**이라, 하나라도 빠지면 특정 도구에서만 깨진다.

---

## 3. 무엇을 제외했나: CSS @use/@import

TS/Vue/TSX의 `import`는 모두 alias로 바꿨지만, **CSS/SCSS의 `@use`·`@import`와 `<style>` 블록 내 경로는 상대경로를 유지**했다.

이유: CSS 경로 해석은 JS 모듈 해석과 **다른 파이프라인**(전처리기·번들러 CSS 플러그인)을 타고, alias 지원 방식이 도구마다 다르다(`~` 접두, 별도 설정 등). 확실하지 않은 영역을 일괄 변환에 끌어들이면 위험만 커진다.

교훈: **일괄 변환의 범위를 "확실히 안전한 영역"으로 좁힌다.** "모든 걸 다 바꾸자"보다 "JS import만, CSS는 그대로"가 회귀 위험을 줄인다. (이건 [문서 06의 Strict Scope](./06-scope-and-layering.md) 원칙과 같은 사고.)

## 4. 대규모 기계적 변경을 안전하게 검증하기

250개 파일을 바꿨다고 눈으로 다 볼 수는 없다. "비즈니스 로직 변경 없음"을 **도구로 증명**한다.

- **타입체크(`vue-tsc`/`tsc`)**: 잘못된 alias는 "모듈을 찾을 수 없음"으로 타입 단계에서 전부 걸린다. 이게 1차 안전망.
- **린트 + import 정렬(`lint:fix`)**: 경로 문자열이 바뀌면 import 그룹 순서가 흐트러지므로 자동 정렬로 정규화. 포맷 노이즈를 줄여 diff를 읽을 수 있게 한다.
- **테스트 스위트**: 로직이 안 바뀌었으면 기존 테스트가 그대로 통과해야 한다. 통과 = "동작 보존"의 증거.
- **diff의 성격 확인**: diff가 **경로 문자열 치환 + 자동 정렬**로만 구성되는지 훑는다. 로직 라인이 섞였다면 그건 기계 변환이 잘못 건드린 것.

```bash
# 검증 파이프라인
pnpm lint:fix     # import 정렬 정규화
pnpm type         # vue-tsc — 잘못된 alias는 여기서 전부 실패
pnpm test:unit    # 로직 보존 확인
```

> 이런 "넓지만 얕은(wide but shallow)" 변경은 **자동화된 검증이 없으면 리뷰가 불가능**하다. 반대로 타입·린트·테스트가 통과하면, 250파일이어도 "기계적 치환"임을 높은 확신으로 말할 수 있다. 변경의 크기가 아니라 **검증 가능성**이 안전성을 만든다.

## 5. 면접 포인트

**Q. 상대경로 대신 path alias를 쓰는 이유는?**
> 가독성(../ 세지 않음), 이동 내성(파일을 옮겨도 경로 불변), 일관된 표기다. 상대경로는 깊이에 따라 ../가 늘고 파일 이동 시 전부 깨진다.

**Q. alias 설정은 어디에 하나요?**
> 번들러(vite resolve.alias)와 타입체커(tsconfig paths)에 동일한 매핑을 각각 선언해야 한다. 테스트 러너를 쓰면 거기에도 필요하다. 한쪽만 하면 "빌드는 되는데 타입 에러" 또는 그 반대가 난다. 여러 도구에 중복 선언되는 구조라 하나라도 빠지면 특정 도구에서만 깨진다.

**Q. CSS import는 왜 같이 안 바꿨나요?**
> CSS 경로 해석은 JS 모듈 해석과 다른 파이프라인을 타고 alias 지원 방식이 도구마다 달라 위험하다. 일괄 변환은 확실히 안전한 영역(JS import)으로 범위를 좁히는 게 회귀 위험을 줄인다.

**Q. 250개 파일을 바꿨는데 "안전하다"를 어떻게 증명하나요?**
> 도구로 증명한다. 타입체크는 잘못된 alias를 전부 잡고, 기존 테스트 통과는 동작 보존의 증거이며, diff가 경로 치환과 자동 정렬로만 구성되는지 확인한다. 변경의 크기가 아니라 검증 가능성이 안전성을 만든다. 넓지만 얕은 변경은 자동 검증이 없으면 리뷰 자체가 불가능하다.
