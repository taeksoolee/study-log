# 09. URL을 상태의 원천으로: 딥링크 · 필터 영속화 · 쿼리 동기화

> 실전 배경: 모니터링/정산 화면의 탭, 선택한 그룹·자원, 보이는 컬럼, 시간 범위, 정렬,
> 열린 드로어까지 — 이 모든 상태를 **쿼리스트링에 동기화**했다. 목적은 명확했다:
> "이 3개 컬럼을, 자원 10번을, 13:00~13:30 구간으로 봐줘"를 **URL 하나로 공유·복원**하는 것.

## 1. 왜 상태를 URL에 두는가

컴포넌트 지역 상태(`ref`/`useState`)에만 두면 새로고침·공유·뒤로가기에서 전부 날아간다. URL 쿼리스트링에 두면 얻는 것:

- **딥링크(공유 가능)**: 링크만 보내면 상대가 같은 화면을 본다. 협업 디버깅에서 특히 강력하다.
- **새로고침 복원**: F5를 눌러도 필터·탭·드로어가 그대로 복원된다.
- **뒤로/앞으로**: 브라우저 히스토리와 자연스럽게 통합된다.
- **북마크**: 특정 뷰를 북마크로 저장.

즉 **URL이 곧 화면 상태의 직렬화된 표현(single source of truth)**이 된다. "이 상태가 공유·복원되어야 하는가?"가 URL에 둘지의 기준이다.

---

## 2. 어떤 상태를 URL에 둘 것인가

실제로 동기화한 파라미터 예:

```
/monitoring?tab=resource&fetchId=42&groupId=7&resourceId=10
           &gCols=power,soc&rCols=power,soc,missing_data
           &start=13:00&end=13:30&sort=period:desc&drawer=detail
```

| 둘 것 (공유·복원 가치 있음) | 두지 말 것 |
|------|------|
| 탭, 선택한 엔티티(group/resource), 시간 범위 | 순수 UI 토글(collapse 펼침 여부) |
| 보이는 컬럼, 정렬, 페이지 | 순간적 hover/focus |
| 열린 드로어·활성 상세 | 서버에서 다시 받을 수 있는 원본 데이터 |
| 필터 조건 | 애니메이션 진행 상태 |

원칙: **"서버 데이터"는 URL이 아니라 [쿼리 캐시](./01-tanstack-query-cache-invalidation.md)에, "그 데이터를 어떻게 보고 있는가(뷰 상태)"는 URL에** 둔다. URL은 뷰의 좌표이지 데이터 저장소가 아니다.

## 3. 양방향 동기화 루프를 막는 법

URL ↔ 상태 동기화의 함정은 **무한 루프**다. `상태 변경 → URL 갱신 → URL watch → 상태 갱신 → URL 갱신 …`

```ts
// 상태 → URL
watch(viewState, (s) => router.replace({ query: serialize(s) }));
// URL → 상태 (복원)
watch(() => route.query, (q) => { viewState.value = parse(q); });
```

방어 전략:
- **`replace` vs `push`**: 필터 조작 같은 잦은 변경은 히스토리를 오염시키지 않도록 `router.replace`를 쓴다(뒤로가기가 필터 한 칸씩 되돌아가면 안 됨). "화면 전환"급만 `push`.
- **값 동등성 가드**: URL을 쓰기 전에 현재 query와 **깊은 비교**해 실제로 달라졌을 때만 `replace`. 같으면 skip → 루프 차단.
- **직렬화 정규화**: `parse(serialize(s))`가 안정적이어야(순서·타입) 불필요한 재갱신이 없다.
- **부작용 분리**: URL 동기화가 트리거하는 다른 전역 훅에 주의. 실제로 이 `router.replace`가 [전역 스크롤 리셋 훅](./06-scope-and-layering.md#1-opt-in-1회성-플래그-vs-전역-수정)을 건드려 드로어를 열 때마다 페이지가 최상단으로 튀는 버그가 있었다 — URL 동기화는 "조용한 상태 갱신"인데 라우터 훅은 "화면 전환"으로 취급한 탓.

## 4. 컨텍스트별 상태 분리

"그룹 모니터링"과 "자원 모니터링"은 컬럼 구성이 다르다. 처음엔 컬럼 가시성 상태를 하나로 공유했다가, 탭마다 독립적으로 유지되어야 한다는 요구가 나왔다.

```
# 하나로 공유 (문제: 탭 전환 시 서로 간섭)
?cols=power,soc

# 컨텍스트별 분리
?gCols=power,soc & rCols=power,soc,missing_data
```

- 상태를 `groupVisibleCols` / `resVisibleCols`로 쪼개고, 각 키 집합(`GROUP_KEYS`/`RESOURCE_KEYS`)을 분리.
- URL 파라미터도 `gCols`/`rCols`로 분리해 **두 뷰를 동시에 독립 유지**한다.
- 필터 UI 위치도 전역 상단이 아니라 각 탭 안(엔티티 선택기 아래)으로 옮겨 "이 필터가 어느 컨텍스트에 속하는지"를 시각적으로 명확히 했다.

교훈: 하나의 상태를 여러 컨텍스트가 공유하면 편해 보이지만, **컨텍스트가 실제로 다르면 상태도 키도 분리**하는 게 맞다. URL 설계가 곧 상태 설계다.

---

## 5. 기본값은 URL에 쓰지 않는다

모든 상태를 항상 URL에 박으면 URL이 길고 지저분해지고, "기본 상태"와 "사용자가 바꾼 상태"의 구분이 사라진다.

```ts
function serialize(state) {
  const q = {};
  if (state.cols !== ALL_COLS) q.cols = state.cols.join(','); // 기본(전체)이면 생략
  if (state.sort) q.sort = state.sort;
  if (state.start) q.start = state.start;
  return q;
}
```

- **기본값(예: "전체 보기")과 다를 때만** 파라미터를 추가한다.
- 빈 쿼리스트링 = 기본 상태로 복원. URL이 깨끗하고 의미가 명확해진다.
- 복원(`parse`)에선 없는 파라미터를 기본값으로 채운다.

## 6. 면접 포인트

**Q. 어떤 상태를 URL에 두고 어떤 걸 두지 않나요?**
> 공유·복원·북마크 가치가 있는 뷰 상태(탭, 필터, 정렬, 페이지, 선택 엔티티, 열린 드로어)는 URL에 둔다. 순수 UI 토글이나 순간적 상태, 그리고 서버에서 다시 받을 수 있는 원본 데이터는 두지 않는다. URL은 뷰의 좌표이지 데이터 저장소가 아니다.

**Q. URL과 상태를 양방향 동기화할 때 무한 루프를 어떻게 막나요?**
> 쓰기 전에 현재 query와 깊은 비교로 실제 변경 시에만 갱신하고, 직렬화를 정규화해 안정적으로 만든다. 잦은 필터 변경은 push 대신 replace로 히스토리 오염을 막는다.

**Q. `router.push`와 `router.replace`를 어떻게 나눠 쓰나요?**
> 화면 전환급 이동은 히스토리에 남겨야 하니 push, 필터·정렬 같은 조용한 상태 갱신은 뒤로가기가 한 칸씩 되돌아가면 안 되므로 replace를 쓴다. replace가 트리거하는 전역 라우터 훅(스크롤 리셋 등)이 의도치 않은 부작용을 내지 않는지도 확인해야 한다.

**Q. 여러 탭이 비슷한 상태를 가질 때 하나로 합칠까요?**
> 컨텍스트가 실제로 다르면(컬럼 구성이 다름 등) 상태도 URL 파라미터도 분리한다(gCols/rCols). 공유하면 탭 전환 시 서로 간섭한다. URL 설계가 곧 상태 설계라는 관점으로 접근한다.

**Q. 모든 상태를 항상 URL에 넣나요?**
> 아니다. 기본값과 다를 때만 파라미터를 추가한다. 그래야 URL이 깨끗하고, 빈 쿼리스트링이 곧 기본 상태라는 의미가 명확해진다.
