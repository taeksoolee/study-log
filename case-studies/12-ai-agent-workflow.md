# 12. AI 에이전트와 협업하는 개발 워크플로

> 실전 배경: 이 `case-studies` 섹션의 원천이 된 자료는, 한 프로덕션 SPA에서
> **작업마다 AI 에이전트와의 대화를 `ai-logs`로 남긴 기록**이었다. 이 문서는 개별 버그가 아니라,
> 그 로그들이 공통으로 보여준 **"AI와 일하는 방식" 자체**를 정리한다.

## 1. 작업 단위마다 결정 로그를 남긴다

각 작업이 끝나면 다음 4개 축으로 짧은 로그를 남긴다. 커밋 메시지나 PR 본문보다 **"왜 그렇게 판단했는가"**에 무게가 있다.

```markdown
## User Prompt (질문)     — 무엇을 요청받았나 (원문 인용)
## Modification Summary   — 무엇을 바꿨나 (파일·핵심 변경)
## Rationale (판단 근거)   — 왜 이 해법인가, 어떤 대안을 왜 버렸나
## Reviewer Notes         — 리뷰어가 알아야 할 트레이드오프·잔여 부채
```

가치:
- **판단의 재구성**: 3개월 뒤 "왜 이렇게 했지?"에 답이 남아 있다. 코드는 결과만, 로그는 이유를 담는다.
- **AI 세션의 연속성**: 다음 세션의 에이전트가 과거 결정을 컨텍스트로 이어받는다.
- **리뷰 효율**: 리뷰어가 diff만 보고 추측하지 않아도 된다.

> 이 문서 시리즈(01~11) 자체가 그 로그를 "학습 자료"로 재가공한 결과물이다. **좋은 결정 로그는 나중에 그대로 지식 베이스가 된다.**

---

## 2. 스코프를 먼저 합의하고 시작한다

로그의 도입부는 거의 항상 "무엇을 할지"와 "어디까지 할지"를 **먼저 정하는** 대화다.

- "origin/develop에서 베이스로 브랜치 하나 만들고 시작하자" — **베이스와 브랜치를 명시**.
- "이건 별도로 가는 게 낫겠지?" — **한 작업에 여러 관심사가 섞이면 분리**를 합의.
- "의견 먼저 줘봐" — 구현 전에 **접근을 먼저 검토**.

원칙: **에이전트에게 곧장 코드를 시키기 전에, 스코프·베이스·접근을 합의한다.** 넓게 고칠지 좁게 고칠지([문서 06](./06-scope-and-layering.md))도 이 단계에서 정한다. 스코프가 흐리면 에이전트는 과하게 고치거나 엉뚱한 걸 건드린다.

---

## 3. 추측하지 말고 실제로 확인한다

로그에서 반복되는 강력한 패턴: **가정을 코드에 반영하기 전에 실제로 관측한다.**

- API 파일명 규격을 "문서"가 아니라 **`curl`로 실응답을 확인**하고 파서를 고쳤다([문서 07](./07-content-disposition-file-download.md)).
- MCP가 안 붙던 원인을 추측으로 두 번 고치다 실패하자, **에디터 로그를 직접 읽어** 진짜 원인을 특정했다([문서 04](./04-shebang-node-path-mcp.md)).
- 목록 상태가 최종인지 확인하려고 **status API를 curl로 실측**했다([문서 01](./01-tanstack-query-cache-invalidation.md)).

원칙: **AI는 그럴듯한 추측을 잘하지만, 그럴듯함은 사실이 아니다.** 사람이 "실제 응답 봤어? 로그 확인했어?"로 관측을 요구하면 실패 루프를 끊을 수 있다. 두 번 같은 방식으로 실패했다면 접근을 바꾸고 근거를 확인한다.

## 4. 커밋을 의미 단위로 나눈다

"커밋 잘 나눠", "split commits" 같은 지시가 반복된다.

- 한 PR 안에서도 **논리적으로 독립된 변경은 별도 커밋**으로. 예: "RTO 필터 추가"와 "실시간 필터 제거"를 한 브랜치에서 두 커밋으로 분리.
- 리팩터링(동작 불변)과 기능 변경(동작 변경)을 **다른 커밋**으로.
- cosmetic 정리(`.clone()` 제거 등)를 기능 커밋에 섞지 않는다([문서 03](./03-moment-to-dayjs-migration.md)).

이유: 커밋이 의미 단위면 **리뷰·되돌리기·이분 탐색(bisect)**이 쉬워진다. [검출력 검증](./02-tests-that-catch-regressions.md)에서 "특정 변경만 되돌려 테스트가 깨지는지" 볼 때도 커밋이 잘 나뉘어 있어야 한다.

---

## 5. 리뷰 지적을 항목 단위로 반영한다

PR 리뷰 코멘트를 처리할 때, 로그는 **"[1번 반영]", "리뷰 항목 1·2·3 적용"**처럼 항목 단위로 대응하고 그 사실을 PR에 코멘트로 남긴다.

- 각 지적사항을 **번호로 추적**하고, 반영/보류/이견을 각각 표시.
- 보류하는 항목은 **왜 보류하는지**를 남긴다(예: "이 enum 이동은 범위 밖, FIXME로 표시").
- 반영 후 **PR에 회신 코멘트**를 달아 리뷰어가 다시 추측하지 않게 한다.

원칙: 리뷰는 "다 고쳤어요"가 아니라 **"n번은 이렇게, m번은 이래서 보류"**로 항목별 폐루프(closed loop)를 만든다.

---

## 6. 형식 변경과 내용 변경을 섞지 않는다

주석 형식을 전역 통일하는 작업에서, 사용자는 명시적으로 **"작업 기조를 주석 내용 말고 형식 변경만으로 가자"**고 못박았다.

- 33개 파일의 주석 **형식**(`//` ↔ `/** */`, prefix 규칙)만 바꾸고 **본문 문구는 그대로** 유지.
- 주석 처리된 코드는 건드리지 않음(의도적 보존).
- prefix 없는 3000여 일반 주석은 "내용 판단이 필요하므로" **이번 범위에서 제외**.

원칙: **한 작업은 한 종류의 변경만.** 형식(포맷)과 내용(로직·문구)을 섞으면 diff가 오염되어 리뷰어가 "이게 단순 포맷인지 의미 변경인지" 구분할 수 없다. 이는 [문서 11의 alias 마이그레이션](./11-path-alias-migration.md)에서 "치환 + 자동 정렬"만으로 diff를 구성한 것과 같은 사고다.

## 7. 체크리스트

AI 에이전트와 작업할 때 사람이 챙길 것:

- [ ] **시작 전**: 베이스 브랜치·스코프·접근을 합의했는가? 여러 관심사면 분리했는가?
- [ ] **판단 시**: 추측이 아니라 실제 관측(curl·로그·실행)에 근거하는가?
- [ ] **실패 시**: 같은 방식으로 두 번 실패했다면 접근을 바꿨는가?
- [ ] **커밋**: 의미 단위로 나뉘었는가? 형식/내용, 리팩터링/기능이 섞이지 않았는가?
- [ ] **검증**: 타입·린트·테스트를 돌렸는가? 회귀를 실제로 잡는지 확인했는가?
- [ ] **기록**: 요청·수정·판단근거·트레이드오프를 로그로 남겼는가?
- [ ] **리뷰**: 지적사항을 항목별로 반영/보류하고 그 사유를 남겼는가?

> 핵심은 **에이전트에게 위임하되 판단의 고삐는 사람이 쥔다**는 것. AI는 빠른 구현과 그럴듯한 초안을 주지만, 스코프 결정·사실 확인·검증 요구·기록은 사람이 주도할 때 품질이 유지된다.
