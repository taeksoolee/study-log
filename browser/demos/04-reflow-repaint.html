Reflow vs Repaint 비교 데모

브라우저 렌더링 성능의 핵심 개념인 Reflow와 Repaint를 버튼 클릭으로 직접 체험하고, 각 작업이 왜 발생하는지 성능 타이밍과 함께 확인해 보세요.

Reflow = Layout 재계산 Repaint = 픽셀 재그리기 Transform = GPU 합성

Reflow (레이아웃 재계산)

DOM 요소의 기하학적 속성(크기, 위치, 여백 등)이 바뀌면 브라우저는 영향 받는 모든 요소의 위치·크기를 다시 계산합니다. 이 작업은 CPU 집약적이며, 변경된 요소의 부모·자식·형제까지 전파될 수 있어 비용이 큽니다. 반드시 Repaint도 뒤따릅니다.

Repaint (픽셀 재그리기)

요소의 시각적 스타일(색상, 배경, 그림자 등)이 바뀌었지만 기하학적 속성은 변하지 않을 때 발생합니다. Layout 단계를 건너뛰고 Paint 단계부터 실행하므로 Reflow보다 비용이 낮습니다. 단, opacity·transform은 GPU 합성 레이어를 사용해 Repaint도 생략 가능합니다.

최적화 비교
Reflow를 줄이는 실전 패턴들을 코드와 함께 비교해 보세요.
패턴 1 — DOM 읽기/쓰기 분리
❌ 나쁜 패턴 (읽기/쓰기 혼합)
// 읽기 → 쓰기 → 읽기 → 쓰기 // 매번 강제 Reflow 발생! const h1 = el1.offsetHeight; // 읽기 el1.style.height = h1 + 'px'; // 쓰기 → dirty const h2 = el2.offsetHeight; // 읽기 → 강제 Reflow! el2.style.height = h2 + 'px'; // 쓰기 → dirty
브라우저는 쓰기 후 layout을 "dirty"로 표시하고 지연합니다. 그런데 읽기(offsetHeight)를 하면 즉시 강제로 Reflow를 수행해야 합니다. 읽기·쓰기가 교차될수록 Reflow 횟수가 늘어납니다.
✅ 좋은 패턴 (읽기 먼저, 쓰기 나중)
// 읽기를 모두 먼저 수행 const h1 = el1.offsetHeight; // 읽기 const h2 = el2.offsetHeight; // 읽기 (Reflow 1회) // 쓰기를 한꺼번에 수행 el1.style.height = h1 + 'px'; // 쓰기 el2.style.height = h2 + 'px'; // 쓰기
모든 읽기를 먼저 수행하면 Reflow는 한 번만 발생합니다. 쓰기는 layout을 다시 dirty로 만들지만, 다음 frame에 한꺼번에 처리되어 성능이 크게 향상됩니다.
패턴 2 — top/left 이동 vs transform 이동
❌ 나쁜 패턴 (top / left)
// position + top/left 변경 // Layout 재계산 → Reflow 발생 el.style.top = x + 'px'; el.style.left = y + 'px';
top/left는 기하학적 속성이므로 변경 시 Reflow가 발생하고 주변 요소의 layout도 영향 받을 수 있습니다.
✅ 좋은 패턴 (transform)
// transform: translate 사용 // GPU 합성 레이어 → Reflow 없음! el.style.transform = `translate(${x}px, ${y}px)`;
transform은 합성(Compositing) 단계만 거쳐 GPU에서 처리됩니다. Layout과 Paint를 건너뛰어 60fps 애니메이션이 가능합니다.
