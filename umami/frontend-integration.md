# 프런트엔드(SPA) 연동 & 로그인 트래킹 설계

> **서버 셋업과는 다른 단계의 작업.** 방향과 결정 필요 사항만 기록해 둔다.
> 서버 셋업은 [README.md](./README.md) 참고.

Umami 서버가 떠 있는 상태에서, 프런트엔드 SPA(예: Vue 3)에 트래킹을 붙이는 작업의
설계 메모다. (React Router 등 다른 SPA 프레임워크도 원리는 동일하다.)

## 기본 트래킹

- Umami 에서 Website 등록 후 나오는 트래커 스니펫을 프런트엔드에 심는다.
  (`data-website-id` + 트래커 스크립트)
- **SPA** 는 기본 스크립트만으로는 최초 진입만 잡힌다.
  라우트 전환 추적은 라우터의 전환 훅(예: **Vue Router `afterEach`**, React Router
  라우트 변경 감지)에서 `umami.track()` 을 호출해 가상 페이지뷰를 보내는 방식으로 보완한다.
- 로드 여부는 아래 [환경별 적용 정책](#환경별-적용-정책)을 따른다. 광고 차단 회피가
  필요하면 서버 쪽 `TRACKER_SCRIPT_NAME` 으로 스크립트명을 바꾼다.

## 환경별 적용 정책

배포 환경이 prod / staging / dev 로 나뉜다면 전부 붙이지 않는다 —
non-prod 접속은 개발·QA 인원의 **내부 트래픽(노이즈)**이라 prod 통계에 섞이면 안 된다.
(셀프호스팅이라 website 여러 개 만드는 비용은 없다. 판단 기준은 비용이 아니라
**데이터 청결성**이다.)

| 환경 | 처리 | website-id |
| --- | --- | --- |
| **prod** | 실제 수집 | 부여 (실데이터) |
| **staging** | (선택) prod 배포 전 연동 검증용. 필요 없으면 off | prod 와 **분리된 별도 id** |
| **dev** | off | 없음 |

핵심 구현은 **"website-id 를 환경변수로 주입하고, 값이 없으면 트래커를 아예 로드하지
않는다"** 하나다. 이러면 붙일 환경만 골라 값을 주고, 나머지는 자동으로 off 된다.

```
VITE_UMAMI_SRC=<트래커 스크립트 URL>       # 없으면 로드 안 함
VITE_UMAMI_WEBSITE_ID=<환경별 website-id>  # 없으면 로드 안 함
```

- **staging 은 반드시 prod 와 다른 website-id** 로 분리한다. 그래야 검증 트래픽이
  prod 대시보드를 오염시키지 않는다.
- **로컬/e2e 는 별도 처리 불필요.** e2e(예: Playwright)가 로컬 dev 서버를 대상으로
  격리 실행된다면 위 env gate 만으로 자동 off 된다. (로컬엔 website-id 를 주지 않음)

## 로그인 연동 (설계 더 필요)

로그인 성공 시점(인증 스토어의 로그인 성공 지점)에 훅을 걸어 세션에 사용자
식별자를 붙이는 방식을 검토한다. 두 갈래:

1. **`umami.identify({...})`**
   - `userId` / `role` 같은 내부 식별자를 세션에 연결.
   - 로그인 유저 기준 분석이 가능해진다.
   - ⚠️ **PII 를 Umami DB 에 저장하는 셈**이므로 넣을 값 선정에 주의.
     이메일 등 raw PII 대신 **내부 id/해시** 권장.
2. **커스텀 이벤트만**
   - `login` / `logout` 이벤트만 전송하고 개인 식별은 하지 않음 (privacy-safe).
   - 어느 유저인지까지는 필요 없을 때.

### 다음 작업에서 확정할 것

- 식별자로 무엇을 보낼지 (PII 최소화 정책)
- 로그아웃 시 identify 초기화 처리
- 인증 스토어 구조에 맞는 훅 위치
