## 1. 칸반이란 무엇인가

칸반(Kanban)은 일본어로 "신호 카드"를 뜻하며, 도요타의 린(Lean) 생산 방식에서 유래했습니다. 소프트웨어 개발에서는 2007년 David Anderson이 IT 분야에 적용하면서 널리 알려졌습니다.

```
핵심 철학: "흐름을 시각화하고, 병목을 제거하고, 지속적으로 개선한다"

워터폴: 단계별로 한 번에 모든 작업을 처리
스크럼:  스프린트 단위로 묶어서 처리
칸반:    흐름(flow)을 연속적으로 최적화
```

칸반은 프레임워크가 아닌 **방법론**입니다. 기존 프로세스에 점진적으로 적용할 수 있습니다.

## 2. 칸반의 4가지 핵심 원칙

### 원칙 1: 흐름 시각화 (Visualize the Workflow)

```
작업의 상태를 보드에 시각적으로 나타냄

보이지 않으면 관리할 수 없다:
  - 현재 어떤 작업이 진행 중인가?
  - 어디서 작업이 멈춰 있는가?
  - 팀원별 작업 부하는 어떤가?
```

### 원칙 2: WIP 제한 (Limit Work In Progress)

```
동시에 진행하는 작업 수를 제한

멀티태스킹의 함정:
  한 번에 1개 작업: 생산성 100%
  한 번에 2개 작업: 각 80% → 총 160% (전환 비용 20%)
  한 번에 3개 작업: 각 60% → 총 180% (전환 비용 40%)

실제로는 전환 비용이 누적될수록 전체 처리량이 감소한다.
```

### 원칙 3: 흐름 관리 (Manage Flow)

```
작업이 빠르고 원활하게 흐르도록 관리

흐름 지표:
  - 처리량(Throughput): 단위 시간당 완료 항목 수
  - 리드 타임: 요청부터 완료까지 소요 시간
  - 사이클 타임: 작업 착수부터 완료까지 소요 시간
```

### 원칙 4: 지속적 개선 (Continuous Improvement)

```
작은 변화를 실험하고 결과를 측정하며 반복

카이젠(Kaizen) 원칙:
  현재 상태 측정 → 개선 실험 → 결과 측정 → 표준화 또는 폐기
```

## 3. 칸반 보드 구성

### 기본 보드 구조

```
┌──────────┬──────────┬──────────────┬──────────┬──────────┐
│ Backlog  │   Todo   │ In Progress  │  Review  │   Done   │
│          │  (WIP≤5) │   (WIP≤3)    │  (WIP≤2) │          │
├──────────┼──────────┼──────────────┼──────────┼──────────┤
│ 다크모드  │ 알림센터  │ ● 결제연동   │ ◎ 검색   │ ✓ 로그인  │
│ PWA지원  │ 마이페이지│ ● 장바구니   │          │ ✓ 회원가입│
│ 리뷰기능 │          │              │          │ ✓ 상품목록│
│ ...      │          │              │          │ ...       │
└──────────┴──────────┴──────────────┴──────────┴──────────┘

● = 진행 중  ◎ = 블록됨  ✓ = 완료
```

### 수영 레인 (Swimlane)

```
작업 유형별로 레인을 분리해 가시성을 높임

┌────────────┬──────────┬──────────────┬──────────┬──────────┐
│   유형     │   Todo   │ In Progress  │  Review  │   Done   │
├────────────┼──────────┼──────────────┼──────────┼──────────┤
│ 기능개발   │ 결제연동  │ 로그인 개선   │          │ 회원가입  │
├────────────┼──────────┼──────────────┼──────────┼──────────┤
│ 버그       │ 결제오류  │              │ 로딩오류  │          │
├────────────┼──────────┼──────────────┼──────────┼──────────┤
│ 긴급 (🔥)  │          │ 서버장애대응  │          │          │
└────────────┴──────────┴──────────────┴──────────┴──────────┘
```

### 서비스 클래스 (Class of Service)

```typescript

  createdAt: new Date('2024-01-15'),
};
```

## 4. WIP 제한의 중요성

### 리틀의 법칙 (Little's Law)

```
리드 타임 = WIP / 처리량

예시:
  팀 처리량: 하루 2개 항목 완료
  현재 WIP: 10개

  평균 리드 타임 = 10 / 2 = 5일

WIP를 6개로 줄이면:
  평균 리드 타임 = 6 / 2 = 3일 (40% 단축!)
```

### WIP 제한 설정 방법

```
초기 설정 권장:
  In Progress WIP = 팀원 수 × 1.5 (한 명당 1~2개 작업)
  Review WIP = 팀원 수 × 0.5

실험적 조정:
  - WIP가 자주 최대치에 달하면 → 병목 발생, 근본 원인 해결
  - WIP가 항상 낮으면 → 더 줄여서 흐름 개선 가능
```

### WIP 초과 시 처리

```
규칙: WIP 제한 도달 시 새 작업을 시작하지 않고
      기존 작업 완료를 돕거나 블로커를 제거한다.

실천:
  "Stop Starting, Start Finishing"
  시작을 멈추고, 완료에 집중하라
```

## 5. 리드 타임 vs 사이클 타임

```
요청 접수                  작업 착수                    완료
    │                          │                          │
    ├──────────────────────────┼──────────────────────────┤
    │         리드 타임                                   │
    │                          │       사이클 타임        │
    │<────────────────────────────────────────────────────>
    │<─────────────────────────><─────────────────────────>
    
    대기 시간                    실제 처리 시간
```

### 실무 해석

```
리드 타임 (고객 관점):
  "내가 요청했을 때부터 받을 때까지 얼마나 걸리나?"
  → SLA(서비스 수준 협약) 기준
  → 예측 가능성의 핵심 지표

사이클 타임 (팀 관점):
  "실제로 작업에 손댔을 때부터 완료까지 얼마나 걸리나?"
  → 팀의 실제 역량 측정
  → 프로세스 효율성 지표

리드 타임 >> 사이클 타임 이라면?
  → 대기 시간이 길다 = 우선순위 문제 또는 팀 과부하
```

### 퍼센타일 분석

```
사이클 타임 분포 예시 (지난 30개 항목):

  50% (중간값): 3일  → 절반의 작업이 3일 이내 완료
  85% 퍼센타일: 7일  → 85% 작업이 7일 이내 완료
  95% 퍼센타일: 14일 → 예외적으로 오래 걸리는 작업

실무 활용:
  "이 작업은 85% 확률로 7일 이내 완료됩니다."
  → 확률적 예측으로 현실적인 기대치 관리
```

## 6. 누적 흐름 다이어그램 (CFD)

### CFD 구조

```
항목    ↑
수      │▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  Done
        │▓▒▒▒▒▒▒▒▒▒▒▒▒▒▒▓  Review
        │▓▒░░░░░░░░░░░░▒▓  In Progress
        │▓▒░▤▤▤▤▤▤▤▤░▒▓  Todo
        │▓▒░▤·········▤░▒▓  Backlog
        └─────────────────────→ 날짜
          1주  2주  3주  4주

수평 거리 = 리드 타임
수직 거리 = WIP
기울기    = 처리량
```

### CFD 이상 패턴 읽기

```
정상 패턴:
  띠(band)가 균일하게 우상향 → 안정적 흐름

이상 패턴 1 - In Progress 띠가 두꺼워짐:
  → 완료되는 것보다 시작되는 것이 많다
  → WIP 한도 초과, 병목 발생

이상 패턴 2 - 특정 컬럼에서 띠가 멈춤:
  → 해당 단계에서 블로커 발생 (코드리뷰 지연 등)

이상 패턴 3 - 계단식 패턴:
  → 배치 처리 중 (한꺼번에 여러 항목 이동)
  → 작은 단위로 분할 필요
```

## 7. 칸반 vs 스크럼 비교

| 구분 | 칸반 | 스크럼 |
|------|------|--------|
| 반복 주기 | 연속적 흐름 (이터레이션 없음) | 고정 스프린트 (1~4주) |
| 역할 정의 | 없음 (선택 사항) | PO, SM, Dev 팀 필수 |
| 계획 회의 | 필요시 수시 | 스프린트 시작 시 |
| 변경 허용 | 언제든 가능 | 스프린트 중 지양 |
| WIP 제한 | 컬럼별 명시적 제한 | 암묵적 (스프린트 용량) |
| 진행 지표 | 리드타임, CFD | 번다운 차트, 벨로시티 |
| 회고 주기 | 필요시 (정해진 주기 없음) | 스프린트마다 의무 |
| 릴리즈 | 준비되면 즉시 | 스프린트 종료 시 |
| 팀 규모 | 유연 | 3~9명 권장 |
| 적합한 상황 | 운영, 유지보수, 지원 | 신규 기능 개발 |

### 스크럼반 (Scrumban)

```
스크럼 + 칸반의 하이브리드

채택 방식:
  - 스크럼의 스프린트 리뷰/회고 유지
  - 칸반의 WIP 제한과 지속적 흐름 적용
  - 스탠드업은 유지하되 시간 제한 엄수

적합한 상황:
  - 스크럼에서 칸반으로 전환 중인 팀
  - 기능 개발 + 운영 지원을 동시에 하는 팀
```

## 8. 개발팀에서의 실용적 활용

### GitHub Issues + 칸반 연동

```yaml
# .github/workflows/kanban-automation.yml
name: Kanban Automation

on:
  pull_request:
    types: [opened, closed]
  issues:
    types: [opened, assigned]

jobs:
  move-card:
    runs-on: ubuntu-latest
    steps:
      - name: Move to In Progress when PR opened
        uses: actions/github-script@v7
        with:
          script: |
            // PR 생성 시 연결된 이슈를 In Progress로 이동
            const issue = context.payload.pull_request;
            // GitHub Projects API로 카드 이동
            console.log(`Moving issue to In Progress: ${issue.title}`);
```

### 칸반 메트릭 수집

```typescript
// 사이클 타임 계산 예시
interface KanbanTicket {
  id: string;
  title: string;
  createdAt: Date;      // Backlog 진입 시점
  startedAt: Date;      // In Progress 진입 시점
  completedAt: Date;    // Done 진입 시점
}

function calculateMetrics(tickets: KanbanTicket[]) {
  const metrics = tickets.map(ticket => ({
    id: ticket.id,
    leadTime: daysBetween(ticket.createdAt, ticket.completedAt),
    cycleTime: daysBetween(ticket.startedAt, ticket.completedAt),
    waitTime: daysBetween(ticket.createdAt, ticket.startedAt),
  }));

  const avgCycleTime =
    metrics.reduce((sum, m) => sum + m.cycleTime, 0) / metrics.length;

  const p85CycleTime = percentile(
    metrics.map(m => m.cycleTime),
    85
  );

  return { avgCycleTime, p85CycleTime };
}

function daysBetween(start: Date, end: Date): number {
  return Math.floor((end.getTime() - start.getTime()) / (1000 * 60 * 60 * 24));
}

function percentile(values: number[], p: number): number {
  const sorted = [...values].sort((a, b) => a - b);
  const index = Math.ceil((p / 100) * sorted.length) - 1;
  return sorted[index];
}
```

### 칸반 회의 (선택 사항)

```
칸반 데일리 스탠드업 (우측에서 좌측으로):
  1. Done: 어제 완료된 항목 확인
  2. Review: 리뷰 대기 중인 항목 확인 (블로커?)
  3. In Progress: 진행 중 항목 확인 (도움 필요?)
  4. Blocked: 블록된 항목 해결 방안 논의

보드를 보드처럼 활용:
  사람이 아닌 카드 기준으로 진행 → 흐름 중심 사고
```

## 9. 면접 포인트

**Q. WIP 제한을 왜 설정해야 하나요?**

WIP 제한은 리틀의 법칙(리드 타임 = WIP / 처리량)에 근거합니다. 동시 진행 작업이 많아지면 컨텍스트 스위칭 비용이 증가하고, 각 작업의 완료까지 걸리는 시간이 늘어납니다. WIP를 제한하면 작업의 완료에 집중하게 되어 전체 처리량이 오히려 증가합니다. 또한 WIP 제한이 달성되는 순간이 병목 지점을 시각화하는 신호가 됩니다.

**Q. 리드 타임과 사이클 타임의 차이를 설명해주세요.**

리드 타임은 고객이 작업을 요청한 시점부터 완료까지의 전체 시간으로, 고객이 체감하는 응답 시간입니다. 사이클 타임은 팀이 실제로 작업을 시작한 시점부터 완료까지의 시간입니다. 두 지표의 차이가 대기 시간이며, 이 차이가 크다면 우선순위 결정 또는 팀 과부하 문제를 의심할 수 있습니다.

**Q. 스크럼을 사용하다가 칸반으로 전환하는 적절한 상황은 언제인가요?**

신규 기능 개발이 안정화되고 운영/유지보수 비중이 높아질 때, 또는 요청이 불규칙하게 들어와 스프린트 계획이 자주 틀어질 때 전환을 고려합니다. 스크럼은 예측 가능한 환경에서 효과적이고, 칸반은 가변적인 우선순위와 연속적인 납품이 필요한 환경에서 유리합니다.

**Q. 누적 흐름 다이어그램(CFD)에서 무엇을 읽을 수 있나요?**

CFD에서 수평 거리는 리드 타임, 수직 거리는 WIP, 각 띠의 기울기는 처리량을 나타냅니다. In Progress 띠가 두꺼워지면 완료보다 시작이 많은 것이고, 특정 컬럼에서 띠가 평탄해지면 해당 단계에 병목이 있다는 신호입니다.
