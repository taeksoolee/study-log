## 1. 회고가 중요한 이유

### 피드백 루프와 지속적 개선

```
회고 없는 팀:
  스프린트 1: 같은 실수
  스프린트 2: 같은 실수
  스프린트 3: 같은 실수 ...

회고 있는 팀:
  스프린트 1: 실수 발생
  회고: 원인 파악, 개선 실험 정의
  스프린트 2: 개선 적용 → 점진적 성장

복리 효과: 매 스프린트 1%씩 개선 → 1년 후 26배 차이
```

### 애자일 선언문과 회고

```
애자일 12원칙 중 12번:
  "팀은 정기적으로 더 효과적인 방법을 반성하고
   그에 따라 행동을 조정한다"

회고의 초점: 결과물(product)이 아닌 프로세스(process)
  → "무엇을 만들었나?"가 아닌 "어떻게 일했나?"
```

### 회고의 황금 규칙

```
Norm Kerth의 회고 프라임 디렉티브:
  "각자의 지식, 기술, 가용한 자원, 주어진 상황에서
   모든 팀원이 최선을 다했음을 믿는다"

→ 회고는 비난의 자리가 아닌 학습의 자리
→ 사람이 아닌 시스템과 프로세스를 개선
```

## 2. KPT (Keep / Problem / Try)

```
가장 널리 쓰이는 회고 기법. 단순하고 직관적.

┌──────────────────────────────────────────────┐
│  Keep          │  Problem                    │
│  잘 됐으니      │  문제가 됐던 것             │
│  계속할 것      │  (원인 분석 포함)            │
├──────────────────────────────────────────────┤
│  Try                                         │
│  다음에 시도할 개선책                         │
│  (Problem의 해결책 + 새로운 시도)             │
└──────────────────────────────────────────────┘
```

### KPT 진행 절차

```
1. 개인 작성 (5~10분): 포스트잇에 익명으로 작성
2. 공유 (10~15분):     돌아가며 붙이고 그룹화
3. 토론 (15~20분):     Problem의 근본 원인 파악
4. Action Item 도출:   Try 중 실행 항목 선정 + 담당자/기한 지정
5. 이전 Action Item 리뷰: 지난 회고의 Try가 실행됐는지 확인

⚠️ 흔한 실수: Try가 실행 불가능하거나 담당자 없이 끝나는 것
```

### KPT 예시

```
Keep:
  + 매일 오전 30분 팀 코어 타임이 집중도를 높였다
  + PR 템플릿 도입으로 리뷰 시간이 줄었다

Problem:
  - QA 환경 배포가 느려서 개발 사이클이 늘어남 (원인: 수동 배포)
  - 백엔드 API 스펙 변경이 공유되지 않아 프론트엔드가 뒤늦게 알게 됨

Try:
  - QA 배포 자동화 (GitHub Actions) 도입 → 담당: 김철수, 기한: 2주
  - 백엔드 API 변경 시 슬랙 #frontend-notify 채널에 공지 → 즉시 적용
```

## 3. 4Ls (Liked / Learned / Lacked / Longed For)

```
감정과 학습에 더 집중하는 기법. 새로운 팀이나 프로젝트 마무리에 적합.

┌───────────────────┬───────────────────┐
│  Liked            │  Learned          │
│  좋았던 점        │  배운 것          │
│  (긍정적 경험)    │  (기술/프로세스)  │
├───────────────────┼───────────────────┤
│  Lacked           │  Longed For       │
│  부족했던 점      │  앞으로 원하는 것 │
│  (개선 필요)      │  (미래 바람)      │
└───────────────────┴───────────────────┘
```

### KPT vs 4Ls 선택 기준

```
KPT 선택:
  - 빠른 액션 중심의 회고
  - 정기적인 스프린트 회고 (반복 가능)
  - 팀이 회고에 익숙한 경우

4Ls 선택:
  - 감정과 경험에 더 깊이 파고들고 싶을 때
  - 프로젝트 완료 후 마무리 회고
  - 새로운 팀원이 많아 관계 형성이 필요한 경우
  - 팀 분위기가 딱딱하고 회고 참여도가 낮은 경우
```

## 4. Start / Stop / Continue

```
3개 질문으로 명확한 행동 변화에 집중

┌──────────────────────────────────────────────┐
│  Start                                       │
│  "지금 안 하지만 해야 할 것"                 │
│  새로운 시도, 도입할 도구나 프랙티스          │
├──────────────────────────────────────────────┤
│  Stop                                        │
│  "지금 하지만 그만해야 할 것"                │
│  비효율적 관행, 낭비되는 시간                │
├──────────────────────────────────────────────┤
│  Continue                                    │
│  "잘 되고 있으니 계속할 것"                  │
│  효과가 검증된 프랙티스                      │
└──────────────────────────────────────────────┘
```

### 예시

```
Start:
  - PR 설명에 스크린샷 또는 영상 첨부 (시각적 리뷰)
  - 매주 금요일 팀 기술 공유 30분 도입

Stop:
  - 스탠드업에서 세부 기술 토론 (15분 넘어가는 것)
  - 기능 완성 전 리뷰 요청 (Draft PR 활용)

Continue:
  - 스프린트 시작 전 백로그 정리 시간
  - 모르는 내용 질문을 두려워하지 않는 팀 문화
```

## 5. 피드백 레이더 (팀 역량 레이더 차트)

```
팀의 여러 역량 영역을 점수로 평가해 레이더 차트로 시각화

평가 축 예시 (팀이 정의):
  - 코드 품질 (테스트 커버리지, 리뷰 문화)
  - 협업/소통 (스탠드업, 문서화)
  - 기술 역량 (학습, 새로운 기술 도입)
  - 배포 안정성 (CI/CD, 장애 대응)
  - 사용자 중심 (요구사항 이해, UX 감수성)
  - 계획/예측 (스프린트 완료율, 추정 정확도)

                코드 품질
                   5 ★
                4 / \
              3/     \3
  계획/예측  /  현재  \  협업
         2/    상태    \4
          \            /
        2  \          / 4
  배포       \        /   기술
  안정성      \      /    역량
               \    /
             사용자중심
                  3
```

### 레이더 활용법

```
1. 개인 점수 작성 (1~5점, 익명)
2. 팀 평균 계산
3. 가장 낮은 영역 2~3개 집중 토론
4. 개선 목표 설정 (다음 분기 목표 점수)
5. 분기마다 재측정 → 변화 추적

주의: 팀 간 비교보다 팀 내 시간 흐름에 따른 변화에 집중
```

## 6. Fun / Done / Learn 보드

```

에너지가 낮은 팀 또는 번아웃 징후가 있는 팀에 효과적

┌──────────────────────────────────────────────┐
│  Fun                                         │
│  "이번 스프린트에서 즐거웠던 순간"            │
│  팀 분위기, 성취감, 협력했던 순간            │

│  Done                                        │
│  "실제로 완료한 것들"                        │

├──────────────────────────────────────────────┤

│  "새롭게 배운 것"                            │
│  기술, 도메인, 협업 방식 등                  │
└──────────────────────────────────────────────┘
```

## 7. 건강한 회고 문화 만들기

### 심리적 안전감 (Psychological Safety)

```
구글의 Project Aristotle (2016):
  팀 성과를 결정하는 5가지 요소 중 1위 = 심리적 안전감

심리적 안전감이란:
  "실수, 의견, 질문이 비난받지 않을 것이라는 믿음"

팀에서 심리적 안전감이 낮으면:
  → 회고에서 진짜 문제가 나오지 않음
  → "다 괜찮았어요"만 반복됨
  → 가장 목소리 큰 사람의 의견만 남음
```

### 심리적 안전감을 높이는 방법

```
1. 퍼실리테이터가 먼저 취약성을 드러낸다
   "저도 이번에 이 부분에서 실수했어요..."

2. 익명 채널을 만든다
   포스트잇, 익명 설문, Mentimeter 등

3. 비난이 아닌 질문으로 전환한다
   "왜 그랬어?" → "어떤 상황이었어? 무엇이 도움이 됐을까?"

4. 과거 회고의 Action Item이 실제로 실행됐는지 확인한다
   → 실행 없는 회고 반복 = 신뢰 하락

5. 리더/매니저는 회고에서 평가자가 되지 않는다
```

### 회고의 안티패턴

```
❌ 개인 비난 ("누가 이걸 늦게 했어서...")
❌ Problem만 잔뜩, Action Item 없음
❌ 같은 문제가 매번 반복됨 (실행 없음)
❌ 퍼실리테이터가 자신의 의견을 강하게 밀어붙임
❌ 회고가 끝나도 아무것도 안 바뀜
❌ 30분 안에 끝내려고 표면만 훑음
```

## 8. 회고 퍼실리테이터 역할

```
퍼실리테이터(Facilitator): 회고가 효과적으로 진행되도록 돕는 사람
→ 보통 스크럼 마스터 또는 팀에서 순번으로 담당
```

### 회고 진행 5단계 (Derby & Larsen)

```
1. Set the Stage (장 설정, 5~10분)
   목적: 참여자가 편안하게 말할 수 있는 분위기 조성
   방법: 체크인 질문 ("지금 기분을 날씨로 표현하면?")

2. Gather Data (데이터 수집, 10~15분)
   목적: 객관적 사실과 주관적 감정 모두 수집
   방법: 포스트잇, 타임라인, 감정 그래프

3. Generate Insights (인사이트 도출, 15~20분)
   목적: 원인 분석과 패턴 파악
   방법: 5 Whys, 피시본 다이어그램

4. Decide What to Do (액션 결정, 10~15분)
   목적: 실행 가능한 개선 사항 선정
   방법: 투표(도트 보팅), 아이젠하워 매트릭스

5. Close the Retrospective (마무리, 5분)
   목적: 회고 자체에 대한 피드백
   방법: "이번 회고는 어떠셨나요?" (회고의 회고)
```

### 효과적인 Action Item 작성

```typescript
// 나쁜 Action Item
const badActionItem = {
  description: "코드 리뷰를 더 잘 하자",
  owner: "모두",
  deadline: "언젠가",
};

// 좋은 Action Item
const goodActionItem = {
  description: "PR 리뷰 응답 시간을 24시간 이내로 줄인다",
  owner: "김철수 (팀 전체 모니터링)",
  deadline: "다음 스프린트부터",
  successCriteria: "GitHub PR 리뷰 응답 시간 메트릭 측정",
  howToTrack: "다음 회고에서 실제 응답 시간 공유",
};
```

## 9. 면접 포인트

**Q. 팀 회고를 진행해본 경험이 있나요? 어떤 방식을 사용했나요?**

KPT 기법을 주로 사용했습니다. 포스트잇에 익명으로 작성 후 그룹화하는 방식으로 심리적 부담을 줄였습니다. 중요했던 것은 회고 자체보다 Action Item의 실행 여부였습니다. 이전 회고에서 정한 개선 사항을 다음 회고 시작 시 먼저 확인하는 습관이 팀의 신뢰를 높이는 데 도움이 됐습니다.

**Q. 심리적 안전감이 팀 회고에서 왜 중요한가요?**

회고의 핵심은 팀이 진짜 문제를 솔직하게 꺼낼 수 있어야 한다는 것입니다. 심리적 안전감이 낮으면 표면적인 이야기만 나오고, 실제 문제는 숨겨집니다. Google의 Project Aristotle 연구에서 팀 성과의 가장 중요한 요소가 심리적 안전감임이 밝혀진 것처럼, 회고를 비난이 아닌 학습의 장으로 만드는 것이 본질입니다.

**Q. KPT와 Start/Stop/Continue의 차이는?**

KPT는 현재 상태를 평가하고 개선점을 찾는 데 집중하며, Problem의 원인 분석이 자연스럽게 포함됩니다. Start/Stop/Continue는 행동 변화에 더 직접적으로 집중하여, "무엇을 새로 시작하고 무엇을 그만할지"를 명확히 합니다. 회고가 처음인 팀이나 액션 지향적인 팀에는 Start/Stop/Continue가 더 직관적이고, 깊은 분석이 필요한 팀에는 KPT가 적합합니다.

**Q. 매번 같은 문제가 회고에서 나온다면 어떻게 하시겠어요?**

이는 Action Item이 실행되지 않는다는 신호입니다. 먼저 Action Item이 왜 실행되지 않는지 파악합니다. 담당자가 불명확하거나, 범위가 너무 크거나, 우선순위가 낮았을 수 있습니다. 해결책으로는 Action Item을 더 작고 구체적으로 만들고, 스프린트 백로그에 공식 항목으로 포함시키며, 다음 회고 시작 시 항상 이전 Action Item부터 리뷰하는 루틴을 만드는 것입니다.
