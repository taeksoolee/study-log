## 1. 애자일이란 무엇인가

애자일(Agile)은 2001년 17명의 개발자들이 유타주 스노버드에서 작성한 **애자일 소프트웨어 개발 선언문**에서 시작된 소프트웨어 개발 철학입니다.

```
전통적 방법론 (워터폴):
요구사항 분석 → 설계 → 구현 → 테스트 → 배포 (선형, 몇 달~몇 년)

애자일:
[계획 → 개발 → 테스트 → 배포 → 피드백] → [반복] → [반복] (2~4주 단위)
```

핵심 가치: **불확실성을 인정하고, 빠른 피드백으로 방향을 수정한다.**

## 2. 애자일 선언문 4가지 가치

```
우리는 소프트웨어 개발 더 나은 방법을 찾고 있다.
이를 통해 우리는 다음 가치를 발견했다:

1. 프로세스와 도구보다  →  개인과 상호작용
2. 포괄적인 문서보다   →  동작하는 소프트웨어
3. 계약 협상보다       →  고객과의 협력
4. 계획을 따르기보다  →  변화에 대응하기
```

좌측도 가치가 있지만, **우측에 더 높은 가치를 둔다.**

### 12가지 원칙 핵심

```
1. 최우선 목표: 고객을 만족시키는 소프트웨어를 빠르고 지속적으로 전달
2. 변화를 환영: 후반부에도 요구사항 변경을 수용
3. 짧은 배포 주기: 몇 주~몇 달 단위의 동작하는 소프트웨어 전달
4. 협력: 비즈니스 팀과 개발팀의 매일 협력
5. 동기부여된 개인: 필요한 환경과 지원을 제공하고 믿어라
6. 대면 대화: 가장 효율적인 의사소통 방법
7. 동작하는 소프트웨어: 진행의 주요 척도
8. 지속 가능한 개발: 일정한 페이스를 영구히 유지
9. 기술적 탁월성: 민첩성을 높이는 지속적인 기술적 관심
10. 단순성: 하지 않아도 되는 일의 양을 최대화
11. 자기 조직화 팀: 최고의 아키텍처와 요구사항은 자기 조직화 팀에서 나온다
12. 정기적 회고: 더 효과적인 방법을 찾아 팀 행동을 조정
```

## 3. 스크럼 프레임워크

스크럼은 애자일 방법론 중 가장 널리 쓰이는 프레임워크입니다.

### 3가지 역할

```
┌─────────────────────────────────────────────────────┐
│  Product Owner (PO)                                 │
│  - 제품 비전 정의, Product Backlog 관리             │
│  - 비즈니스 가치 우선순위 결정                      │
│  - 이해관계자와 개발팀의 중간 역할                  │
├─────────────────────────────────────────────────────┤
│  Scrum Master                                       │
│  - 스크럼 프로세스 가이드/코치                      │
│  - 장애물(impediment) 제거                          │
│  - 팀 보호 (외부 간섭 차단)                         │
├─────────────────────────────────────────────────────┤
│  Development Team (3~9명)                           │
│  - 실제 개발, 테스트, 배포                          │
│  - 자기 조직화 (how는 팀이 결정)                    │
│  - 크로스펑셔널 (프론트/백/인프라 포함)             │
└─────────────────────────────────────────────────────┘
```

### 3가지 산출물

```typescript
// Product Backlog: 제품의 모든 요구사항 목록
const productBacklog: UserStory[] = [
  {
    id: 'US-001',
    title: '사용자는 소셜 로그인으로 가입할 수 있다',
    acceptanceCriteria: [
      'Google, GitHub 로그인 지원',
      '최초 로그인 시 프로필 설정 페이지로 이동',
      '로그인 실패 시 에러 메시지 표시',
    ],
    storyPoints: 5,
    priority: 'HIGH',
  },
  // ...
];

// Sprint Backlog: 현재 스프린트에서 할 작업 목록
const sprintBacklog: Task[] = [
  { id: 'T-001', storyId: 'US-001', title: 'OAuth 연동 구현', estimate: 3, status: 'IN_PROGRESS' },
  { id: 'T-002', storyId: 'US-001', title: '소셜 로그인 UI 구현', estimate: 2, status: 'TODO' },
];

// Increment: 스프린트 종료 시 동작하는 소프트웨어
// (잠재적으로 출시 가능한 제품 증분)
```

### 번다운 차트

```
남은        ↑
스토리      │\
포인트      │  \  실제 진행
            │   \____
  이상적    │        \
  번다운    │ \       \___
            │  \_________\___→ 시간 (스프린트 날짜)
            └─────────────────→
            Day1  Day5  Day10
```

번다운 차트가 이상적 선보다 위에 있으면 → 스프린트 위험 신호

## 4. 스프린트 이벤트

```
Sprint Planning  →  Daily Scrum  →  Sprint Review  →  Sprint Retrospective
    (시작)           (매일)           (종료)              (종료 후)
    2~4시간          15분            1~2시간              1~2시간
```

### Sprint Planning

```
질문 1. "이번 스프린트에 무엇을 할 것인가?"
  - PO가 우선순위 설명
  - 팀이 완료 가능한 백로그 항목 선택
  - Sprint Goal 정의

질문 2. "어떻게 할 것인가?"
  - 선택한 항목을 세부 태스크로 분해
  - 각 태스크 담당자 자율 할당
  - 스토리 포인트 추정
```

### Sprint Review (데모)

```
참여자: 팀 + PO + 이해관계자
목적:   완성된 Increment 시연 및 피드백 수집
결과:   Product Backlog 업데이트
```

## 5. 칸반 vs 스크럼 비교

| 구분 | 스크럼 | 칸반 |
|------|--------|------|
| 반복 주기 | 고정 스프린트 (1~4주) | 연속적 흐름 |
| 역할 | PO, SM, Dev 팀 정의 | 역할 정의 없음 |
| 계획 | 스프린트 단위 | 필요시 |
| 변경 | 스프린트 중 변경 지양 | 언제든 변경 가능 |
| WIP 제한 | 없음 | 컬럼별 WIP 제한 |
| 진행 상황 | 번다운 차트 | 칸반 보드, 리드타임 |
| 적합한 팀 | 기능 개발 팀 | 운영/유지보수 팀 |

```
칸반 보드:
┌──────────┬──────────┬──────────┬──────────┐
│  Backlog  │  To Do   │  Doing   │   Done   │
│           │  (WIP≤5) │  (WIP≤3) │          │
├──────────┼──────────┼──────────┼──────────┤
│ 로그인   │ 마이페이지│ 결제 연동 │ 회원가입  │
│ 소셜연동 │ 알림기능  │          │ 상품목록  │
│ ...      │          │          │ ...       │
└──────────┴──────────┴──────────┴──────────┘
```

WIP(Work In Progress) 제한: 동시 진행 작업 수를 제한해 흐름을 개선

## 6. 데일리 스탠드업과 스프린트 회고

### 데일리 스탠드업 (Daily Scrum)

```
시간: 15분 (넘기지 않음)
형식: 스탠딩 미팅 (앉으면 길어짐)
목적: 동기화 + 장애물 파악

3가지 질문:
  1. 어제 무엇을 했나? (완료된 작업)
  2. 오늘 무엇을 할 것인가? (계획)
  3. 장애물이 있는가? (블로커)
```

```
// 좋은 스탠드업 발언 예시
"어제 결제 API 연동 작업을 완료했고,
오늘은 에러 처리 UI를 구현할 예정입니다.
PG사 sandbox 환경이 간헐적으로 내려가서 테스트가 어렵습니다."

// 나쁜 스탠드업 (세부 논의 금지)
"어제 결제 연동 했는데요, 그게 어떻게 동작하냐면..."
→ 상세 논의는 미팅 후 관련자끼리 별도 진행
```

### 스프린트 회고 (Sprint Retrospective)

```
목적: 팀의 프로세스 개선 (결과물이 아닌 일하는 방식)
참여: 개발팀 + SM (PO 선택)

4L 회고 기법:
┌──────────────────────────────────────────┐
│  Liked       │  Learned                 │
│  좋았던 점   │  배운 점                  │
├──────────────┼───────────────────────────┤
│  Lacked      │  Longed For              │
│  부족했던 점 │  앞으로 바라는 점         │
└──────────────┴───────────────────────────┘

KPT 기법:
  Keep:    잘 됐으니 계속 할 것
  Problem: 문제가 됐던 것
  Try:     다음 스프린트에 시도할 것
```

## 7. 개발자 관점에서의 애자일

### 기획-개발 협업 팁

```
1. 인수 조건(Acceptance Criteria)을 구체화하라
   Bad:  "로그인 기능 만들기"
   Good: Given 비로그인 유저가 / When 이메일+비밀번호 입력 후 로그인 클릭 /
         Then JWT 토큰 발급 후 홈으로 이동

2. Definition of Done(완료 기준)을 팀이 합의하라
   예시:
   - 코드 리뷰 승인 1명 이상
   - 단위 테스트 작성 및 통과
   - QA 확인 완료
   - 스테이징 배포 확인

3. 스프린트 중 요구사항 변경 대응
   - 긴급한 경우: PO와 협의 후 기존 항목과 교환 (범위 조정)
   - 다음 스프린트에 포함: Product Backlog에 추가
   - 절대 안 되는 것: 팀 동의 없이 스프린트 범위 추가
```

### 기술 부채와 스프린트

```typescript
// 스프린트 백로그에 기술 부채 포함하기
const sprintBacklog = [
  // 기능 스토리 (70%)
  { type: 'FEATURE', title: '주문 상세 페이지 구현', points: 8 },

  // 기술 부채 (20%)
  { type: 'TECH_DEBT', title: 'API 레이어 타입 안전성 개선', points: 3 },

  // 버그 (10%)
  { type: 'BUG', title: '모바일 결제 버튼 클릭 오류', points: 2 },
];

// 권장 비율: 기능 70% / 기술부채+리팩토링 20% / 버그 10%
```

### 애자일과 코드 품질

```
애자일의 오해: "빠른 개발" = "품질 희생"
현실:          지속 가능한 속도를 위해 품질이 필요

기술적 실천 (XP에서 유래):
  - TDD: 회귀를 방지해 리팩토링을 안전하게
  - 지속적 통합(CI): 매일 통합해 충돌 최소화
  - 페어 프로그래밍: 실시간 코드 리뷰
  - 리팩토링: 기능 추가 전 코드 정리
  - 작은 릴리즈: 위험 분산
```

### 스토리 포인트 추정

```
피보나치 수열 사용: 1, 2, 3, 5, 8, 13, 21, ...
  1  = 매우 간단 (버튼 색상 변경)
  3  = 보통 (목록 페이지 구현)
  5  = 복잡함 (외부 API 연동)
  8  = 매우 복잡 (새 결제 시스템)
  13 = 스플릿 필요 (너무 크면 이야기 분리)

Planning Poker:
  각자 카드로 동시 공개 → 차이가 크면 토론 → 재추정
```

## 8. 면접 포인트

**Q. 스크럼에서 스프린트 중간에 요구사항이 변경되면 어떻게 하나요?**

스프린트의 무결성을 위해 스프린트 중 범위 변경은 지양합니다. 긴급한 경우 PO와 협의해 기존 항목과 교환(swap)하거나, 그렇지 않으면 다음 스프린트의 Product Backlog에 추가합니다. 아주 긴급한 경우에는 현재 스프린트를 취소하고 재계획할 수 있습니다.

**Q. 스토리 포인트와 시간 추정의 차이는?**

스토리 포인트는 상대적 복잡도와 노력을 나타내는 추상적 단위입니다. 시간으로 환산하지 않는 이유는 같은 작업이라도 팀원마다 소요 시간이 다르고, 시간 기반 추정은 압박감을 주기 때문입니다. 팀의 속도(velocity: 스프린트당 완료 포인트)를 측정해 예측에 활용합니다.

**Q. 애자일이 실패하는 이유는?**

가장 흔한 원인은 "이름만 애자일"인 경우입니다. 스탠드업 회의만 하고 나머지는 워터폴인 경우, PO가 부재하거나 의사결정 권한이 없는 경우, 스프린트 회고에서 실질적 개선이 없는 경우가 대표적입니다. 애자일은 도구가 아닌 문화입니다.

**Q. 칸반과 스크럼 중 어떤 것을 선택해야 하나요?**

신규 기능 개발 중심 팀에는 스크럼이, 운영/고객지원/유지보수 팀에는 칸반이 적합합니다. 예측 가능한 배포 주기와 팀 속도 측정이 필요하면 스크럼, 요청이 불규칙적으로 들어오고 우선순위가 수시로 바뀌면 칸반이 맞습니다.

**Q. 개발자 입장에서 좋은 유저 스토리의 조건은?**

INVEST 원칙입니다. Independent(독립적), Negotiable(협의 가능), Valuable(가치 있음), Estimable(추정 가능), Small(작은 크기), Testable(테스트 가능)입니다. 특히 인수 조건(Acceptance Criteria)이 구체적으로 작성된 스토리가 구현하기 좋습니다.

## 9. 스토리 포인트 추정 심화

### Planning Poker

```
방법:
  1. PO가 유저 스토리 설명
  2. 팀원 각자 카드(숫자)를 선택 (동시 공개)
  3. 가장 높은 수와 낮은 수를 고른 사람이 이유 설명
  4. 재토론 후 재추정
  5. 합의가 이루어질 때까지 반복

카드 값: 피보나치 수열 (0, 1, 2, 3, 5, 8, 13, 21, ?) 또는
          T-shirt 크기 (XS, S, M, L, XL)

동시 공개 이유:
  → 먼저 공개된 수치에 영향받는 앵커링 편향 방지
  → 각자의 독립적 추정이 모여야 정확도 높아짐
```

### Fibonacci 수열을 쓰는 이유

```
1, 2, 3, 5, 8, 13, 21 ...

선형이 아닌 이유:
  1 → 2: 쉬운 작업의 구별 (1점과 2점의 차이는 작음)
  8 → 13: 복잡한 작업의 불확실성 인정

비선형 간격의 의미:
  - 5점 작업은 3점보다 정확히 67% 더 크지 않다
  - 복잡도가 커질수록 불확실성도 커진다는 것을 반영
  - 세밀한 구분이 무의미한 구간을 자연스럽게 합침

13점 이상 → 스토리 분할 신호:
  너무 크면 추정 오차가 너무 커짐
  → 더 작은 단위로 분해 후 재추정
```

### 팀 벨로시티 활용

```typescript
// 벨로시티 기반 스프린트 예측
interface SprintRecord {
  sprintNumber: number;
  completedPoints: number;
}

const sprintHistory: SprintRecord[] = [
  { sprintNumber: 1, completedPoints: 24 },
  { sprintNumber: 2, completedPoints: 28 },
  { sprintNumber: 3, completedPoints: 22 },
  { sprintNumber: 4, completedPoints: 30 },
  { sprintNumber: 5, completedPoints: 26 },
];

function calculateVelocity(history: SprintRecord[], last: number = 3): number {
  const recentSprints = history.slice(-last);
  const total = recentSprints.reduce((sum, s) => sum + s.completedPoints, 0);
  return Math.round(total / recentSprints.length);
}

const avgVelocity = calculateVelocity(sprintHistory); // 26

// 릴리즈 예측
const remainingBacklog = 130; // 남은 스토리 포인트
const estimatedSprints = Math.ceil(remainingBacklog / avgVelocity); // 약 5 스프린트
```

## 10. 스프린트 리뷰 vs 스프린트 회고

```
혼동하기 쉬운 두 이벤트의 차이:

┌────────────────────┬───────────────────────────────────────────┐
│ 구분               │ 스프린트 리뷰 (Review)                    │
├────────────────────┼───────────────────────────────────────────┤
│ 다른 이름          │ Sprint Demo, 데모                          │
│ 참여자             │ 팀 + PO + 이해관계자 (외부 포함 가능)      │
│ 초점               │ 무엇을 만들었나? (결과물)                  │
│ 주요 활동          │ Increment 시연, 피드백 수집                │
│ 산출물             │ Product Backlog 업데이트                   │
│ 소요 시간          │ 스프린트 1주당 1시간 (2주 → 2시간)        │
└────────────────────┴───────────────────────────────────────────┘

┌────────────────────┬───────────────────────────────────────────┐
│ 구분               │ 스프린트 회고 (Retrospective)              │
├────────────────────┼───────────────────────────────────────────┤
│ 참여자             │ 팀 + SM (PO는 선택, 이해관계자 없음)       │
│ 초점               │ 어떻게 일했나? (프로세스)                  │
│ 주요 활동          │ KPT, 4Ls 등 회고 기법, Action Item 도출   │
│ 산출물             │ 프로세스 개선 Action Item                  │
│ 소요 시간          │ 스프린트 1주당 45분 (2주 → 1.5시간)       │
└────────────────────┴───────────────────────────────────────────┘
```

### 실수하기 쉬운 경우

```
잘못된 패턴:
  리뷰에서 "이 기능이 왜 이렇게 됐어요?"
  → 이것은 회고에서 다룰 주제

  회고에서 "다음 스프린트 기능 어떻게 할까요?"
  → 이것은 Sprint Planning에서 다룰 주제

올바른 분리:
  리뷰: 제품에 관한 모든 것 (기능, 요구사항, 우선순위)
  회고: 팀의 일하는 방식 (프로세스, 협업, 도구)
```

## 11. Definition of Done vs Acceptance Criteria

### Definition of Done (완료의 정의)

```
팀 전체에 적용되는 완료 기준
→ 모든 유저 스토리가 "완료"가 되려면 갖춰야 할 조건

예시:
  □ 코드 리뷰 최소 1명 승인
  □ 단위 테스트 작성 및 통과 (커버리지 80% 이상)
  □ 빌드 성공 및 CI 통과
  □ 스테이징 환경 배포 확인
  □ QA 팀 승인
  □ 관련 문서 업데이트
  □ 접근성 기본 요건 충족 (WCAG 2.1 AA)

팀이 합의해서 정하고, 모든 스프린트에 일관되게 적용
```

### Acceptance Criteria (인수 조건)

```
특정 유저 스토리에만 적용되는 검증 조건
→ "이 기능이 올바르게 작동하는지" 확인 기준

유저 스토리: 사용자는 이메일로 로그인할 수 있다

인수 조건:
  □ Given: 올바른 이메일과 비밀번호 입력 시
    When:  로그인 버튼 클릭
    Then:  JWT 발급 후 홈 페이지로 이동
  
  □ Given: 틀린 비밀번호 입력 시
    Then:  "이메일 또는 비밀번호가 올바르지 않습니다" 에러 메시지 표시
  
  □ Given: 5회 연속 로그인 실패 시
    Then:  계정 잠금 + 이메일 알림 발송
  
  □ 비밀번호 찾기 링크 제공
```

### 비교 요약

```
┌──────────────────┬──────────────────────────────────────────────┐
│ 구분              │ 설명                                         │
├──────────────────┼──────────────────────────────────────────────┤
│ DoD               │ 팀 전체, 항상 동일, 프로세스 기준            │
│ Acceptance Criteria│ 스토리별로 다름, 기능 동작 기준             │
├──────────────────┼──────────────────────────────────────────────┤
│ 누가 정하나       │ DoD: 팀 전체 합의                            │
│                  │ AC: PO가 초안, 팀이 구체화                    │
├──────────────────┼──────────────────────────────────────────────┤
│ 언제 확인하나     │ DoD: 스프린트 리뷰 전                        │
│                  │ AC: 개발 완료 후 QA 단계                      │
└──────────────────┴──────────────────────────────────────────────┘

AC를 모두 만족해도 DoD를 충족하지 못하면 → 완료 아님
```

## 12. 번다운 차트 읽는 법

### 번다운 차트 기본 구조

```
남은        40 ┤
포인트      35 ┤ ×
(Story      30 ┤   \  × 이상적 번다운 (점선)
 Points)    25 ┤    ×  \
            20 ┤        × \
            15 ┤          × \    ← 실제 진행 (실선)
            10 ┤              × \  ×
             5 ┤                   × \
             0 ┤─────────────────────── ×
               D1  D3  D5  D7  D9 D10

이상적 번다운: 총 포인트 ÷ 스프린트 일수 만큼 매일 직선 감소
실제 번다운:   실제 완료된 포인트 누적
```

### 패턴별 해석

```
패턴 1 - 실선이 이상적 선보다 위에 있음:
  ↑ 계획보다 느린 진행
  원인: 작업이 예상보다 복잡, 예상 못한 이슈, 범위 추가
  대응: SM이 스탠드업에서 블로커 파악, PO와 범위 조정 협의

패턴 2 - 실선이 이상적 선보다 아래에 있음:
  ↓ 계획보다 빠른 진행
  원인: 과소 추정된 작업, 팀 역량 향상
  대응: 백로그에서 추가 항목 당겨오기 (PO 협의)

패턴 3 - 실선이 며칠간 수평 (평탄):
  → 작업이 완료되지 않는 구간 존재
  원인: 특정 작업이 블로킹됨, 의존성 문제
  대응: 블로커 즉시 해결

패턴 4 - 마지막에 급락:
  → 작업이 막판에 몰아서 완료됨
  원인: 작업 단위가 너무 크거나 지연 시작
  대응: 작업을 더 작은 단위로 분할

패턴 5 - 실선이 0에 닿지 않음:
  → 스프린트 목표 미달
  대응: 완료 못한 항목을 다음 스프린트로 이동 (재추정 필요)
```

### 번다운 vs 번업 차트

```
번다운 차트:
  남은 작업량의 감소를 보여줌
  직관적, 목표까지의 거리 파악 용이

번업 차트:
  완료된 작업량의 증가 + 전체 범위를 함께 표시

완료     ↑         ______ 전체 범위 (증가하면 범위 추가)
항목     │_____----
         │____----
         └────────────→ 날짜

번업의 장점: 범위 추가(scope creep)를 시각적으로 확인 가능
  → "완료가 늘었는데 왜 목표 달성을 못하지?"의 이유를 보여줌
```
