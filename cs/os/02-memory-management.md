## 1. 가상 메모리(Virtual Memory)

**가상 메모리**란 실제 물리 메모리(RAM)보다 큰 메모리 공간을 프로세스에게 제공하기 위한 메모리 관리 기법이다.
각 프로세스는 자신만의 가상 주소 공간(Virtual Address Space)을 가지며, 운영체제와 하드웨어(MMU)가 가상 주소를 물리 주소로 변환한다.

### 가상 메모리의 필요성

1. **메모리 격리**: 각 프로세스가 독립된 주소 공간을 가져 서로 침범 불가
2. **물리 메모리 초과 사용**: 자주 사용하지 않는 페이지를 디스크(스왑)로 내보내 더 많은 프로세스 실행 가능
3. **메모리 단순화**: 프로세스는 항상 0번지부터 시작하는 연속 공간으로 인식 (물리 메모리 배치와 무관)
4. **Copy-on-Write**: fork() 시 페이지를 즉시 복사하지 않고 쓰기 발생 시에만 복사하여 효율 향상

### 가상 주소 → 물리 주소 변환

```
프로세스 (Virtual Address)
         |
         | 가상 주소 0x00400000
         ↓
+------------------+
|       MMU        |  ← Memory Management Unit (하드웨어)
| (주소 변환 장치)  |
+------------------+
         |
         | 페이지 테이블 참조
         ↓
+------------------+
|   물리 메모리     |  ← Physical Address 0x1A300000
+------------------+
```

### 32비트 vs 64비트 가상 주소 공간

| 아키텍처 | 가상 주소 공간 크기 | 예시 |
|----------|------------------|------|
| 32비트 | 4GB (2^32) | 사용자 2GB + 커널 2GB |
| 64비트 | 이론상 16EB (2^64) | 실제 사용: ~128TB (x86-64) |

## 2. 페이징(Paging)

**페이징**은 가상 메모리를 고정 크기의 **페이지(Page)**로 나누고, 물리 메모리를 같은 크기의 **프레임(Frame)**으로 나누어 관리하는 방법이다.

### 페이징 메커니즘

```
Virtual Address Space          Physical Memory
+--------------------+         +--------------------+
| Page 0  (4KB)      | ──────→ | Frame 3  (4KB)     |
| Page 1  (4KB)      | ──────→ | Frame 7  (4KB)     |
| Page 2  (4KB)      | ──────→ | Frame 1  (4KB)     |
| Page 3  (4KB)      |  (swap) | Frame 5  (4KB)     |
| ...                |         | ...                |
+--------------------+         +--------------------+

* Page 3는 현재 물리 메모리에 없고 디스크(스왑)에 있음
```

### 페이지 테이블(Page Table)

각 프로세스마다 페이지 테이블을 가지며, 가상 페이지 번호를 물리 프레임 번호로 매핑한다.

```
페이지 테이블 엔트리(PTE) 구조:

+--------+--------+--------+--------+--------+--------+
| Frame# | Valid  |  Dirty |  Ref   |  Prot  | ...    |
+--------+--------+--------+--------+--------+--------+

- Frame#: 매핑된 물리 프레임 번호
- Valid Bit: 1이면 메모리에 있음, 0이면 디스크에 있음 (Page Fault 발생)
- Dirty Bit: 1이면 수정됨 → 스왑 아웃 시 디스크에 써야 함
- Reference Bit: 최근에 접근했는지 여부 (페이지 교체 알고리즘에 사용)
- Protection: 읽기/쓰기/실행 권한
```

### 주소 변환 과정

```
가상 주소 (32비트, 페이지 크기 4KB 기준)
+-------------------+----------------+
|   VPN (20비트)    |  Offset (12비트)|
+-------------------+----------------+
         |                  |
         | 페이지 테이블 조회  |
         ↓                  |
+-------------------+       |
|   PFN (Frame 번호) |       |
+-------------------+       |
         |                  |
         ↓                  ↓
+-------------------+----------------+
|   PFN (20비트)    |  Offset (12비트)|
+-------------------+----------------+
         물리 주소 완성
```

### 다단계 페이지 테이블 (Multi-level Page Table)

64비트 시스템에서 단일 페이지 테이블은 너무 큼. x86-64는 4단계 페이지 테이블을 사용한다.

```
Virtual Address (48비트 유효)
+-------+-------+-------+-------+-------------+
| PML4  |  PDP  |  PD   |  PT   |   Offset    |
| (9비트)| (9비트)| (9비트)| (9비트)|  (12비트)   |
+-------+-------+-------+-------+-------------+

CR3 레지스터 → PML4 Table → PDP Table → PD Table → PT → Physical Frame
```

### 코드 예시: 페이지 크기 확인 (Linux/macOS)

```c
#include <stdio.h>
#include <unistd.h>

int main() {
    long page_size = sysconf(_SC_PAGESIZE);
    printf("페이지 크기: %ld bytes (%ld KB)\n", page_size, page_size / 1024);
    return 0;
}
// 출력: 페이지 크기: 4096 bytes (4 KB)
```

```python
import resource

# Python에서 페이지 크기 확인
page_size = resource.getpagesize()
print(f"페이지 크기: {page_size} bytes ({page_size // 1024} KB)")
```

## 3. TLB(Translation Lookaside Buffer)

**TLB**는 페이지 테이블 접근 속도를 높이기 위한 **하드웨어 캐시**다.
최근에 사용한 가상 주소 → 물리 주소 매핑을 저장하여, 페이지 테이블 조회(메모리 접근) 없이 빠르게 변환할 수 있다.

### TLB 동작 과정

```
CPU가 가상 주소 생성
         |
         ↓
+------------------+
|   TLB 검색        |
|  (하드웨어 캐시)   |
+------------------+
    |         |
TLB Hit     TLB Miss
    |             |
    | 빠르게       | 페이지 테이블 접근 (메모리)
    | 물리 주소 획득 |
    |             ↓
    |     +----------------+
    |     |  Page Table    |
    |     |  조회 (느림)    |
    |     +----------------+
    |             |
    |             | TLB에 새 항목 추가
    ↓             ↓
      물리 주소로 메모리 접근
```

### TLB 성능 지표

- **TLB Hit Rate**: TLB에서 바로 찾는 비율. 일반적으로 99% 이상
- **TLB Miss**: 페이지 테이블에서 찾아야 하며 수백 사이클 추가 소요
- **TLB Size**: 일반적으로 L1 TLB는 64~128개 엔트리, L2 TLB는 512~1024개 엔트리

### TLB와 컨텍스트 스위칭

프로세스 전환 시 각 프로세스의 가상 주소 공간이 다르므로 TLB 내용이 무효화된다.
- **TLB Flush**: 스위칭 시 TLB 전체를 비움 → 다음 프로세스 초기에 TLB Miss 증가
- **ASID (Address Space ID)**: 현대 CPU는 TLB 엔트리에 프로세스 ID를 태그하여 플러시 없이 공존 가능

## 4. 스왑(Swap)과 페이지 교체 알고리즘

### 스왑(Swap) 공간

물리 메모리가 부족할 때, 운영체제는 현재 사용하지 않는 페이지를 디스크의 스왑 공간으로 옮기고(Swap Out) 그 프레임을 다른 용도로 사용한다.
나중에 해당 페이지가 필요해지면 디스크에서 다시 메모리로 불러온다(Swap In).

```
[Page Fault 처리 과정]

프로세스가 Page X에 접근
         |
         | Valid Bit = 0 (메모리에 없음)
         ↓
    Page Fault 발생
         |
         ↓
  OS가 디스크(스왑)에서 Page X 로드
         |
         | 빈 프레임 있음?
    Y    |    N
    |    |    ↓
    |    |  희생 페이지 선택 (교체 알고리즘)
    |    |    |
    |    |    | Dirty하면 디스크에 기록(Swap Out)
    |    |    ↓
    ↓    |  프레임 확보
  Page X를 프레임에 적재
         |
         | 페이지 테이블 업데이트 (Valid Bit = 1)
         ↓
  프로세스 재시작
```

### 페이지 교체 알고리즘

#### FIFO (First-In, First-Out)

가장 먼저 들어온 페이지를 교체한다.

```
참조 순서: 1 2 3 4 1 2 5 1 2 3 4 5
프레임 수: 3

Step 1: [1, -, -]  → Miss (1 적재)
Step 2: [1, 2, -]  → Miss (2 적재)
Step 3: [1, 2, 3]  → Miss (3 적재)
Step 4: [4, 2, 3]  → Miss (1 교체 → 4 적재) ← FIFO: 가장 오래된 1 교체
Step 5: [4, 1, 3]  → Miss (2 교체 → 1 적재)
Step 6: [4, 1, 2]  → Miss (3 교체 → 2 적재)
Step 7: [5, 1, 2]  → Miss (4 교체 → 5 적재)
...
총 Page Fault: 9번
```

단점: **Belady's Anomaly** - 프레임 수를 늘렸는데 오히려 Page Fault가 증가하는 현상 발생 가능.

#### LRU (Least Recently Used)

가장 오랫동안 사용되지 않은 페이지를 교체한다. 과거 접근 패턴이 미래에도 유사하다는 가정.

```python
from collections import OrderedDict

class LRUCache:
    def __init__(self, capacity: int):
        self.capacity = capacity
        self.cache = OrderedDict()  # 삽입 순서 유지

    def get(self, page: int) -> bool:
        if page in self.cache:
            # 가장 최근 사용으로 이동
            self.cache.move_to_end(page)
            return True  # Hit
        return False  # Miss

    def put(self, page: int):
        if page in self.cache:
            self.cache.move_to_end(page)
        else:
            if len(self.cache) >= self.capacity:
                # 가장 오래된 항목(맨 앞) 제거
                evicted = next(iter(self.cache))
                del self.cache[evicted]
                print(f"  페이지 {evicted} 교체")
            self.cache[page] = True

# 시뮬레이션
pages = [1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5]
lru = LRUCache(3)
faults = 0

for page in pages:
    if not lru.get(page):
        print(f"Page Fault: 페이지 {page}")
        lru.put(page)
        faults += 1

print(f"총 Page Fault: {faults}번")
```

#### Clock (Second-Chance) 알고리즘

FIFO의 변형으로, Reference Bit를 활용한다. 하드웨어 구현이 단순하여 실제 OS에서 많이 사용.

```
프레임을 원형 큐로 관리:
                    ↑ (손 포인터)
[Page 1, R=1] → [Page 2, R=0] → [Page 3, R=1] → [Page 4, R=0]
     ↑ 포인터

교체 시:
- R=1이면: R=0으로 바꾸고 다음으로 이동 (두 번째 기회 부여)
- R=0이면: 해당 페이지 교체

결과: Page 2 교체 (R=0이므로)
```

#### 알고리즘 비교

| 알고리즘 | 구현 복잡도 | 성능 | 특징 |
|---------|-----------|------|------|
| FIFO | 낮음 | 낮음 | Belady's Anomaly 가능 |
| LRU | 높음 | 좋음 | 하드웨어 지원 필요 |
| Clock | 중간 | 좋음 | LRU 근사치, 실제 OS 사용 |
| Optimal | 낮음 | 최적 | 미래 참조 순서를 알아야 함 (이론상) |

## 5. 메모리 단편화

**단편화(Fragmentation)**란 메모리 공간이 있음에도 불구하고 적절히 할당하지 못하는 현상이다.

### 내부 단편화 (Internal Fragmentation)

할당된 메모리 블록이 요청한 크기보다 클 때 발생하는 낭비.
페이징에서 발생: 프로세스가 마지막 페이지를 다 채우지 않으면 남은 공간이 낭비됨.

```
페이지 크기: 4KB = 4096 bytes
프로세스 요청: 9000 bytes

페이지 1: [||||||||||||||||] 4096 bytes 사용
페이지 2: [||||||||||||||||] 4096 bytes 사용
페이지 3: [||||    ] 808 bytes 사용 + 3288 bytes 낭비 ← 내부 단편화
```

내부 단편화 크기 = `페이지 수 * 페이지 크기 - 실제 필요 크기`
= `3 * 4096 - 9000` = `3288 bytes`

### 외부 단편화 (External Fragmentation)

사용 가능한 메모리의 합은 충분하지만, 연속된 공간이 없어 할당하지 못하는 현상.
연속 메모리 할당 방식에서 발생.

```
메모리 상태 (16KB 총 크기):
+------+--------+------+--------+------+
| 사용  |  빈공간 | 사용  |  빈공간 | 사용  |
| 2KB  |  2KB   | 4KB  |  2KB   | 6KB  |
+------+--------+------+--------+------+

빈 공간 합계: 4KB
새 프로세스 요청: 3KB

→ 각 빈 공간(2KB, 2KB)이 3KB보다 작아 할당 불가
→ 외부 단편화 발생
```

### 단편화 해결 방법

| 방법 | 대상 단편화 | 설명 |
|------|-----------|------|
| 컴팩션(Compaction) | 외부 | 사용 중인 메모리를 한쪽으로 모아 연속 공간 확보 (오버헤드 큼) |
| 페이징 | 외부 | 비연속 메모리 할당으로 외부 단편화 원천 차단 |
| 버디 시스템(Buddy System) | 외부 | 2의 거듭제곱 크기로 분할/합병하여 단편화 최소화 |
| 슬랩 할당자(Slab Allocator) | 내부 | 같은 크기 객체를 미리 할당해두어 내부 단편화 최소화 |
| 페이지 크기 축소 | 내부 | 작은 페이지 크기 사용 (단, 페이지 테이블 크기 증가) |

### 코드 예시: 메모리 할당 시 단편화 이해

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main() {
    // malloc은 내부적으로 메모리 풀을 관리하며 단편화 최소화 시도
    char *p1 = malloc(10);   // 10 bytes 요청 → 실제 16bytes 할당 (정렬)
    char *p2 = malloc(1);    // 1 byte 요청 → 실제 16bytes 할당 (내부 단편화 발생)
    char *p3 = malloc(100);  // 100 bytes 요청

    free(p2);   // p2 해제 → 중간에 빈 공간 생김 (외부 단편화 가능성)

    // p4는 p2 자리(16bytes)에 들어가기에는 너무 큼
    char *p4 = malloc(50);  // p2 자리에 못 들어갈 수도 있음

    printf("p1=%p, p3=%p, p4=%p\n", p1, p3, p4);

    free(p1);
    free(p3);
    free(p4);
    return 0;
}
```

## 6. 세그멘테이션(Segmentation)

**세그멘테이션**은 프로세스를 논리적 의미 단위인 **세그먼트(Segment)**로 나누어 관리하는 방법이다.
페이징은 고정 크기로 나누지만, 세그멘테이션은 가변 크기로 나눈다.

### 세그먼트 구성

```
프로세스 메모리
+-------------------+
|  Code Segment     |  세그먼트 0 (읽기/실행)
+-------------------+
|  Data Segment     |  세그먼트 1 (읽기/쓰기)
+-------------------+
|  Stack Segment    |  세그먼트 2 (읽기/쓰기)
+-------------------+
|  Heap Segment     |  세그먼트 3 (읽기/쓰기)
+-------------------+
```

### 세그먼트 테이블

```
세그먼트 테이블:
+-------+---------+-------+-------+
|  Seg# |  Base   | Limit | Perm  |
+-------+---------+-------+-------+
|   0   | 0x1000  | 0x400 |  R-X  |
|   1   | 0x2000  | 0x200 |  RW-  |
|   2   | 0x5000  | 0x800 |  RW-  |
|   3   | 0x7000  | 0x600 |  RW-  |
+-------+---------+-------+-------+

가상 주소: (세그먼트 번호, 오프셋)
예: (1, 0x50) → 세그먼트 1의 Base(0x2000) + 0x50 = 0x2050
```

### 페이징 vs 세그멘테이션

| 구분 | 페이징 | 세그멘테이션 |
|------|--------|------------|
| 분할 단위 | 고정 크기 (4KB) | 가변 크기 |
| 단편화 | 내부 단편화 | 외부 단편화 |
| 주소 구조 | 페이지 번호 + 오프셋 | 세그먼트 번호 + 오프셋 |
| 공유 | 페이지 단위 공유 | 세그먼트 단위 공유 (의미 있는 단위) |
| 보호 | 페이지 단위 | 세그먼트 단위 (코드/데이터 분리) |

현대 OS(Linux, Windows)는 **세그멘테이션 + 페이징**을 혼합하여 사용한다.

## 7. 면접 포인트

### Q1. 가상 메모리란 무엇이고 왜 필요한가요?

> 가상 메모리는 실제 물리 메모리보다 큰 주소 공간을 각 프로세스에 제공하는 기법입니다. 필요성은 크게 세 가지입니다. 첫째, 프로세스 간 메모리 격리로 안전성을 보장합니다. 둘째, 디스크(스왑)를 활용해 물리 메모리보다 많은 프로세스를 실행할 수 있습니다. 셋째, 각 프로세스가 연속된 주소 공간으로 인식하게 하여 프로그래밍을 단순화합니다.

### Q2. 페이지 폴트(Page Fault)란 무엇인가요?

> 프로세스가 접근하려는 페이지가 현재 물리 메모리에 없을 때 발생하는 인터럽트입니다. OS는 Page Fault를 처리할 때 디스크(스왑)에서 해당 페이지를 찾아 빈 프레임에 로드하고, 페이지 테이블을 업데이트한 후 프로세스를 재시작합니다. 이 과정에서 디스크 I/O가 발생하므로 매우 느립니다.

### Q3. TLB란 무엇이며 왜 필요한가요?

> TLB(Translation Lookaside Buffer)는 페이지 테이블의 최근 사용 항목을 저장하는 하드웨어 캐시입니다. 페이지 테이블은 메모리에 있어서 가상→물리 주소 변환 시 추가 메모리 접근이 필요한데, TLB를 이용하면 이 과정을 캐시에서 빠르게 처리할 수 있습니다. TLB Hit Rate는 99% 이상으로 매우 높아 성능에 큰 기여를 합니다.

### Q4. LRU 페이지 교체 알고리즘을 설명하세요.

> LRU(Least Recently Used)는 가장 오랫동안 사용되지 않은 페이지를 교체하는 알고리즘입니다. 과거의 참조 패턴이 미래에도 유지된다는 지역성(Locality) 원리에 기반합니다. 구현 방법으로는 타임스탬프를 기록하거나 OrderedDict(연결 리스트 + 해시맵)를 사용하는 방법이 있습니다. 하드웨어 지원 없이는 구현 비용이 높아 실제 OS에서는 Clock 알고리즘 같은 LRU 근사 방법을 사용합니다.

### Q5. 내부 단편화와 외부 단편화의 차이는?

> 내부 단편화는 할당된 메모리 블록 내부의 남는 공간으로, 페이징에서 마지막 페이지가 다 채워지지 않을 때 발생합니다. 외부 단편화는 메모리 합계는 충분하지만 연속된 공간이 없어 할당에 실패하는 경우로, 가변 크기 메모리 할당 방식에서 발생합니다. 페이징은 외부 단편화를 방지하지만 내부 단편화가 생기고, 세그멘테이션은 내부 단편화는 없지만 외부 단편화가 발생합니다.

### Q6. Thrashing이란 무엇인가요?

> **스레싱(Thrashing)**은 프로세스들이 실제 작업보다 페이지 교체(Page Fault 처리)에 더 많은 시간을 쓰는 상황입니다. 너무 많은 프로세스가 실행되어 각 프로세스에 할당된 프레임 수가 너무 적어지면, 자주 필요한 페이지도 계속 교체되며 CPU 이용률이 급감합니다. 해결 방법으로는 Working Set 모델(현재 사용 중인 페이지 집합 보장)이나 프로세스 수를 줄이는 방법이 있습니다.
